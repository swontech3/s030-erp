# Requirements: SwonBiz ERP

**Defined:** 2026-09-01
**Core Value:** 운영사가 계약을 시스템 안에서 끝까지 처리할 수 있어야 한다 — 입주사 등록부터 계약 확정(`confirmed`)과 계약서 출력까지.

## v1 Requirements

1차 마일스톤 범위. 각 항목은 로드맵 페이즈에 매핑된다.

- [ ] **PLAT-02**: 화면 ID ↔ 라우트 매핑이 `lib/screens.ts` 한 곳에서 관리되고, 각 `page.tsx` 상단에 화면 ID 주석이 있다
- [ ] **PLAT-03**: 디자인 토큰(색·타이포·간격·shape)이 `styles/tokens.css`에 `.dc.html` 템플릿에서 그대로 이관되어 있다
- [ ] **PLAT-04**: DS 컴포넌트 15종(Button, IconButton, Icon, Card, Badge, Tag, Input, Select, Checkbox, Radio, Switch, Tabs, Dialog, Toast, Tooltip)이 템플릿 마크업 그대로 구현되어 있다

- [ ] **PLAT-06**: 미확정 상수(예약 시간·요금·QR URL·계약 한도·계약서 기본 담당자·기본 센터명)가 `lib/constants.ts` 한 곳에 모여 있다

- [ ] **PLAT-08**: `typescript@5.9.3`이 명시적으로 고정되어 있다 (`latest`는 Go 네이티브 TS 7.x로 해석됨)

### Authentication (인증 · 삐용 JWT 통합)

> **2026-09-06 개정.** `doc/지시_ERP_로그인_권한관리.md` 수령으로 6건이 폐기·수정됐다.
> 대조 근거는 `doc/AUTH_ACL_RECONCILIATION.md` §1. 원안은 ERP가 자체 세션을 발급하는
> 구조였고, 지시서는 **삐용 토큰을 그대로 쓰고 판정은 삐용에 묻는** 구조를 확정했다.

- [ ] **AUTH-01**: 사용자는 삐용 계정으로 ERP에 로그인할 수 있다 (ERP 전용 계정 발급 없음)
- [ ] **AUTH-02**: *(보류 — 회신 ⑩)* 겸직을 지원하는 경우에만 2단계 로그인(계정 확인 → 조직 선택)을 둔다. `tb_s020_member010.org_id`가 단일 컬럼이라 미지원이면 이 항목과 `s0300000010p1`을 폐기한다
- [ ] **AUTH-03′**: ERP는 삐용 로그인 API를 직접 호출하고, 받은 토큰을 저장해 이후 요청에 싣는다. 저장 위치는 삐용 구현을 따른다 *(회신 ④ 대기)* — 지시서 1-2
- [ ] ~~**AUTH-04**~~: **폐기.** ERP는 자체 토큰을 발급하지 않는다 — 지시서 3장
- [ ] **AUTH-05′**: 서버는 모든 보호된 요청에서 **삐용 JWT**를 독립적으로 검증한다 (프런트 미들웨어 통과 여부와 무관)
- [ ] **AUTH-06′**: 모든 토큰 검증이 단일 진입점(`lib/auth/verifyToken.ts`)을 거치며, 알고리즘 허용 목록·`iss`·`aud`·`exp`를 명시적으로 검사하고 클레임을 Zod로 검증한다. **검증된 클레임은 표시 용도로만 쓴다** — 권한·범위 판정에 쓰지 않는다 (지시서 1-6)
- [ ] **AUTH-07**: 액세스 토큰 만료 시 세션이 자동 갱신되며, 동시 요청이 겹쳐도 갱신은 한 번만 일어난다 (single-flight). **TTL과 회전 방식은 삐용 구현에 맞춘다** *(회신 ⑤ 대기)* — 지시서 1-5
- [ ] **AUTH-08**: 세션 만료 시 사용자는 `/login?redirect=`로 이동하고, 로그인 후 원래 가려던 화면으로 돌아온다
- [ ] **AUTH-09′**: 로그인 직후 삐용에 접근 가능 화면 목록을 물어, 그 목록의 첫 화면을 홈으로 삼는다. ERP가 역할을 보고 분기하지 않는다
- [ ] **AUTH-10′**: 목록에 없는 화면 URL로 직접 접근하면 접근 가능한 화면으로 보낸다. 판단 근거는 삐용 응답이며 토큰 클레임이 아니다
- [ ] **AUTH-11**: 사용자는 로그아웃할 수 있고, 로그아웃 후 인증 화면 외에는 접근할 수 없다
- [ ] **AUTH-12**: 삐용 개발 환경 없이도 목(mock) 로그인으로 전체 인증 흐름을 실행할 수 있다
- [ ] **AUTH-13**: 로그인은 됐으나 접근 가능 화면이 0건이면 안내 문구를 띄운다 — "이 계정은 ERP 이용 권한이 없습니다. 담당자에게 문의하세요." (지시서 1-7. `tb_s020_org_module010`이 0행이라 현재는 전 계정이 해당)
- [ ] **AUTH-14**: 비밀번호 재설정·이메일 변경·회원가입 화면을 만들지 않는다. 로그인 화면의 "비밀번호 찾기"는 삐용 해당 화면으로 보내는 링크다 (지시서 1-3 → 화면 `s0300000020`·`s0300000030`·`s0300000040` 폐기)
- [ ] **SEC-01**: 토큰이 브라우저 저장소에 놓이는 구조(AUTH-03′)의 대가로 CSP를 적용하고 의존성 감사를 CI에 건다

### Access Control (권한 · 멀티테넌트 격리)

> **2026-09-06 개정.** 지시서 2-1이 **ERP의 권한 판정 자체를 금지**한다. ERP는 역할 표도
> 권한 표도 접근 제어 로직도 두지 않고, 화면 진입 시 삐용에 물어 답대로 연다.

- [ ] **ACL-01′**: ERP는 역할을 저장하지 않는다. 저장하는 것은 삐용 조직 ↔ ERP 입주사의 대응 하나이며(`tb_s080_companies.link_s020_org_id`, FK 없음), 이는 권한이 아니라 데이터 소유자 식별이다. 선례는 `tb_s090_org010.link_s020_org_id`
- [ ] **ACL-02**: 테넌트 스코프 테이블은 공용 스코프 헬퍼를 통해서만 조회된다 — 목록·상세·검색·자동완성·내보내기 모두 예외 없이. 범위는 `본인 것만` / `회사 전체` **2종뿐**이며 부서·타사 범위는 만들지 않는다 (지시서 2-4)
- [ ] **ACL-03**: 회사 식별자와 범위는 검증된 세션·삐용 응답에서만 읽으며, 클라이언트가 보낸 값은 절대 신뢰하지 않는다 (지시서 3장 "✗ 요청에서 회사번호 받기" — 8월 명부 유출의 직접 원인)
- [ ] **ACL-04**: 입주사가 타사 리소스 ID로 직접 접근하면 "없음"과 "내 것 아님"이 동일한 404로 응답한다 (존재 여부가 새지 않음)
- [ ] **ACL-05**: 마스킹은 서버에서 필드를 아예 빼는 방식으로 이뤄진다 — 빈 문자열 치환이나 프런트 숨김이 아니다
- [ ] **ACL-06**: 입주사는 타사 예약을 "예약됨"으로만 조회하며 제목·조직명·인원이 응답에 포함되지 않는다
- [ ] **ACL-07′**: 사이드바는 삐용이 준 접근 가능 화면 목록만 그린다. ERP가 역할을 보고 거르지 않는다. 화면 숨김은 편의이고 실제 통제는 서버다 (지시서 2-9)
- [ ] **ACL-08**: 권한 판정에 shadow 모드를 둔다 — 1단계는 막지 않고 "막았을 것"만 기록하고, 기록이 0건이 되면 실제 차단으로 전환한다 (지시서 2-12)
- [ ] **ACL-09**: 화면 개발 완료 시 화면·동작 목록을 삐용 화면 마스터에 제출한다. **팝업·상세·모달을 빠뜨리지 않는다** — 마스터에 없으면 권한 체크 대상이 없어 그냥 뚫린다 (지시서 2-6 ③)
- [ ] **ACL-10**: 동작 어휘는 `VIEW`·`CREATE`·`UPDATE`·`DELETE` 4종이며 `APPROVE`·`EXPORT`를 쓰지 않는다 (지시서 2-8)
- [ ] **ACL-11**: 운영사 전용 화면(입주 계약 관리, 청구·수납)은 고객사 화면과 섞지 않는다. 화면 마스터 등록 시 대상 구분을 정확히 붙인다 — 하나만 잘못 분류돼도 샌다 (지시서 2-10)
- [ ] **ACL-12**: `company_id` 격리를 **DB에서도 강제한다** — `contracts`·`invoices`·`payments`·`settlements`·`members`·`reservations` 6테이블에 RLS를 켜고, Fastify는 BYPASSRLS 없는 `erp_app` 역할로 접속해 트랜잭션마다 `SET LOCAL app.current_company_id`·`app.current_role`을 세팅한다 (`003_revoke_public.sql`). **2026-09-06 결정** — 애플리케이션 스코프 헬퍼(ACL-02)를 대체하지 않고 병행한다: 헬퍼를 안 거친 쿼리가 생겨도 DB가 막는다
- [ ] **ACL-13**: RLS가 실제로 동작함을 검증한다 — (a) `withCompanyScope`를 거치지 않은 쿼리가 **0건**을 반환하고(정책만 만들고 `ENABLE ROW LEVEL SECURITY`를 빠뜨리는 실수가 흔하다), (b) `003` 적용 후 기존 S-WonERP 앱의 계약 목록·상세가 정상 동작한다
