# Requirements: SwonBiz ERP

**Defined:** 2026-09-01
**Core Value:** 운영사가 계약을 시스템 안에서 끝까지 처리할 수 있어야 한다 — 입주사 등록부터 계약 확정(`confirmed`)과 계약서 출력까지.

## v1 Requirements

1차 마일스톤 범위. 각 항목은 로드맵 페이즈에 매핑된다.

### Platform (플랫폼 · 기반)

- [ ] **PLAT-01**: 개발자는 `s030_*` 스키마 변경을 Drizzle 스키마 → `drizzle-kit generate` → `supabase/migrations/` → Supabase CLI 순서로 적용할 수 있다 (`drizzle-kit push` 사용 금지 — `s020_*`/`s040_*`와 DB 공유)
- [ ] **PLAT-02**: 화면 ID ↔ 라우트 매핑이 `lib/screens.ts` 한 곳에서 관리되고, 각 `page.tsx` 상단에 화면 ID 주석이 있다
- [ ] **PLAT-03**: 디자인 토큰(색·타이포·간격·shape)이 `styles/tokens.css`에 `.dc.html` 템플릿에서 그대로 이관되어 있다
- [ ] **PLAT-04**: DS 컴포넌트 15종(Button, IconButton, Icon, Card, Badge, Tag, Input, Select, Checkbox, Radio, Switch, Tabs, Dialog, Toast, Tooltip)이 템플릿 마크업 그대로 구현되어 있다
- [ ] **PLAT-05**: 녹색 계열 색상이 코드에 들어오면 lint가 실패한다 (리뷰어 기억이 아니라 자동 검사로 강제)
- [ ] **PLAT-06**: 미확정 상수(예약 시간·요금·QR URL·계약 한도·계약서 기본 담당자·기본 센터명)가 `lib/constants.ts` 한 곳에 모여 있다
- [ ] **PLAT-07**: JWT 시크릿과 DB 접속 정보가 `.env`에만 있고 코드에 하드코딩되어 있지 않다
- [ ] **PLAT-08**: `typescript@5.9.3`이 명시적으로 고정되어 있다 (`latest`는 Go 네이티브 TS 7.x로 해석됨)

### Authentication (인증 · 삐용 JWT 통합)

- [ ] **AUTH-01**: 사용자는 삐용 계정으로 ERP에 로그인할 수 있다 (ERP 전용 계정 발급 없음)
- [ ] **AUTH-02**: 사용자는 2단계 로그인을 거친다 — 계정 확인 후 소속 조직을 선택한다
- [ ] **AUTH-03**: 브라우저는 삐용의 토큰을 절대 보유하지 않는다 — 삐용 호출은 Next.js Route Handler에서 서버-서버로만 일어난다
- [ ] **AUTH-04**: 로그인 성공 시 ERP가 자체 세션 JWT를 발급해 httpOnly 쿠키로 내려준다
- [ ] **AUTH-05**: Fastify는 모든 요청에서 ERP 세션 JWT를 독립적으로 검증한다 (Next.js 미들웨어 통과 여부와 무관)
- [ ] **AUTH-06**: 모든 토큰 검증이 단일 진입점(`lib/auth/verifyToken.ts`)을 거치며, 알고리즘 허용 목록·`iss`·`aud`·`exp`를 명시적으로 검사하고 클레임을 Zod로 검증한다
- [ ] **AUTH-07**: 액세스 토큰 만료 시 세션이 자동 갱신되며, 동시 요청이 겹쳐도 갱신은 한 번만 일어난다 (single-flight)
- [ ] **AUTH-08**: 세션 만료 시 사용자는 `/login?redirect=`로 이동하고, 로그인 후 원래 가려던 화면으로 돌아온다
- [ ] **AUTH-09**: 로그인 후 홈이 역할에 따라 분기된다 — 운영사는 `/dashboard`, 입주사는 `/booking`
- [ ] **AUTH-10**: 입주사가 운영사 전용 화면(`role: 'operator'`) URL에 직접 접근하면 `/booking`으로 리다이렉트된다
- [ ] **AUTH-11**: 사용자는 로그아웃할 수 있고, 로그아웃 후 인증 화면 외에는 접근할 수 없다
- [ ] **AUTH-12**: 삐용 개발 환경 없이도 목(mock) 로그인으로 전체 인증 흐름을 실행할 수 있다

### Access Control (권한 · 멀티테넌트 격리)

- [ ] **ACL-01**: 삐용의 `member_id` + 선택한 `org_id`가 ERP의 `tenant_id` + `role`(운영사/입주사)로 매핑된다 (`s030_org_member`)
- [ ] **ACL-02**: 테넌트 스코프 테이블은 공용 스코프 헬퍼를 통해서만 조회된다 — 목록·상세·검색·자동완성·내보내기 모두 예외 없이
- [ ] **ACL-03**: `tenantId`와 `role`은 검증된 세션에서만 읽으며, 클라이언트가 보낸 값은 절대 신뢰하지 않는다
- [ ] **ACL-04**: 입주사가 타사 리소스 ID로 직접 접근하면 "없음"과 "내 것 아님"이 동일한 404로 응답한다 (존재 여부가 새지 않음)
- [ ] **ACL-05**: 마스킹은 서버에서 필드를 아예 빼는 방식으로 이뤄진다 — 빈 문자열 치환이나 프런트 숨김이 아니다
- [ ] **ACL-06**: 입주사는 타사 예약을 "예약됨"으로만 조회하며 제목·조직명·인원이 응답에 포함되지 않는다
- [ ] **ACL-07**: 입주사에게는 사이드바에 운영사 전용 항목이 아예 렌더링되지 않는다

### Master Data (기준관리)

- [ ] **MAST-01**: 운영사는 건물을 등록·수정·삭제할 수 있다
- [ ] **MAST-02**: 운영사는 건물에 속한 층을 등록·수정·삭제할 수 있다
- [ ] **MAST-03**: 운영사는 층에 속한 호실을 등록·수정·삭제할 수 있다
- [ ] **MAST-04**: 운영사는 회의실을 등록·수정·삭제할 수 있다
- [ ] **MAST-05**: 회의실별 예약 설정값이 비어 있으면 전사 기본값을 따르고, 값이 있으면 그 값이 우선한다
- [ ] **MAST-06**: 계약이나 예약이 참조 중인 호실·회의실은 삭제되지 않고 명확한 사유가 표시된다
- [ ] **MAST-07**: 센터 관리 화면이 건물 셀렉트 + 층 탭 + 테이블 조합으로 동작한다 (트리 UI 없음)

### Tenants (입주사)

- [ ] **TNNT-01**: 운영사는 입주사를 등록할 수 있다 (사업자등록번호·연락처·담당자 포함)
- [ ] **TNNT-02**: 운영사는 입주사 목록을 조회하고 검색할 수 있다
- [ ] **TNNT-03**: 운영사는 입주사 상세에서 해당 입주사의 계약 목록을 볼 수 있다
- [ ] **TNNT-04**: 사업자등록번호가 형식 검증되며 중복 등록이 차단된다
- [ ] **TNNT-05**: 입주사·계약 마스터-디테일 화면에서 좌측 입주사 선택 시 우측에 계약이 표시된다

### Contracts (계약)

- [ ] **CONT-01**: 운영사는 계약을 3가지 모드로 생성할 수 있다 — 신규 입주사 / 기존 입주사의 신규 계약 / 재계약
- [ ] **CONT-02**: 재계약 시 직전 계약의 계약 항목·조건·사용자 목록이 복사되고 기간만 갱신된다 (첨부파일은 복사하지 않음)
- [ ] **CONT-03**: 계약 폼에서 4개 섹션을 입력하고 저장할 수 있다
- [ ] **CONT-04**: 계약 항목을 최대 10행까지 추가·수정·삭제할 수 있다
- [ ] **CONT-05**: 계약 항목은 유형 구분자를 가진다 — 호실뿐 아니라 주차·사물함·가상오피스·전용데스크 등 호실 없는 항목도 등록된다
- [ ] **CONT-06**: 계약 사용자를 최대 20명까지 등록·수정·삭제할 수 있다
- [ ] **CONT-07**: 계약 상태를 전이할 수 있다 — `draft → confirmed → terminated`, `draft → cancelled`
- [ ] **CONT-08**: 허용되지 않은 상태 전이는 서버가 거부한다 — UI 버튼 노출 여부와 무관하게 API 직접 호출로도 우회되지 않는다
- [ ] **CONT-09**: `confirmed` 이후 섹션 2(계약정보)가 잠기고 섹션 1·3은 계속 수정 가능하며, 이 잠금이 서버에서도 강제된다
- [ ] **CONT-10**: 계약 총액이 항목에서 서버가 재계산해 저장하며, 항목 수정 후 총액이 어긋나지 않는다
- [ ] **CONT-11**: 계약 상태 전이가 누가·언제·무엇을 바꿨는지 이력으로 남는다 (`s030_contract_status_history`)
- [ ] **CONT-12**: 계약 유형(이용계약 / 전대차계약)이 명시적 필드로 선택·검증된다
- [ ] **CONT-13**: 운영사는 계약서를 2종(이용계약서 4섹션 / 전대차계약서 10조)으로 미리보고 인쇄할 수 있다
- [ ] **CONT-14**: 계약서의 담당자명·센터명이 하드코딩되어 있지 않고 `lib/constants.ts` 기본값에서 온다 (2차 설정 화면에서 DB 조회로 교체 가능한 구조)
- [ ] **CONT-15**: 계약서 인쇄 시 `@media print` 규칙이 적용되어 화면과 다른 인쇄 레이아웃이 나온다
- [ ] **CONT-16**: 운영사는 계약 목록에서 만료 임박 계약을 필터·정렬할 수 있다
- [ ] **CONT-17**: 계약에 파일을 첨부하고 조회·삭제할 수 있다
- [ ] **CONT-18**: 입주사 담당자는 자사 계약 정보를 조회할 수 있다 (수정 불가)
- [ ] **CONT-19**: 금액·사업자등록번호·연락처 입력이 마스킹되며 입력 중 커서가 튀지 않는다

### Contract Schema — 청구 대비 (3차 UI, 1차 컬럼)

> 3차 청구·세금계산서 발행 때 소급 입력이 불가능한 값들. 1차에서 컬럼과 계약 폼 입력란까지 만들되, 청구 로직·화면은 만들지 않는다.

- [ ] **CSCH-01**: 계약에 `billing_start_date`가 `contract_start_date`와 별도로 저장된다 (무상기간 표현)
- [ ] **CSCH-02**: 계약에 보증금 금액과 반환 상태(보유/반환/차감/일부차감)가 저장된다
- [ ] **CSCH-03**: 계약 시점의 사업자등록정보가 계약 레코드에 스냅샷으로 저장된다 (입주사 레코드 참조가 아님 — 세금계산서는 거래 시점 정보에 법적으로 묶임)
- [ ] **CSCH-04**: 계약에 `renewed_from_contract_id` 자기참조 FK가 있어 재계약 이력이 추적된다
- [ ] **CSCH-05**: `s030_billing` / `s030_billing_item` 스키마가 append-only 스냅샷 원장 형태로 정의되어 있고, 외부 세금계산서 발행 참조번호 필드를 포함한다 (테이블만 생성, 로직·화면 없음)

### Booking (회의실 예약)

- [ ] **BOOK-01**: 운영사는 회의실 예약 현황을 월간·주간으로 조회할 수 있다
- [ ] **BOOK-02**: 입주사는 주간 현황만 조회하며 월/주 토글 자체가 렌더링되지 않는다
- [ ] **BOOK-03**: 사용자는 회의실을 예약할 수 있다
- [ ] **BOOK-04**: 사용자는 자신의 예약을 수정·취소할 수 있다
- [ ] **BOOK-05**: 같은 회의실의 시간대 중복 예약이 DB 제약으로 차단된다 (앱 레벨 검사만이 아니라 동시 요청에서도 안전)
- [ ] **BOOK-06**: 취소된 예약은 해당 시간대를 막지 않는다
- [ ] **BOOK-07**: 예약 시각이 `timestamptz`로 저장되고 표시 시점에만 `Asia/Seoul`로 변환된다 (서버 기본 타임존에 의존하지 않음)
- [ ] **BOOK-08**: 입주사별 1일 무료 시간 한도가 예약 시 검증된다 (초과요금 부과는 하지 않음 — 청구가 3차)
- [ ] **BOOK-09**: 최대 연속 슬롯 수와 예약 가능 기간(N일 이내) 제한이 적용된다
- [ ] **BOOK-10**: 예약 상태가 `confirmed` / `requested` / `rejected` / `cancelled`로 관리된다
- [ ] **BOOK-11**: 예약 현황 화면이 3단 반응형으로 동작한다 — 1280+ 주간 / 768~1279 축약 / ~767 일간

### Kiosk (회의실 현황판)

- [ ] **KIOS-01**: 인증 없이 접근 가능한 회의실 현황판이 오늘의 예약 현황을 표시한다
- [ ] **KIOS-02**: 현황판은 표시 전용이며 예약 기능이 없고, QR로 예약 화면을 안내한다
- [ ] **KIOS-03**: 현황판이 `100dvh`에 고정되어 스크롤이 발생하지 않는다
- [ ] **KIOS-04**: 현황판이 주기적으로 갱신되어 새 예약이 반영된다

### Dashboard & Occupancy (대시보드 · 호실현황)

- [ ] **DASH-01**: 운영사는 로그인 후 대시보드에서 운영 요약 지표를 본다
- [ ] **DASH-02**: 대시보드에 호실 점유·공실 현황이 위젯으로 표시된다
- [ ] **DASH-03**: 대시보드에 만료 임박 계약이 표시되고 계약 목록으로 이동할 수 있다
- [ ] **DASH-04**: 대시보드는 운영사 전용이며 입주사에게는 사이드바에도 나타나지 않는다
- [ ] **DASH-05**: 대시보드 집계 쿼리가 테넌트 스코프 헬퍼를 거쳐 전사 집계가 입주사에게 새지 않는다

## v2 Requirements

2차 이후로 미룬 항목. 추적하되 현재 로드맵에는 없다.

### Settings (설정 · 2차)

- **SET-01**: 운영사는 지점을 추가·수정할 수 있다
- **SET-02**: 운영사는 지점별·조직 기본 계약서 담당자를 설정할 수 있다 (CONT-14의 상수를 DB 조회로 교체)
- **SET-03**: 운영사는 IP 화이트리스트를 관리할 수 있다
- **SET-04**: 운영사는 전사 예약 기본값(운영시간·슬롯·무료시간·예약가능기간)을 설정할 수 있다
- **SET-05**: 입주사는 계정 설정 카테고리만 접근할 수 있다

### Members & Applications (멤버 · 신청 · 2차)

- **MEMB-01**: 운영사는 입주사 멤버를 관리할 수 있다
- **APPL-01**: 운영사는 신청 대기 목록을 조회하고 입주사로 전환할 수 있다
- **APPR-01**: 운영사는 외부 예약 승인 큐에서 승인·반려할 수 있다

### Booking 확장 (2차+)

- **BKX-01**: 사용자는 반복 예약을 등록할 수 있다
- **BKX-02**: 예약 체크인·노쇼 처리
- **BKX-03**: 예약 앞뒤 버퍼 시간
- **BKX-04**: 취소 기한 제한

### Billing (청구 · 3차)

- **BILL-01**: 운영사는 월별 청구를 생성할 수 있다
- **BILL-02**: 운영사는 납부 현황을 조회하고 상태를 변경할 수 있다
- **BILL-03**: 청구에 일할 계산(proration)과 일회성 항목이 반영된다
- **BILL-04**: 회의실 초과 사용 요금이 청구에 집계된다
- **BILL-05**: 세금계산서가 외부 발행 서비스를 통해 발행되고 참조번호가 청구에 기록된다

## Out of Scope

명시적 제외. 나중에 "왜 안 넣었나"를 막기 위해 사유를 남긴다.
