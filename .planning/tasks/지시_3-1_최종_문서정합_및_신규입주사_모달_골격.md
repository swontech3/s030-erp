## 1. 배경

페이즈 3은 입주사 관리다. 확정된 설계는 이렇다.

- ERP에 **회사 등록 화면·직원 등록 화면을 따로 두지 않는다**
- **운영사**가 신규 계약을 등록하는 흐름 안에서 회사와 대표를 함께 만든다
- 그 자리는 **계약 등록 모달 `s0300200030p2` 의 신규 입주사 모드**다
- ERP 화면에 비밀번호 입력란은 없다

삐용 회신으로 확정된 것 (`doc/BBIYONG_REPLY_4~6.md`).

- 회사·대표·구독·역할이 **한 번의 호출**로 만들어진다. 부분 실패가 없다
- 대표의 `member_tp='C'` 는 **삐용이 정한다.** ERP가 보내지 않는다
- 단체코드(`orgCode`)는 **ERP가 `Z01` 부터 순번으로 자동 생성해 보낸다.**
  운영자는 관여하지 않고, **화면에도 두지 않는다**
- 구독은 `moduleCodes` 배열로 함께 보낸다. 형식은 확정됐다.
  다만 **ERP 모듈 5개는 아직 켤 수 없다** — 지금 보내면 회사가 거부된다
- **팝업도 삐용 화면 마스터에 등록한다.** 권한 부여 단위만 부모다

이 작업은 **삐용 API를 하나도 부르지 않는 부분**만 한다.

### A-2. `.planning/ROADMAP.md` 페이즈 3 절에 확정 사항 반영

1. **회사·대표를 등록하는 주체는 운영사다.** 입주사가 스스로 자기 회사를 만드는 경로는

2. **진입점은 `s0300200030p2` 의 신규 입주사 모드**다. 새 화면을 만들지 않는다.
   이 모달은 페이즈 3과 4가 나눠 채운다 — **페이즈 3은 회사·대표 입력,

4. **단체코드는 `Z01` 부터 순번으로 ERP가 자동 생성한다.** 화면에 두지 않는다.

### A-3. `doc/SWONBIZ_SCREEN_LIST.md` 갱신

**① 팝업 규칙을 고쳐 쓴다** (삐용 회신으로 방침이 바뀌었다)

지금 문서에는 "팝업에 독자적인 구분을 주지 않는다"고만 되어 있다. 등록 여부가 빠져
있어 아래로 대체한다.

> 팝업도 삐용 화면 마스터에 **등록한다.** 다만 권한을 주는 단위는 부모 화면이고,
> 팝업에 독자적인 권한을 주지 않는다. 등록하지 않으면 그 화면코드가 권한 체크 대상
> 자체가 아니어서, 부모가 잠겨 있어도 팝업 경로가 열린다. 등록은 권한을 갖기 위한
> 것이 아니라 **체크 대상이 되기 위한 것**이다.

**② `s0300600010` 대상 구분을 확정한다**

지금 §5에 "판단 애매 · 사실상 공통으로 동작 중"으로 남아 있다. **공통으로 확정**한다.

- 입주사 대표의 로그인 후 첫 화면이 이 화면이다. 운영사 전용이면 입주사는 로그인하자마자
  접근 권한 없음으로 간다
- 060 절의 "월간 뷰는 운영사 전용" 각주는 **화면을 나누지 않고 같은 화면 안에서
  월/주 토글을 운영사에게만 렌더링**하는 것으로 정리한다
- **§5의 일반 규칙("입주사도 보게 해달라는 요구가 오면 새 ID를 판다")은 그대로 둔다.**

  자리**를 위한 것이고, 여기는 타사 예약이 전부 마스킹되어 새는 것이 없다

**③ 나머지 갱신**

### B-4. ★ 단체코드 — 화면에 두지 않는다

`orgCode` 는 삐용 필수 필드이고 ERP가 정해서 보내는 값이지만, **운영자가 입력하는
값이 아니다.** 신규 입주사를 받는 자리에서 뜻 없는 3자리를 사람이 정할 근거가 없다.

**이 작업에서 할 일**

- **등록 화면에 입력란도 안내 문구도 넣지 않는다.** 원본 디자인에 없는 요소를
  추가하지 않는다는 이관 원칙과도 맞는다
- 입력 항목 정의에만 `orgCode` 를 **"삐용에 보내는 값 · ERP 자동 생성 · 화면 없음"**
  으로 기록한다. 정의 파일을 보는 사람이 "왜 화면에 없지"를 묻지 않게 한다

**이 작업에서 하지 않을 일**

- **생성 규칙을 짜지 않는다.** `Z01` 부터의 순번 발급과 중복 시 재시도는 새 로직이고,
  3-2에서 테스트와 함께 만든다. 여기서 미리 짜면 3-2에서 다시 고친다
- 표시도 하지 않는다. 등록된 뒤 입주사 상세에 읽기 전용으로 붙이는 것은 3-4다

```
org_tp         서버가 정한다 (신규 입주사도 'N')
member_tp      서버가 정한다 (대표는 항상 'C')
mailAgentYn    폐기됨. 메일 구독은 moduleCodes 로 정한다
```

### B-6. 구독 설정 — 자리를 둔다

삐용이 요청 형식(`moduleCodes` 배열)을 확정했으므로 자리를 둔다. 나중에 되돌릴 구조가
아니다.

- 「구독 설정」 섹션을 두되, **지금은 고를 수 있는 항목이 없어 비어 있거나 비활성**
- ERP 모듈 5개(`OFFICE` · `BOOKING` · `LEGAL` · `TAX` · `BILLING`)는 삐용에서 아직
  꺼져 있다. **지금 보내면 회사가 아예 만들어지지 않는다**
- `CORE` 는 보내지 않아도 자동으로 붙는다. 화면에 넣지 않는다
- 섹션에 안내 한 줄: **"선택 가능한 서비스가 준비되면 여기에 표시됩니다"**

### B-7. 계약 정보 섹션

자리만 잡고 비워 둔다. 호실 선택·계약 항목·금액은 전부 페이즈 4다.

### B-8. 저장 버튼

**아무것도 호출하지 않는다.** 비활성이거나 콘솔 출력까지만. 삐용 호출도 ERP DB 쓰기도
이 작업에는 일절 없다.

### B-9. 등록 완료 안내 문구 (자리만)

대표 계정은 만들어져도 **메일 발송 기능(삐용 2단계)이 열리기 전까지 로그인할 수 없다.**
완료 화면 문구는 **"계정 개통은 별도 안내 예정"** 으로 잡는다.
"메일을 확인하세요" 라고 쓰면 안 온다.

### 검증 — ★ PowerShell에서 실행할 것

**이 PC의 Git Bash에서 `npm run` 은 실패해도 종료코드 0을 낸다**(npm 9.6.6 / node 24).
bash에서 본 성공을 믿지 말 것.

```powershell
npm run tokens:check      # 토큰 119개 원본 대조
npm run icons:check       # 아이콘 11종
npm run lint:green        # 녹색 금지
npm run design:links      # 디자인 자원 참조
npm run ds:compare        # DS 컴포넌트 마크업 대조
npm run typecheck         # 3패키지
```

**검사 건수가 0인데 통과한 것은 통과가 아니다.** 페이즈 1에서 녹색 lint가 검사 대상 0개로
초록을 냈던 전례가 있다. **몇 건을 검사해서 통과했는지 숫자를 보고한다.**

개발 서버는 PowerShell 창 2개로 띄운다.

```powershell
npm run dev --workspace @swonbiz/web   # localhost:3000
npm run dev --workspace @swonbiz/api   # localhost:3001
```

`packages/api/.env` 의 `BBIYONG_MOCK=true` 상태에서 작업한다. `.env` 를 고쳤으면 API를
재기동해야 반영된다.
