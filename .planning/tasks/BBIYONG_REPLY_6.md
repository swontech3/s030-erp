## 0. 한 줄 요약

단체코드를 ERP가 정해 보내는 쪽으로 확정했습니다.
**ERP 입주사는 `Z` 로 시작하는 코드만 쓰겠습니다. 그 대역을 비워 주십시오.**

요청은 이것 하나입니다. 나머지는 확정 사항 공유입니다.

---

## 1. ★ 요청 — 첫 자리 `Z` 를 ERP 몫으로 남겨 주십시오

### 무엇을

```
ERP 입주사   Z01 · Z02 · Z03 …  →  ZZZ
삐용         첫 자리 Z 를 쓰지 않는다
```

**지금 `Z` 로 시작하는 단체가 하나도 없는 것을 확인했습니다.** 비어 있는 지금이
대역을 나누기 가장 좋은 시점입니다.

### 왜 나누는가

ERP와 삐용이 같은 3자리 공간을 나눠 쓰면, ERP가 자동 생성한 코드가 삐용 기존 단체와
겹칩니다. 겹치면 다음 번호로 재시도하면 되지만 입주사가 쌓일수록 재시도가 늘어납니다.

그리고 **부서코드가 단체코드를 접두사로 물려받는 구조**라, 코드가 겹치면 부서코드까지
같이 꼬입니다. 앞선 회신에서 알려주신 그 지점입니다.

대역을 나누면 이 문제가 처음부터 생기지 않습니다.

### `Z` 를 고른 이유

알파벳 끝이라 기존 코드가 쓰고 있을 가능성이 가장 낮고, 실제로 지금 0건입니다.
삐용 운영 화면에서 `Z` 로 시작하는 코드를 보면 **ERP 경로로 들어온 회사**라는 것이
바로 보이는 이점도 있습니다. 부서코드도 `Z0101` 처럼 나와 구분됩니다.

`Z**` 는 1,296개입니다. ERP 입주사가 수백 규모라 넉넉합니다.

### ★ 가능하시면 — 서버에서 막아 주십시오

삐용 단체 등록에서 **첫 자리가 `Z` 면 거부**하도록 검증을 걸어 주시면 좋겠습니다.

사람이 기억해서 피하는 방식은 언젠가 뚫립니다. 그리고 한 번 뚫리면 부서코드까지 같이
꼬여서 되돌리기 어렵습니다. 검증을 걸면 약속이 구조가 됩니다.

**다만 지금 권한관리 재구축 중이신 것을 알고 있습니다.** 여력이 안 되시면 운영 약속으로
두고 나중에 걸어 주셔도 됩니다. 급한 요청은 아닙니다.

## 2. ERP 쪽 확정 사항 (공유)

### 생성 방식

```
Z01 부터 순번으로 발급
ERP 가 저장할 때 자동으로 만든다 — 운영자는 관여하지 않는다
중복 응답이 오면 다음 번호로 재시도한다
```

**운영자가 코드를 정하지 않습니다.** 신규 입주사를 받는 자리에서 "이 회사의 3자리
코드를 정하세요"라고 물으면 답할 근거가 없습니다. 회사명과도 무관하고 입주사에게
알려줄 값도 아닙니다.

### 화면에는 두지 않습니다

- 등록 화면에 입력란도 안내 문구도 넣지 않습니다
- 등록이 끝난 뒤 **입주사 상세 화면에 읽기 전용으로 표시**합니다.
  삐용 운영 화면과 대조할 때 이 값이 유일한 연결고리이므로 어딘가에는 보여야 합니다

### 중복 응답 처리

앞서 권해주신 대로입니다.

```
응답의 orgName 이 우리가 보낸 회사명과 같다   →  재시도 상황. data.orgId 를 쓴다
다르다                                        →  코드만 겹쳤다. 다음 번호로 다시 보낸다
```

중복 확인 API 는 미리 부르지 않습니다.

### 종료된 단체의 코드

재사용하지 않습니다. `Z` 대역에서도 마찬가지로 한 번 쓴 번호는 건너뜁니다.

## 3. 회신 바랍니다

```
★ 첫 자리 Z 를 ERP 몫으로 비워 주실 수 있는지
  (가능하시면 서버 검증까지 — 급하지 않습니다)
```

**이 답이 없어도 ERP는 개발을 진행할 수 있습니다.** 중복 시 다음 번호로 재시도하는
로직은 어차피 필요하고, 대역이 나뉘면 그 로직이 거의 돌지 않게 될 뿐입니다.

다만 **대역을 나눌 거라면 지금이 가장 싼 시점**입니다. `Z` 로 시작하는 단체가 하나라도
생긴 뒤에는 정리 비용이 생깁니다.
