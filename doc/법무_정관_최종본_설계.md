작성 2026-11-08 · 결정 2026-11-07 을 받아 쓴 **설계 보고**다. 코드 · DB 는 고치지 않았다.
근거로 읽은 것(모두 읽기만):

- **개발 DB:** 공통 코드 `LAW_CNG_TP` · `LAW_CNG_MT`, 법령 원문 048(`tb_s080_law_article`, 상법 시행일 2026-09-10판), 표양식 「정관」 · 「정관(유한회사)」의 정의
- **소스:** `corp-change.ts` · `incorporation-print.ts` · `form-template.ts` · `legal-form-mark.ts` · `legal-articles-file.ts`

## 0. 결정(2026-11-07) — 이 설계가 지키는 것

- **정관을 다루는 범위:** 정관이 바뀌는 변경 구분일 때만 다룬다. 안 바뀌는 구분은 정관을 올리지도 관리하지도 않는다.
- **최종본:** 회사(단체 `org_id`)마다 최종본 하나만 둔다. DB 에 조항 단위로 저장하고, 출력은 늘 최종본에서 한다.
- **정관이 바뀌는 변경등기:**
  - 최종본에서 해당 조항만 바꾼 「변경된 정관」을 [서류 출력]에 넣는다.
  - 건이 완료되면 그것이 새 최종본이 된다.
- **최종본이 처음 필요할 때:**
  - 우리가 설립한 회사는 설립 건 자료(정관 양식 + 설립 값)로 만든다. 시점은 §5-1 에 적었다.
  - 다른 곳에서 설립한 회사는 정관이 바뀌는 변경등기를 처음 할 때 docx · txt 를 올린다. 이것을 조항으로 나누고, 사람이 확인하고 고친 뒤 확정한다.
  - HWP 는 docx 로 저장해 올리라고 안내한다.
- **정관 파일 첨부:** 지금의 「정관 파일」 첨부(55b3cf1)는 원본 보관용으로 그대로 둔다.

|---|---|---|---|---|

| `CEO_ADDR` 대표이사 주소변경 | 바뀌지 않는다 | — | — | 제317조② 9호 / 제549조② 4호 |
| `CEO_CHG` 대표이사변경(코드만 있고 구현 없음) | 바뀌지 않는다 | — | — | 제389조 / 제562조 |

**본점 「시·도가 다를 때만」인 이유**

- 법이 본점의 「소재지」라고만 하므로, 정관에 적은 단위를 따른다.
- 우리 양식은 「본 회사의 본점은 {{hqSido}}에 둔다」로 시·도 단위다. 시·도가 같으면 문구가 그대로라서 정관 변경이 아니다.
- 지금 [서류 출력] 안내(`articlesChangeNotice`, 2026-11-07)와 같은 기준이다.
- ★ 올린 정관이 구 · 시까지 적었다면(예 「서울특별시 강남구에 둔다」) 시·도가 같아도 바뀐다. 그래서 판단은 「새 조항 문구가 지금 조항 문구와 다른가」로 한다(§3-2).

**★ `OFFICER` 단서(유한회사)**

- 제547조①은 「정관으로 이사를 정하지 아니한 때에는…」이라고 한다. 유한회사는 정관에 이사를 적을 수 있다는 뜻이다.
- 우리 양식(제20조)은 이사를 적지 않는다.
- 다른 곳에서 설립한 유한회사의 정관이 이사를 적어 두었다면 임원변경도 정관 변경이다.
- 이번 설계는 이 경우를 다루지 않는다(확인 필요 ⑥).

### 1-3. 정관이 바뀌는 구분 목록 — 공통 코드로(소스에 박지 않음)

**안:** 새 분류 **`LAW_CNG_AR`** / 파티션 `000` 을 둔다. `LAW_CNG_MT`(2026-11-07)와 같은 모양이다.

| 칸 | 값 |

| 이름 | 구분 이름(`LAW_CNG_TP` 의 이름과 같게) |
| **설명** | 바꾸는 **조항 역할**을 쉼표로 적는다(§2-3) |

시작값:

| 코드 | 설명 |
|---|---|
| `NAME` | `TRADE_NAME` |
| `PURPOSE` | `PURPOSE` |
| `HQ` | `HQ,NOTICE` |
| `HQ_OUT` | `HQ,NOTICE` |

- `OFFICER` · `CEO_ADDR` · `CEO_CHG` 는 줄을 두지 않는다.
- **줄이 없거나 설명이 비면 정관이 바뀌지 않는 구분이다.** 정관을 올리지도, 「변경된 정관」을 만들지도 않는다.
- 고치는 곳은 코드 관리(s030100030)의 그 줄 「설명」이다. 「한 업무는 한 화면」 원칙대로이고, `LAW_CNG_MT` 와 같다.
- **역할 어휘(`TRADE_NAME` · `PURPOSE` · `HQ` · `NOTICE`)는 소스에 둔다.** 역할마다 문구를 바꾸는 방법이 코드이기 때문이다. 앱이 박아 둔 값이므로 `code-usage.ts` 의 `PINNED_CODES` 와 같은 취급이다. 모르는 역할이 설명에 있으면 무시하고 로그에 남긴다.
- **본점 「시·도가 다를 때만」은 코드표에 적지 않는다.** 「바꾼 문구가 지금과 같으면 바뀌지 않은 것」이라는 일반 규칙(§3-2)에서 나온다.
- 지금 소스에 박힌 `articlesChangeNotice`(NAME · PURPOSE · HQ · HQ_OUT)도 이 코드를 읽도록 바꾼다(단계 S1).
- 회사유형별 차이(유한회사 양식에는 공고 조항이 없음)는 「그 역할의 조항이 최종본에 없으면 건너뛴다」로 푼다. 유형별 줄은 두지 않는다.

## 2. 저장 구조 안

### 2-1. 표 두 개(마이그레이션 `051`)

**① `tb_s080_legal_articles` — 최종본 머리.** 단체마다 한 줄이다.

| 칸 | 뜻 |
|---|---|
| `org_id` integer PK | 단체 — 회사마다 하나(결정) |
| `company_type` text | 만들 때의 회사유형(R · A) — 읽기 참고용 |
| `origin` text | `INCORP`(우리 설립 건에서 만듦) · `UPLOAD`(docx · txt 를 나눔) |
| `origin_ref` text | 설립 건 id, 또는 올린 원본 파일 이름 |
| `state` text | `DRAFT`(나눴지만 아직 확인 전) · `FINAL`(확정 = 최종본) |
| `revision` integer | 확정 · 건 완료로 바뀔 때마다 +1. 동시 고침 막기와 출력 기록에 쓴다 |
| `confirmed_at` / `confirmed_by` | 최종본 확정(`DRAFT`→`FINAL`) |
| `updated_at` / `updated_by` · `last_change_id` | 마지막으로 바꾼 법인변경 건 |

**② `tb_s080_legal_article_items` — 조항.** 한 줄이 한 덩어리다.

| 칸 | 뜻 |
|---|---|
| `org_id` · `seq` (PK) | 순서 |
| `kind` text | `CHAPTER`(장 제목 줄) · `ARTICLE`(조) · `TEXT`(머리말 · 부칙 머리 · 말미 등 조가 아닌 글) |
| `article_no` text | 조 번호 글자 — 「1」 · 「2의2」. 조가 아니면 null. **번호는 회사마다 다르므로 찾는 데 쓰지 않는다** |
| `title` text | 조 제목 — 「상호」 · 「목적」. 장이면 장 제목 |
| `body` text | 본문. 항(①②) · 호(1. 2.)는 **본문 안에 줄로** 둔다(나누지 않는다 — 출력은 그대로 이어 쓰면 된다) |
| `role` text | 조항 역할(§2-3) — 찾는 열쇠. 한 최종본 안에서 역할마다 0 또는 1 개(부분 유일 인덱스) |
| `section` text | `MAIN`(본칙) · `SUPPLEMENT`(부칙) — 부칙은 조 번호가 다시 1 부터라 가른다 |

**RLS 와 권한**

- 정책은 037 · 040 · 042 와 같은 `erp_org_scope` 다. 운영사는 전부, 회사 세션은 자기 단체만 본다. FORCE 를 건다.
- erp_app 은 SELECT · INSERT · UPDATE · DELETE 를 갖는다. 조항 표는 통째로 바꿔 쓰기 때문이다.

**이력은 남기지 않는다** — 결정이 「최종본 하나만」이다. 다만 「변경된 정관」의 근거는 건에 남는다(§3-1). 다시 출력하는 문제는 확인 필요 ④에 적었다.

### 2-2. 왜 jsonb 한 칸이 아니라 표인가

- 역할(`role`) 유일 인덱스로 「상호 조항이 둘」 같은 잘못을 DB 가 막는다.
- 건 완료 때 그 역할의 줄 하나만 바꾸면 된다. 동시에 열린 건 둘(상호 · 목적)이 서로의 조항을 덮지 않는다.
- jsonb 한 칸으로도 된다. 차이는 위 두 가지 지킴이뿐이다. jsonb 쪽이 마이그레이션과 코드가 작다(확인 필요 ⑪).

### 2-3. 상호 · 목적 · 본점 조항을 어떻게 찾나 — 조 번호가 회사마다 다를 때

**번호로 찾지 않고 「조항 역할」을 단다.**

| 역할 | 뜻 | 자동으로 붙이는 단서(제목 우선) |
|---|---|---|
| `TRADE_NAME` | 상호 | 제목이 「상호」 |
| `PURPOSE` | 목적 | 제목이 「목적」 |
| `HQ` | 본점의 소재지 | 제목에 「본점」 또는 「소재지」 |
| `NOTICE` | 공고방법 | 제목이 「공고방법」 또는 「공고」(「소집통지 및 공고」처럼 다른 낱말이 붙은 제목은 후보에서 뺀다) |

- **역할은 만들 때 자동으로 추측하고, 확인 화면에서 사람이 고친 뒤 확정한다.**
  - 우리 양식에서 만들 때는 제목이 정해져 있어 늘 맞는다.
  - 올린 정관은 후보가 여럿이거나 없으면 비워 두고, 사람이 고른다.
- **확정 막기:** `LAW_CNG_AR` 에 적힌 역할 가운데 이 회사의 정관에 있어야 하는 것이 비면 확정을 막는다.
  - 상호 · 목적 · 본점은 늘 있어야 한다.
  - 공고는 주식회사만이다. 유한회사는 비어도 된다.
- 표지의 상호는 조항이 아니다. 출력 때 최종본의 `TRADE_NAME` 조항이 아니라 **회사 정보의 지금 상호**를 쓴다(§3-3).

## 3. 「변경된 정관」과 출력

### 3-1. 건에서 바뀐 조항 만들기

1. 정관이 바뀌는 구분의 건(§1-3)을 연다. 최종본이 없으면 먼저 최종본을 만들라는 안내와 바로가기가 나온다(§5).
2. 최종본이 있으면 건 상세에 **「변경된 조항」** 칸이 생긴다. 역할마다 글 칸이 하나씩이고, 값은 아래처럼 미리 채운다. 사람이 고칠 수 있다.

| 역할 | 미리 채우는 방법 |
|---|---|
| `TRADE_NAME` | 지금 조항 본문에서 **지금 상호**(회사 정보)를 **신규 상호**(건)로 바꾼다. 신규 영문상호가 있으면 영문 문장도 바꾼다. 지금 상호가 본문에 없으면 그대로 두고 「찾지 못함 — 직접 고치세요」를 띄운다 |
| `PURPOSE` | 본문의 첫 줄(「…목적으로 한다.」)과 끝의 부대사업 줄(있으면)은 두고, 그 사이를 건의 목적으로 번호를 다시 매겨 채운다(우리 양식 모양 = `articlesPurposeList`) |
| `HQ` · `NOTICE` | 본문의 **지금 본점 시·도 정식 이름**(`sidoOf` · `korea-sido.ts`)을 새 본점 시·도로 바꾼다. 못 찾으면 「찾지 못함」 |

3. 바뀐 조항 문구는 **건에 저장한다**(payload `articlesItems: [{role, body}]`). 작성완료(P→E) 스냅샷에도 들어간다.
   - 최종본 본문은 건에 복사하지 않는다. 바뀐 조항만 둔다.

### 3-2. 「정관이 실제로 바뀌는가」

- 바뀐 조항의 문구가 **모두 지금 최종본과 같으면** 이 건은 정관 변경이 아니다. 예: 시·도가 같은 본점이전.
  - 이때는 「변경된 정관」을 [서류 출력]에 넣지 않는다.
  - 「정관 변경이 아닙니다(본점 조항 그대로)」 한 줄을 보인다.
- 지금 `articlesChangeNotice` 의 시·도 비교를 이 일반 규칙이 대신한다.

### 3-3. [서류 출력]에 넣기 — 지금 표양식으로 되나

**결론: 지금 표양식만으로는 안 된다. 조항 목록을 이어서 그리는 출력이 따로 필요하다.**

지금 표양식이 안 되는 이유(소스와 개발 DB 의 양식으로 확인):

- 표양식은 **장 · 행이 고정**된 A4 표다(`Page.rowHeights`).
- 넘치는 부분은 잘린다(`overflow: hidden`). 장 나누기도 출력 때가 아니라 일회용으로 미리 해 두었다(§6-2 20번 — 정관 7장 → 10장).
- 「내용에 맞춤」(`fitHeight`)은 행을 **줄이기만** 한다. 늘리거나 다음 장으로 넘기지 않는다.
- 우리 정관 양식은 53조(주식회사) · 36조(유한회사)의 문구가 **양식 칸에 박혀** 있다. 조항 하나하나가 자리표시가 아니다.
- 올린 정관은 조 수 · 길이가 회사마다 다르므로 고정 칸에 넣을 수 없다.

방법은 셋이다.

| | 방법 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **가** | **조항 목록을 이어 그리는 출력**을 하나 둔다. 표지(定款 + 상호) → 장 제목 → 「제n조 (제목)」 + 본문을 A4 로 이어 쓰고, 조 중간에서는 장을 넘기지 않으려 한다(`break-inside: avoid`). 글꼴 · 크기 · 여백은 지금 정관 양식과 같은 값으로 고정한다 | 길이 · 조 수에 상관없다. 올린 정관 · 우리 양식 둘 다 같은 길이다. 표양식 렌더러를 건드리지 않는다 | 서류 모양이 표양식 관리 밖(코드)에 있다. 「서류 양식 편집은 표양식 관리」 원칙의 **예외**가 된다 |
| 나 | 표양식에 **「흐름 칸」**을 더한다. 한 칸의 자리표시(`{{articlesItems}}`)가 칸을 넘으면 다음 장으로 이어진다 | 모양을 표양식 관리에서 고친다(원칙 그대로) | 장 고정 모델을 깨는 큰 변경이다. 모든 법무 서식의 렌더러 · 인쇄 규칙 · 편집기에 영향이 있다. 시간이 가의 2~3배다 |
| 다 | 지금 정관 양식에 자리표시만 더한다 | 작다 | 우리 설립 회사만 된다. 올린 정관은 안 된다 → 결정(「출력은 늘 최종본」)과 맞지 않는다 |

**제안은 가다(확인 필요 ① → 결정됨, §8-1).** 표양식 관리의 「정관」 양식은 설립 출력에 그대로 쓴다. 「변경된 정관」만 가로 그린다.

[서류 출력] 목록에서의 모습:

- 정관이 바뀌는 건이면 목록 **맨 끝에 「변경된 정관」** 이 한 줄 더 붙는다.
- 이 줄은 표양식 양식이 아니다. 법무 표시가 붙은 양식 목록과 따로 더한다.
- 미리보기 · [인쇄] · 출력 이력(040)은 다른 서류와 같다.
  - 이력의 `form_id` 는 고정 값 `ARTICLES_AMENDED` 로, `form_name` 은 「변경된 정관」으로 남긴다.
- 지금 위쪽 안내 「정관 변경 건입니다 — 변경된 정관은 따로 준비하세요」는 이 서류가 생기면 지운다.

출력 내용:

- 본문은 최종본의 조항 순서대로 그린다. 바뀐 역할의 조항만 건의 문구로 바꿔 넣는다.
- 표지 상호:
  - 상호변경 건은 신규 상호를, 그 밖은 회사 정보의 지금 상호를 쓴다.
  - 회사 형태 낱말을 붙이는 규칙(`f20a58e`)은 법인변경 출력과 같다.
- 말미(발기인 · 사원 성명 · 주민등록번호 · 주소)는 확인 필요 ②에 적었다.

### 3-4. 건 완료(E→C) 때 새 최종본

- 완료 트랜잭션 안에서 건의 `articlesItems` 를 최종본의 같은 역할 조항 `body` 에 넣는다.
- 그러면서 `revision` +1, `last_change_id` = 이 건으로 둔다.
- **완료를 막는 경우:** 최종본이 `FINAL` 이 아니거나, 그 역할 조항이 사라졌으면(최종본을 그 사이 다시 확정했으면) 막는다. 「정관 최종본이 바뀌었습니다 — 변경된 조항을 다시 확인하세요」를 띄운다.
- 건이 작성완료될 때의 `revision` 을 스냅샷에 넣어 두고, 완료 때 비교한다.
- 같은 역할을 바꾸는 열린 건이 둘이면 확인 필요 ⑤를 따른다.

## 4. docx · txt → 조항 나누기와 확인 화면(최소)

### 4-1. 읽기

**docx**

- docx 는 zip 이다. 새 라이브러리 없이 Node `zlib.inflateRaw` 로 `word/document.xml` 하나만 푼다.
  - 지금 저장소에는 zip 라이브러리가 없다(package.json 확인).
- 문단(`<w:p>`)마다 `<w:t>` 글자를 이어 한 줄로 만든다. 표 안의 문단도 차례대로 한 줄씩 읽는다.
- 그림 · 머리글 · 바닥글 · 각주는 버린다.

**txt**

- 줄 단위로 읽는다.
- 글자 인코딩은 UTF-8 로 읽어 깨지면 CP949(EUC-KR)로 다시 읽는다. Node `TextDecoder('euc-kr')` 를 쓴다.
- 한글 Windows 메모장 파일이 CP949 일 수 있기 때문이다.

**HWP 는 받지 않는다.** 「HWP 는 한글에서 [다른 이름으로 저장] → Word 문서(.docx)로 저장해 올리세요」를 안내한다.

**크기 한도는 1MB · 글자만 받는다.** ~~원본 파일은 나누고 나면 버린다~~ → 결정: 올린 원본은 「정관 파일」로 보관한다(§8-9).

### 4-2. 나누기 규칙(줄마다 위에서부터)

| 줄 모양(앞뒤 공백 · 전각 공백 무시) | 결과 |
|---|---|
| `제 n 장 …` | `CHAPTER` |
| `부칙` · `부　칙` · `부칙 (2020. 1. 1.)` | `TEXT`(부칙 머리). 이 뒤의 조는 `section = SUPPLEMENT` |
| `제 n 조(의 m)` + 괄호 · 꺾쇠 · 낫표 안 제목(`(상호)` · `【상호】` · `[상호]`) + 같은 줄 뒷글 | 새 `ARTICLE`. 번호 = n(의 m), 제목 = 괄호 안. 같은 줄 뒷글은 본문 첫 줄이 된다 |
| 그 밖 | 바로 앞 덩어리의 본문에 한 줄로 붙인다. 첫 조 앞의 줄은 `TEXT`(표지 · 머리말) |

- 표지의 「정관」 · 「定款」 한 줄과 빈 줄은 버린다.
- 역할은 §2-3 단서로 추측한다.
- **검사 표시(확인 화면에 띄운다):**
  - 본칙 조 번호가 1 부터 차례가 아니다(빠짐 · 겹침).
  - 조가 하나도 없다.
  - 필수 역할이 비었다.
- **★ 나눌 수 없는 경우:** Word 자동 번호로 「제1조」를 매긴 문서는 번호가 글자로 없다(번호가 `numbering.xml` 의 서식이다).
  - 이때는 조가 0 개로 나온다.
  - 「조 번호가 글자로 없습니다 — Word 에서 자동 번호를 글자로 바꾸거나(번호 붙은 문단 복사 → 메모장에 붙여 txt 로) 올리세요」를 띄운다.
  - 자동 번호를 흉내 내 풀지는 않는다(확인 필요 ⑧).

### 4-3. 확인 화면(최소)

자리는 **건 상세의 대화상자 하나**다. 정관이 바뀌는 구분의 건에서만 연다. 새 화면(경로)은 두지 않는다.

- 나눈 덩어리를 위에서부터 한 줄씩 보인다.

| 칸 | 내용 |
|---|---|
| 종류 | 장 · 조 · 글 — 고를 수 있다 |
| 조 번호 · 제목 | 글 칸 |
| 본문 | 여러 줄 글 칸 |
| 역할 | 없음 · 상호 · 목적 · 본점 · 공고 — 한 역할은 한 줄에만 |

- 줄마다 [위 줄과 합치기] · [아래에 줄 넣기] · [지우기]가 있다.
- 위쪽에는 검사 표시(§4-2)가 있고, 원문 미리보기는 없다.
- [초안 저장]은 `DRAFT` 로 저장한다.
- [확정]은 검사를 통과하면 `FINAL` 로 저장하고 `revision` = 1 이 된다. 「확정하면 이 회사의 정관 최종본이 됩니다」를 한 번 확인한다.
- **이미 `FINAL` 인 최종본을 다시 고치는 것도 이 대화상자다.** 다시 확정하면 `revision` +1. 열린 건과 부딪히는 경우는 §3-4 에 적었다.
- 권한 안(확인 필요 ⑨): 「정관 파일」과 같다.
  - 운영사, 또는 회사 정보를 고칠 수 있는 사람(`canEditCompany`)이 고칠 수 있다. 입주사는 운영사만이다.
  - 보기는 운영사 · 그 회사 사람이다.

## 5. 최종본이 처음 필요할 때

### 5-1. 우리가 설립한 회사 — **첫 정관 변경 때 만드는 쪽이 더 단순하다(제안)**

| | 설립 완료(E→C) 때 | 첫 정관 변경 때(제안) |
|---|---|---|
| 손대는 곳 | 이미 운영 중인 설립 완료 전이(`c238d7e`, 회사유형 설정)에 일을 더한다. 거기서 실패하면 완료가 막힌다 | 새 코드만 늘어난다. 설립 완료 전이는 그대로다 |
| 길 | 「설립 완료 때 만들기」와 「올려서 만들기」의 **길이 둘**이다 | 「최종본이 없으면 → (설립 건이 있으면 그것으로, 없으면 올려서) 초안 → 확인 → 확정」으로 **길이 하나**다. 확인 화면도 하나다 |
| 이미 완료된 설립 건 | 개발 DB 1344 같은 지난 건은 따로 일회용으로 만들어야 한다 | 따로 할 일이 없다. 필요할 때 만든다 |
| 만들 일 | 정관을 바꾸지 않는 회사도 만든다 | 정관이 바뀌는 건을 낸 회사만 만든다 |
| 약점 | — | 설립 뒤 표양식 「정관」을 고쳤다면 **낸 정관과 다른 글**이 나올 수 있다 → 만든 것을 **초안으로** 두고 확인 화면을 거쳐 확정한다(올린 정관과 같은 길) |

**만드는 방법**

1. 그 단체의 완료된 설립 건(`completedIncorporationIdOf`, 55b3cf1)의 작성완료 스냅샷과 등기 설정으로 정관 출력값을 만든다. 출력값 함수(`incorporation-print.ts`)를 그대로 쓴다.
2. 회사 형태에 맞는 정관 양식(`incorpArticlesFormName` → 「정관」 · 「정관(유한회사)」)의 칸 글자에 출력값을 넣는다.
3. 칸을 위 → 아래, 장 → 장 순서로 읽어 §4-2 와 같은 규칙으로 나눈다. 장 제목 행 · 「제n조 (제목)」 행 · 본문 행이 따로 있는 모양이라 그대로 나뉜다.
4. 표지(1장)와 말미(발기인 · 사원 서명란 행)는 넣지 않는다(확인 필요 ②).

**★ 주민번호:** 설립 스냅샷에는 주민번호가 없다(042). 정관 말미 목록은 출력 때만 복호화한다. 최종본 조항 표에는 **주민번호를 넣지 않는다.**

### 5-2. 다른 곳에서 설립한 회사

- 정관이 바뀌는 건에서 최종본이 없으면 「정관 최종본이 없습니다 — docx · txt 로 올려 주세요(HWP 는 docx 로 저장)」를 띄우고 [올리기]를 보인다.
- 올리면 §4 를 따른다.

| ⑦ | 본점이 구 · 시까지 적힌 정관 | **결정됨** — 확인 화면에서 사람이 고친다. §8-7 |
| ⑧ | Word 자동 번호 문서 | **결정됨** — 안내만. §8-8 |
| ⑨ | 권한 · 올린 원본 | **결정됨** — 권한은 「정관 파일」과 같다 · 원본은 「정관 파일」로 보관. §8-9 |
| ⑩ | 코드 이름 | **결정됨** — 제안대로. §8-10 |
| ⑪ | 저장 모양 | **결정됨** — 표 두 개(머리 · 조항). §8-11 |

## 8. 결정(2026-11-08)

§1~§6 과 이 장이 다르면 **이 장을 따른다.** 본문에서 바뀌는 곳은 항목마다 적었다.

### 8-1. 「변경된 정관」은 조항을 이어 그린다(①)

- §3-3 의 **가**로 한다. 최종본의 조항 목록을 A4 로 이어 그리는 출력이다.
- **표양식 원칙의 예외는 「변경된 정관」 하나뿐이다.** 다른 법무 서류와 설립 「정관」은 지금처럼 표양식 관리의 양식을 읽어 그린다.
- 구현할 때 CLAUDE.md 「한 업무는 한 화면에서」 표의 「서류 양식 편집」 줄에 이 예외를 한 줄 적는다.

### 8-2. 정관 끝 — 서명란 대신 개정일 · 상호 · 대표이사(②)

- 발기인 · 사원의 서명란(성명 · 주민등록번호 · 주소)은 넣지 않는다. 주민번호를 다루지 않는다.
- 끝에는 세 줄을 둔다.
  - 개정일
  - 상호 — 상호변경 건은 신규 상호, 그 밖은 지금 상호. 회사 형태 낱말 규칙은 §3-3 과 같다
  - 「대표이사 ○○○」 — 회사 정보의 대표자 성명
- ★ 개정일에 쓸 날짜는 결정에 없다. 문서의 안은 건의 **결의일**(§8-3 부칙 날짜와 같은 날)이다 — 구현 시작 때 확인한다.

### 8-3. 개정마다 부칙 한 줄 자동(③)

- 「변경된 정관」에 부칙 한 줄을 자동으로 붙인다: 「이 정관은 ○년 ○월 ○일부터 시행한다」.
- ★ 날짜 출처는 결정에 없다. 문서의 안은 건의 **결의일**(`resolutionDate`)이다 — 정관이 바뀌는 구분(상호 · 목적 · 본점이전)은 모두 결의일이 필수 칸이다. 구현 시작 때 확인한다.
- 건이 완료되면 이 줄이 최종본에도 남는다. 부칙 머리(`TEXT`) + 그 한 줄을 `section = SUPPLEMENT` 로 덧붙인다. 개정할 때마다 한 줄씩 늘어난다.
- §3-4(완료 때 반영)에 이 덧붙임을 더한다.

### 8-4. 완료 건 다시 출력은 최종본 기준 — 안내 한 줄(④)

- 완료된 건을 다시 출력하면 **지금 최종본** 기준으로 그린다. 그때의 정관을 따로 남기지 않는다(최종본 하나).
- 완료된 건의 [서류 출력]에 「변경된 정관」을 고르면 위쪽에 안내 한 줄을 보인다. 예: 「완료된 건입니다 — 변경된 정관은 지금 최종본 기준으로 나옵니다」. 종이에는 나가지 않는다.

### 8-5. 같은 조항을 바꾸는 열린 건 둘 — 둘째 건 작성완료를 막는다(⑤)

- 같은 단체에서 같은 역할의 조항을 바꾸는 건이 이미 작성완료(E) 상태로 열려 있으면, 다른 건의 작성완료(P→E)를 막는다. 「둘째 건」은 나중에 작성완료하려는 건으로 읽었다.
- 막는 문구에 먼저 열린 건을 알려 준다. 먼저 건이 완료(C) · 취소(X)되면 작성완료할 수 있다.
- §3-4 의 `revision` 비교(완료 때 최종본이 바뀌었으면 막기)는 그대로 둔다.

### 8-6. 유한회사 정관에 이사가 적힌 경우는 범위 밖(⑥)

- 임원변경(`OFFICER`)은 정관이 바뀌지 않는 구분으로 둔다. `LAW_CNG_AR` 에 줄을 두지 않는다.
- 이사 조항에 붙일 역할은 만들지 않는다.

### 8-7. 본점이 구 · 시까지 적힌 정관은 사람이 고친다(⑦)

- 자동 바꾸기는 시·도 이름만 한다(§3-1).
- 나머지는 사람이 고친다. 본점 조항을 지금 본점에 맞게 고치는 것은 최종본 **확인 화면**에서, 건의 새 본점 문구는 건의 「변경된 조항」 칸에서 고친다.

### 8-8. Word 자동 번호 문서는 안내만(⑧)

- §4-2 의 안내를 띄우고 나누지 않는다. `numbering.xml` 을 풀어 번호를 만들어 주지 않는다.

### 8-9. 권한은 「정관 파일」과 같다 · 올린 원본은 「정관 파일」로 보관(⑨)

- **권한:** 최종본 초안 저장 · 확정 · 고치기는 운영사, 또는 회사 정보를 고칠 수 있는 사람(`canEditCompany`)이다. 입주사는 운영사만이다. 보기는 운영사 · 그 회사 사람이다. 서버가 다시 판정한다.
- **원본:** 올린 docx · txt 는 버리지 않고 그 단체의 「정관 파일」(55b3cf1, `tb_cm_file` LEGAL_ORG · ARTICLES)로 보관한다. 회사마다 하나뿐이므로 이전 파일은 지금 「정관 파일」 바꾸기와 같이 지운다.
- **§4-1 이 바뀐다:**
  - 「원본 파일은 나누고 나면 버린다」 → 「정관 파일」로 보관한다.
  - 「정관 파일」의 받는 형식은 지금 JPG · PNG · PDF 다. docx · txt 를 넣으려면 그 칸의 받는 형식을 넓혀야 한다. 받는 형식 · 크기 한도(지금 10MB, §4-1 의 1MB 와 다르다)는 구현 S2 · S3 에서 맞춘다. 저장소 버킷의 허용 형식도 함께 본다.
  - 바꾸기 전 확인 문구(「바꾸면 이전 정관 파일은 지워집니다」)는 올릴 때도 뜬다.

### 8-10. 코드 이름은 제안대로(⑩)

- 분류 `LAW_CNG_AR` / 파티션 `000`. 역할 어휘 `TRADE_NAME` · `PURPOSE` · `HQ` · `NOTICE`.
- 코드값 줄의 **이름 칸은 사람이 읽는 이름**(`LAW_CNG_TP` 의 구분 이름과 같게), **규칙 값(역할)은 설명 칸**에 둔다. `LAW_CNG_MT`(2026-11-07)와 같은 모양이다(§1-3 그대로).

### 8-11. 저장은 표 두 개(⑪)

- §2-1 대로 머리(`tb_s080_legal_articles`) · 조항(`tb_s080_legal_article_items`) 두 표다. 역할 유일은 DB 가 지킨다.

### 8-12. 구현 시작

- 구현은 **가동 뒤 2단계 첫 작업**으로 시작한다.
- 그때 이 문서대로 S1 부터 S8 까지 **끊지 않고** 진행한다. §7 은 모두 결정됐으므로 S7 도 기다리지 않는다.
