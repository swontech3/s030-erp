## 1. 이 문서의 목적과 작업 원칙

세무 서비스(S05)는 새 방에서 개발하고, 이 문서는 법무 서비스(S04) 방에서 쌓은 공통 기반 · 로그인 인증 · 권한관리를 넘겨 준다. 세무 방은 이 기반을 새로 만들지 않고 그대로 쓴다.

역할 분담: 이 방(Claude)은 설계 · 판단 · Claude Code 작업지시문 작성, Claude Code 는 저장소에서 실제 개발 · 시험 · 커밋을 한다. 대표는 결정과 화면 확인을 한다.

### 대표가 정한 작업 원칙 (세무 방에서도 그대로)

1. 단순하게 — 지나치게 검토 · 확장하지 않는다. 요청한 일만 하고 범위 밖은 하지 않는다. 범위 밖 문제는 한 줄로 알리기만 한다.
2. 임의 판단 금지 — 시안이 있으면 시안대로, 다르게 할 이유가 생기면 혼자 정하지 말고 멈추고 묻는다.
3. 질문을 받으면 먼저 답하고, 지시를 받은 뒤에 작업한다. 조사 결과를 알리지 않고 혼자 진행하지 않는다.
4. 한 업무는 한 화면에서만 — 같은 업무를 여러 화면에 흩지 않는다(중복 개발 금지).
5. 코드성 항목(이름 · 선택지 · 목록)은 공통 코드 표에 두고 읽는다. 소스 상수로 박지 않는다(서버 재빌드 없이 반영).
6. 설명은 일상적인 말로 — 표 · 칸 이름 같은 내부 용어를 쓸 때는 무엇인지 함께 붙인다.
7. 쓰지 않는 코드 · 화면은 단호히 지운다.

### Claude Code 작업지시문 규칙

- 짧게: 설명은 덜고 지킬 것과 멈출 지점만 남긴다.
- 스킬(gstack · GSD · Superpowers)은 지시문 하나에 하나만 넣는다. 조사 · 작은 수정은 「스킬 없이」로 써 왔다.
- 끝에 늘 「★ 위 범위만 · 임의 판단 금지 · 서버는 건드리지 않는다」.
- 마이그레이션(DB 구조 변경)은 파일만 쓰고 적용 전에 영향 범위를 보고하고 멈춘다.
- 일회용 스크립트는 「보기」로 먼저 돌려 보고하고, 승인 뒤 --apply.
- 단계마다 보고하고 커밋한다.

## 3. 서비스 체계 · 화면 번호 · 회사 기준

세무는 서비스 코드 S05, 화면 번호는 s05 로 시작한다. 회사를 가르는 기준은 법무와 같이 삐용 단체 ID 다.

### 서비스 코드 (결정 2026-10-08)

| 코드 | 서비스 | 비고 |
|---|---|---|
| S02 | 삐용 | 공통 플랫폼 — 로그인 · 권한 · 회사(단체) 정본 |
| S03 | ERP | 공유오피스 입주 계약 · 청구 · 회의실 · 문의 |
| S04 | 법무 | 법인설립 · 법인변경 · 사업목적 · 설정(설정 090 은 미개발) |
| S05 | 세무 | 이번에 새로 개발 |
| S09 | 메일 Agent | 별도 서비스 |

화면 번호 규칙: s + 서비스 2자리 + 그룹 3자리 + 순번 4자리. 프로그램마다 10씩 띄우고, 딸린 화면(상세 등)은 1~ 사이에 끼운다. 팝업은 뒤에 p1.

- 법무 예: s040100010 법인설립 목록 · s040100020 법인설립 상세 · s040200010 법인변경 목록 · s040200011 법인변경 상세 · s040300010 사업목적(운영사 전용) · 팝업 s040300010p1
- 세무는 s05 + 그룹(010 · 020 …)으로 정한다. 그룹 구성은 세무 범위를 정할 때 함께 정한다.

### 회사 기준 — 회사의 정본은 삐용 단체 (결정 2026-10-09)

- 세무 건 · 법무 건의 주인은 삐용 단체 ID(정수, 예 9003) 다. 권한 · 데이터 격리 · 서류가 모두 이 값을 쓴다.
- 단체코드는 사람이 보는 이름표(3자 이내)다. 화면에는 단체코드, 없으면 「단체 {ID}」로 보인다. 법무는 단체코드를 읽어 보여 주기만 하고 만들거나 검증하지 않는다. 접두어로 회사 종류를 가르지 않는다.
- 입주사: ERP 가 입주 계약을 확정할 때 삐용에 단체를 등록하며 단체코드를 Z01, Z02 … 로 자동 발번한다. Z 코드는 ERP 전용 예약 코드다.
- 일반 고객사(비입주사): 운영사가 삐용 화면에서 직접 등록한다. 삐용은 Z 로 시작하는 코드를 막는다.
- ERP 회사 표(tb_s080_companies)는 입주사만 있다. 법무는 입주사가 아닌 회사의 회사 정보를 따로 둔다(tb_s080_legal_orgs — 등기상 상호 · 회사유형 등). 세무도 비입주사를 다루면 같은 방식이 필요할지 정해야 한다.
- ★ 미결(M4): ERP 회사를 이미 있는 삐용 단체에 잇는 기능이 없다. 그래서 삐용에 먼저 등록한 회사가 나중에 입주 계약을 확정하면 단체가 하나 더 생긴다. 법무는 이 때문에 입주 예정사 설립을 막아 두었다. 세무도 같은 경우가 생기면 이 문제를 먼저 풀어야 한다.

### 세무 서비스 방향 (결정 2026-10-05 · 10-06 · 10-10)

- 에스원테크 자사 세무(세금계산서 · 카드 매입)는 팝빌 같은 중개서비스로 직접 처리한다.
- 입주사 세무는 삐용에 붙여 연계 서비스로 제공한다. ERP 는 신청을 받아 넘기는 역할이다.
- 구상 범위: 계산서 발행 · 매입/매출 · 카드 사용내역으로 부가세 신고 자료 · 급여 산출과 원천세 신고 · 월별 손익표 정리 → 세무서에 서류를 넘긴다.
- 에스원테크는 핀테크 사업자 권한이 없으므로 고객사 업무에 직접 관여하지 않고 시스템만 제공한다.
- 세금계산서 발행(팝빌 연동)은 전체 개발 순서상 가장 마지막으로 정해져 있었다.

## 4. 로그인 인증 — 삐용을 통해서

세무 화면은 로그인을 새로 만들지 않는다. ERP 로그인이 이미 삐용을 거쳐 동작하고, 세무 화면은 그 세션을 그대로 받는다.

### 구조 (확정)

- ERP 는 랜딩 · 로그인 화면 UI 만 자체로 만들고, 이메일 · 비밀번호 확인과 토큰(JWT) 발급은 삐용 백엔드가 한다. ERP 자체 직원 표 · 토큰 발급은 없다.
- 삐용 DB 를 직접 조회 · 조인하거나 외래키를 걸지 않는다. 삐용과는 API 로만 주고받는다(어댑터로 감쌈).
- 2026-10-07 에 ERP ↔ 삐용 연동(로그인 · 회사 · 직원 · 퇴실 · 재입주 · 실패 복구)을 마쳤다.

### 로그인 흐름

1. 사용자가 ERP 로그인 화면에 이메일 · 비밀번호를 넣는다.
2. ERP 서버가 삐용에 확인을 맡기고, 삐용이 토큰을 준다.
3. 이메일 하나에 회사가 여럿이면 회사를 고른다. 로그인 뒤 회사를 바꾸면 토큰을 새로 받고 메뉴를 다시 그린다.
4. ERP 는 세션(쿠키의 세션 번호)을 만들고, 세션에는 회원 · 단체 ID · 단체코드 · 역할(운영사 operator / 회사 tenant) · 받은 화면 목록이 든다.
5. 화면마다 서버에서 「이 화면을 받았는가」를 확인하고(requireScreen), 아니면 열리지 않는다.

### 정해진 로그인 정책 (결정 2026-10-11)

- 이메일 하나 · 비밀번호 하나로 여러 회사. 로그인 실패 5회면 잠근다.
- 비밀번호 등록 · 변경은 메일 링크로 한다(최초 비밀번호를 관리하지 않음). 메일 발송은 Resend, 보내는 도메인 swonbiz.com.
- 개발계는 비밀번호 규칙을 쉽게 두고, 가동계로 옮길 때 보안 정책에 맞춘다.
- 보안 방침: 남의 정보를 보지 못하게 하는 것이 가장 중요하다.

## 5. 권한관리 — 판정은 삐용, 데이터 격리는 DB

권한은 두 겹이다. ① 「이 화면을 열 수 있는가」는 삐용이 정하고, ② 「어느 회사의 자료를 보는가」는 DB 의 행 단위 보안(RLS)이 막는다. ERP · 세무는 자체 권한 모델을 두지 않는다.

### 5-1. 삐용 권한 구조 (업무 관점)

- 서비스 → 기능 → 화면 3단. 예: 법무 서비스 아래 기능 넷(법인설립 · 법인변경 · 사업목적 · 설정), 기능 아래 화면들. 세무도 서비스 S05 와 그 기능을 삐용 「서비스 일람」에 등록해야 한다.
- 운영사(에스원테크)가 회사마다 기능을 배포한다(단체 등록의 「사용할 기능」). 회사가 받은 기능의 화면만 쓸 수 있다.
- 운영사가 권한(역할)별로 화면과 동작을 부여한다. 고객사 · 입주사는 권한 목록을 보기만 하고, 「권한별 사용자관리」에서 사람만 배정한다.
- 받은 화면만 왼쪽 메뉴에 나오고, 메뉴에 없는 화면은 주소로 들어가도 열리지 않는다(차단 모드). 메뉴는 삐용 「화면일람」(DB)에서 그린다.
- 버튼 권한은 Function Key: F001 조회 · F002 조회 · 등록 · 수정 · 삭제 · 내려받기 · 승인 · F003 · F004 화면별 특별 버튼. 서버 입구는 화면 권한만 보고, 버튼 제어는 각 프로그램이 한다.
- 기본 권한 등급은 공통 코드 표 BASIC_GRADE_CODE(ADMIN 관리자 · NORMAL 일반회원)에서 읽는다.

운영사 직원이 볼 회사 (결정 2026-10-09 · 10-10): 회사 보기 범위는 단체코드 앞글자가 아니라 그 회사가 받은 서비스로 가른다.

| 운영사 권한 | 보는 회사 |
|---|---|
| 총괄관리자(대표 · 일부 임원) | 모든 회사 |
| ERP관리자 | ERP 서비스를 받은 회사 |
| 삐용관리자 | 삐용 서비스를 받은 회사 |
| 메일관리자 | 메일 Agent 를 받은 회사 |
| 겸임 | 합친 범위 |

세무가 생기면 「세무관리자」 같은 권한과 「관리 서비스 = 세무」를 같은 방식으로 더하면 된다. 서비스 목록은 서비스 일람에서 읽고 코드에 박지 않는다.

### 5-2. 새 화면을 열리게 하는 배선 (세무 화면마다 반드시)

1. packages/shared/src/screens.ts — 화면 번호 · 경로 · 이름 · 그룹 등록. 사이드바 순서는 이 표의 선언 순서다.
2. packages/web/src/lib/sidebar.ts — 메뉴 아이콘. 상세 화면처럼 메뉴에 안 나오는 화면은 null.
3. 화면 페이지 맨 앞에서 requireScreen('화면번호', 경로) — 사이드바에 없는 화면도 꼭 거친다.
4. 모의 삐용 계정 화면 목록(MockBbiyongAuth)에 추가 — 운영사 · 회사 중 쓰는 쪽 모두.
5. 삐용 「화면일람」에 등록하고, 권한별 화면을 부여한다. ★ 목록과 상세는 함께 등록해야 상세가 열린다.
6. doc/SWONBIZ_SCREEN_LIST.md 화면 목록 정본에 한 줄.

- 웹 → 서버 중계(packages/web/src/app/api/...)와 프록시는 법무 것을 본떠 만든다.
- 세션의 역할(operator / tenant)은 화면 모양(버튼 보이기 등)에만 쓴다. 남의 회사 자료를 막는 것은 서버 · DB 몫이다.

### 5-3. 데이터 격리 — RLS (행 단위 보안)

- 법무 표(037 · 040 · 042 · 043)는 정책 erp_org_scope 로 묶여 있다: 운영사 세션은 전부, 회사 세션은 자기 단체 ID 의 줄만. FORCE 로 앱 계정도 예외 없이 적용.
- 서버는 DB 를 쓸 때 반드시 scopeOfSession 으로 세션 범위를 건 연결을 쓴다. ★ scopeOf(옛 방식)로는 법무 표에 접근이 안 된다 — 세무도 scopeOfSession.
- 남의 회사 건은 「없는 건」과 똑같이 404 로 답한다. 회사 세션이 남의 단체 ID 를 적어 보내면 403, 그리고 RLS 의 쓰기 검사가 한 번 더 막는다.
- 회사 ID 같은 값은 화면이 준 값을 믿지 않고, RLS 를 통과한 건에서 꺼내 쓴다.
- 앱 계정 erp_app 에는 필요한 권한만 준다(예: 이력 표는 읽기 · 넣기만, 지우기 없음). 마지막에 scripts/check-grants.js 로 바깥 계정 권한이 0건인지 본다.
- 표를 만들 때마다 verify 스크립트로 「회사는 자기 건만 보임 · 남의 단체로 넣기 거절」을 erp_app 접속으로 잰다(시험 줄은 롤백).

## 6. 공통 부품과 작업 관례 — 세무가 그대로 가져다 쓸 것

세무 화면은 법무에서 만든 부품을 새로 만들지 말고 재사용한다. 다시 만들면 같은 업무가 두 곳에 생긴다.

### 6-1. 화면 · 업무 부품

| 부품 | 하는 일 | 위치(참고) |
|---|---|---|
| 목록 + 상세 틀 | 목록 → 줄 누르면 상세, 상세는 사이드바에 없음 | features/legal/CorpChangesView · CorpChangeDetail |
| 임시 모드(새 건) | [새 건]은 DB 에 쓰지 않고 상세로 보내기만, 첫 [저장]이 건 + 내용 + 사람을 한 트랜잭션으로 만든다 | 법인변경 · 법인설립 상세 |
| 상태 전이 공용 규칙 | 서류작성중(P) → 작성완료(E) → 완료(C), 취소(X)·복원. 서버가 가능한 전이와 삭제 가능 여부를 내려 주고 화면은 그대로 그린다. 화면이 본 상태를 보내 다르면 409 | shared checkLegalTransition(corp-change.ts) |
| [작성완료] 한 번에 | 지금 입력 저장 → 검증 → P→E. 검증에 걸리면 저장만 하고 칸마다 오류 표시 | 법무 상세 |
| 작성완료 기록(스냅샷) | P→E 때 그 순간의 값을 JSON 으로 남김(주민번호 없음). 서류는 이 기록으로 찍어, 나중에 회사 정보가 바뀌어도 그때 값 유지. 칸을 더하면 판 번호를 올린다 | submit_snapshot · 작성완료일 written_at |
| 법무 확인 창 | 완료 · 완료 취소 · 취소(사유 선택) · 복원 · 삭제를 한 창으로 | CorpChangeConfirmDialog |
| 회사 조회 팝업 | 운영사가 [새 건]에서 삐용 단체를 고름 | 공용 회사 조회 팝업 |
| 주소 입력 | 카카오 우편번호 + 상세주소 | AddressInput |
| 숫자 모양 | 법인번호 000000-0000000 · 사업자 000-00-00000 · 전화 자동 하이픈(02 규칙 포함) | shared maskValue |
| 주민번호 | 받는 즉시 암호화, 화면에는 마스킹만, 서류 출력 순간에만 복호화(저장 · 로그 · 기록 없음, 응답 캐시 금지) | ERP_ENCRYPTION_KEY |

### 6-2. 서류(양식) 출력

- 양식은 표양식 관리(s030100020)에서 만든다. 양식에 「법무 표시」(업무 · 출력 단위 · 회사유형)를 붙이면 그 업무의 [서류 출력]에 뜬다. 세무 서류를 만들면 이 표시에 「세무」 업무를 더하는 방식이 된다.
- 가변항목은 {{영문이름}} 만 동작한다. 이름은 shared 의 이름표 목록(법인변경 CORP_CHANGE_PRINT_FIELDS, 법인설립 INCORP_PRINT_FIELDS)에 있어야 값이 들어간다. {{한글}} 은 값이 안 들어간다 — 법무에서 8종을 정리했다.
- 새 값이 필요하면: ① 값의 출처(이미 있는 입력 칸 / 새 입력 칸 / 계산) 정하기 → ② 이름표에 영문 이름 추가 → ③ 양식에 그 이름을 적기.
- 출력 대화상자: 왼쪽 서류 목록 · 가운데 미리보기(빈 칸은 흐린 이름표, 종이에는 안 나감) · 서류 하나씩 [인쇄]. 「기본 양식입니다. 제출 전 등기소 또는 법무사에게 확인하세요.」 안내는 화면에만.
- [인쇄]할 때 출력 이력을 한 줄 남긴다(FK 없음 · 주민번호 없음 · 실패해도 인쇄는 함). 세무 서류도 같은 모양의 이력 표가 필요하면 040 · 043 을 본뜬다.

### 6-3. 공통 코드 표

- 상태 이름 · 선택지 · 구분은 코드 표에서 읽는다(예: CORP_CHANGE_STATUS, NAME_POSITION, LAW_EST_TP, BASIC_GRADE_CODE). 화면에 상태 이름을 적지 않는다.
- 코드 이름 변경은 일회용 스크립트로 한다(예: 「상호변경」).
- ★ 법무 세금 계산의 세율 · 최소액 · 수수료는 지금 shared 상수(incorporation-tax.ts)에 있다. 이 상수 결정(10-14)은 대표의 「코드성 항목은 공통 코드 표에」 원칙(10-15)보다 앞선 것이다. 세무는 세율 · 기준 금액처럼 해마다 바뀌는 값을 처음부터 코드 표나 설정 표에 두는 것을 먼저 정한다.

### 6-4. DB · 스크립트 관례

- 마이그레이션: 파일만 쓰고 → 적용 전 영향 보고 → 승인 → 개발 DB 적용 → verify → 커밋 → doc/배포_계통전환.md §6-1 표에 한 줄. 앱이 새 칸을 읽으면 앱보다 마이그레이션을 먼저 적용해야 한다(안 그러면 화면이 안 열림).
- 일회용 스크립트: 기본 「보기」, --apply 일 때만 한 트랜잭션으로 쓰기. 조건이 안 맞으면 아무것도 쓰지 않고 멈춤(두 번 돌려도 안전). 개발 DB 에 적용한 것은 「등록함」 표시로 기본 선택에서 빼고 --only=이름 으로 다시 고른다. 배포 문서 §6-2 표에 한 줄.
- 원본 자료(docx · 엑셀)는 git 밖 폴더에 두고, 배포 문서에 「그 PC 에 원본이 있어야 돈다」를 적는다.
- 해마다 바뀌는 자료(업종 사전 등)는 「최신 한 벌 덮어쓰기, 빠진 것은 지우지 않고 사용 안 함」으로 갱신한다.

### 6-5. 화면 모양 규칙

- 디자인: 대표색 #4F46E5(인디고), 강조 #22D3EE(시안), 녹색 계열 쓰지 않음.
- 등록 · 수정 · 삭제 버튼은 왼쪽. 행마다 버튼 대신 「행 선택 + 목록 위 버튼」.
- 저장 버튼은 하나로(여러 묶음을 한 번에 저장). 제목 옆에는 상태명만. 날짜 줄은 상태에 맞는 날짜만.
- 시안이 없으면 법무 목록 · 상세 모양을 따른다. 시안이 있으면 시안대로.

## 7. 법무에서 확정된 결정 — 세무에도 그대로

법무를 만들며 대표가 정한 것 중 세무에 그대로 적용할 원칙이다. 세무 방에서 다시 묻지 않아도 된다.

| 결정 | 내용 | 세무에 적용 |
|---|---|---|
| ERP 는 판단하지 않는다 | 기본 서류 초안 · 자료만 만들고, 최종 확인은 고객이 전문가(등기소 · 법무사)에게 받는 구조 | 세무도 신고 자료 · 서류 초안까지. 최종 확인은 세무사 · 세무서. 「참고용」 안내 문구 |
| 운영사 · 회사가 같은 화면 | 한 화면을 운영사 · 회사가 함께 쓰고, 보이는 범위는 RLS 가 가름 | 세무 화면도 한 벌로 |
| 회사 키 = 삐용 단체 ID | 입주사 · 일반 고객사 모두 같은 키 | 그대로 |
| 상태 흐름 단순화 | 제출(A) 단계 없음. P → E → C, 취소 X | 세무 흐름도 단계를 늘리지 않는다 |
| 완료 취소 · 삭제는 운영사만 | 삭제는 P · X 일 때만 | 같은 규칙 권장 |
| 회사는 ERP 회사표에 쓰지 않음 | 법무 완료가 ERP 회사 정보를 바꾸지 않는다 | 세무도 다른 업무 자료를 고치지 않는다 |
| 선택 입력은 막지 않음 | 개회시간 · 납입은행처럼 선택 칸은 비워도 작성완료를 막지 않고 서류는 빈칸 | 그대로 |
| 비어 있으면 빈칸 | 입력하지 않은 값은 종이 · 미리보기 모두 빈칸(지어 넣지 않음) | 그대로 |
| 세금 계산 근거는 조문으로 | 세율 · 최소액 · 수수료에 근거 조문을 주석으로 남김(지방세법 제28조 등) | 세무 계산은 모두 근거 조문을 붙이고, 값은 코드 · 설정 표에 |
| 회사 정보 보안 | 주민번호는 출력 순간에만 평문, 응답 캐시 금지 | 급여 · 원천세 자료(주민번호 · 급여)는 같은 수준 이상으로 |

### 법무 쪽 참고 자료 중 세무에 쓸 만한 것

- 업종 사전(작업 중, 법무 방): 국세청 업종코드(6자리) · 업태 · 종목 · KSIC 연계. 원본은 홈택스 「업종코드-표준산업분류 연계표」(2026 귀속) · 「2025 귀속 업종코드」 엑셀(doc/data-src/). 마이그레이션 047 과 적재 스크립트는 파일만 있고 적용 · 커밋 전이며, 법무 방에서 방향을 다시 정하기로 했다. 세무(사업자등록 업태 · 종목 · 경비율)와 겹치므로 두 방이 같은 표를 쓰도록 먼저 맞춘다.
- 법인설립 세금 계산: 등록면허세(자본금 × 4/1000, 최소 112,500원, 대도시 중과 3배) · 지방교육세 20% · 등기신청수수료 35,000원(서면). 세무 계산 모양의 본보기.
