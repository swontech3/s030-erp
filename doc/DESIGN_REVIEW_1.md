## 먼저 — 시안을 브라우저로 열어 확인했습니다

1440×1000 으로 렌더해서 5개 상태를 전부 전환해 보고, 최대 행수까지 눌러 보고,
확인 모달을 열어 보고, 좁은 창에서 가드를 떼어 보며 확인했습니다.
아래 모든 판단에는 그렇게 얻은 실제 값이 붙어 있습니다.

**결론부터: 이 형식으로 나머지도 주십시오.** 마크다운 명세만 있던 때와 비교가 안 됩니다.
지난 3-1 에서 저희가 화면을 원본과 다르게 만든 원인이 "배치를 볼 수 없어서"였는데,
이 시안은 그 문제를 없앱니다. 아래 요청은 전부 **이 형식을 유지한 채로**의 보완입니다.

| 4 | **오류 상태가 사업자번호 하나뿐** | `.err` 클래스는 있는데 쓰이는 곳이 `#biz-msg` 하나입니다. 필수 미입력으로 «계약확정»을 눌렀을 때 어느 칸이 어떻게 빨개지는지 알 수 없습니다 |

| 6 | **빈 상태 규격** | 입주사 목록이 0곳일 때의 아이콘·문구·액션 버튼 유무가 어디에도 없습니다. `05-patterns.md#8` 의 **기하**(패딩 32~80px·아이콘 32~40px·문구 14~16px)는 있는데 이 경우의 **내용**이 없습니다. 저희가 3-1 에서 지어내 넣었고, 지금도 지어낸 채로 있습니다 |

### 그리고 하나 — 라벨이 데이터 모델과 어긋납니다

## ③ 상단 확인 컨트롤 바가 도움이 되는지

### → 크게 도움이 됩니다. 유지해 주십시오. 다만 최대치를 넣어 주십시오.

**동작을 확인했습니다 — 장식이 아니라 실제로 화면을 바꿉니다.**

`mode` 를 `confirmed` 로 바꿨더니 한 번에 이렇게 됐습니다.

```
제목      계약 수정 → 계약 상세
버튼      이전·계약취소·임시저장·계약확정  →  이전·계약서 출력·종료·저장
잠금 뱃지  없음 → 「확정됨」
삭제 열    grid 트랙 10개 → 9개 (열이 사라짐)
섹션 2     전 입력 disabled
```

계약 폼은 **상태 5종 × 회원구분 3종 × 첨부 3종 × 사업자확인 4종**의 조합입니다.
컨트롤 바가 없으면 저희가 이 조합을 코드로 만들어 가며 확인해야 하고, 그 과정에서
"명세엔 있는데 시안엔 없는" 상태를 놓칩니다. 위 ②-1(보조 안내 2종 미구현)도
컨트롤 바로 상태를 돌려 보다가 찾았습니다.

### 보완 요청 — 최대치를 넣어 주십시오

```
contractItemCount   1 / 2 / 3        → 1 / 3 / 10  (최대)
userCount           1 / 3            → 1 / 3 / 20  (최대)
```

지금은 3까지만 있어서 **최대 행일 때의 화면을 컨트롤 바로 볼 수 없습니다.**
저희는 버튼을 15번 눌러서 확인했습니다. 10행·20행은 세로가 길어져 sticky 헤더와
금액 합계 블록의 관계가 달라지는 지점이라 한 번은 봐야 합니다.

`docUploaded` 에 `none` 이 이미 있는 것처럼, 0건 상태도 함께 넣어 주시면 ②-3 이 해결됩니다.

### 시안 전용 요소의 표시 — 지금 상태로 충분합니다

```
50행    /* ── 확인 컨트롤 바 ── ★ 개발 확인용. 실서비스에는 포함되지 않습니다 ── */
322행   ★ 개발 확인용입니다. 실서비스 화면에는 포함되지 않습니다.
```

클래스 이름도 `.devbar` 하나로 격리돼 있고 마크업이 `.shell` **바깥**에 있어서,
이관할 때 통째로 지우면 끝입니다. 섞여 들어올 위험이 없습니다.

## ④ 주석·코드 구조가 파악하기 쉬운지

### → 네. 저희가 실제로 뽑아 쓸 세 가지가 다 찾기 쉽습니다.

저희가 이 파일에서 가져가는 것은 **토큰 사용 · 섹션 구조 · 클래스 이름** 셋입니다.

| 가져갈 것 | 시안에서 | 평가 |
|---|---|---|
| 토큰 | 10행 `/* ── 디자인 토큰 ── handoff/tokens/*.css 와 동일한 값 ── */` | 값이 실제로 같은지 대조했습니다. **같습니다** |
| 섹션 구조 | `<!-- ══ 섹션 1 · 회사 기본정보 ══ -->` + `id="sec-company"` 등 4개 | id 가 붙어 있어 바로 집힙니다 |
| 클래스 | `/* ── 폼 ── */` `/* ── 계약 폼 전용 ── */` 등 12개 블록 주석 | CSS 가 역할별로 묶여 있습니다 |

**특히 좋았던 것 — "왜"가 적힌 주석입니다.**

```
63행   고정 1440px 제작 — 좁은 창에서는 클리핑이 아니라 가로 스크롤이 생겨야 합니다.
       이 가드가 없으면 .contract-item-table 의 overflow:hidden 이 우측 열을 잘라냅니다.
```

이 두 줄이 질문 ⑤ 의 답을 거의 다 만들어 줬습니다. 값만 있는 주석이었다면 저희가
가드를 무심코 지우고 열이 잘리는 걸 나중에 발견했을 겁니다.
`1168행 /* ── 파생값만 갱신 ── 입력 중 포커스를 잃지 않도록 행은 다시 그리지 않습니다 ── */`
도 같은 종류입니다. **이 스타일을 나머지 3개에도 유지해 주십시오.**

### 이관 시 저희가 바꿀 것 (문제가 아니라 참고)

- **폰트·아이콘 CDN** — 시안은 jsdelivr(Pretendard)·unpkg(lucide)를 씁니다.
  저희는 폰트를 자체 호스팅하고 아이콘은 SVG 를 빌드에 넣습니다(CSP 때문에 외부
  도메인을 열지 않습니다). 시안에서는 CDN 이 편하니 그대로 두셔도 됩니다
- **인라인 스타일** — `style="flex:1;min-width:0"` 류가 섞여 있습니다. 개수가 적고
  레이아웃 미세조정용이라 이관에 지장 없습니다

## ⑤ `min-width:1440px` 가드를 그대로 둘지

### → 두십시오. 그런데 이 가드는 T7 재사용의 걸림돌이 아닙니다. 진짜 걸림돌은 따로 있습니다.

이 질문에 "떼면 반응형 개발이 편하다"로 답하면 틀립니다. 실제로 재어 봤습니다.

### 측정값

```
가드 선언 위치     .shell  단 한 곳          (min-width:1440px)
계약 항목 테이블    minmax 하한 합계  948px   + overflow:hidden
입주자 사용자 행    minmax 하한 합계 1022px
섹션 1 그리드      repeat(4, minmax(0,1fr))  ← 하한 없음
```

900px 창에서 가드를 떼고 측정한 결과:

```
계약 항목 테이블   보이는 폭 528px / 실제 폭 948px  → 잘림. 스크롤바 없음
입주자 사용자 행   보이는 폭 530px / 실제 폭 1022px → 넘침
섹션 1 그리드      117.5px × 4                      → 안 잘림, 그냥 좁아짐
```

### 그래서 셋으로 나뉩니다

**1. 가드는 섹션 2 때문에 있습니다.** `.contract-item-table{overflow:hidden}` 이 우측 열을
**스크롤바 없이 조용히** 잘라냅니다. 주석에 적으신 그대로입니다.

**2. T7 이 재사용하는 섹션 1·4 는 가드와 무관합니다.**
`03-contract-form.md` 는 "섹션 1·3·4 를 비로그인 온라인 신청 폼에 그대로 재사용"한다고
적었고, T7(`s0300500020`)은 **050 공개 화면 — 로그인 전, 외부인, 휴대폰**입니다.
그런데 가드는 `.shell`(ERP 셸)에 걸려 있고 **T7 은 ERP 셸을 쓰지 않습니다**
(핸드오프 README: "별도 랜딩·신청 폼 — 공개 영역, ERP 셸을 쓰지 않습니다").
섹션 1 은 하한이 없어 117px 열까지 줄어들고, 섹션 4 는 flex 카드라 그냥 쌓입니다.
**둘 다 가드를 들고 오지 않습니다.**

**3. ★ 진짜 문제는 섹션 3 입니다.** 사용자 테이블 8열의 minmax 하한 합계가 **1022px** 입니다.
이건 가드와 무관한 **그리드 자체의 하한**이라, 가드를 떼도 휴대폰에서 안 줄어듭니다.
`minmax(300px, 1.7fr)` 인 이메일 열 하나만 해도 웬만한 휴대폰 폭입니다.

> **요청 — 섹션 3 의 모바일 레이아웃을 주십시오.**
> 8열 그리드를 유지한 채 폭만 줄이는 방법은 없습니다. 행을 카드로 쌓는 별도 배치가
> 필요합니다. T7 착수 전에 필요하고, 이건 CSS 조정이 아니라 **설계**입니다.

### 가드 자체에 대한 제안 하나

`.contract-item-table` 의 `overflow:hidden` 을 **`overflow-x:auto`** 로 바꿔 주시면,
좁은 창에서 열이 잘리는 대신 가로 스크롤이 생깁니다. 주석에 쓰신 의도
("클리핑이 아니라 가로 스크롤이 생겨야 합니다")가 가드 없이도 성립하게 됩니다.
그러면 가드는 **필수**에서 **취향**으로 내려가고, 나중에 떼기 쉬워집니다.

지금은 유지에 찬성합니다. 없으면 시안이 "화면에 있는 것"에 대해 거짓말을 합니다.

## 우리 확정 사항과의 충돌 — **충돌 0건**

시안을 저희가 못 박아 둔 항목들과 하나씩 맞춰 봤습니다.

| 확인할 것 | 우리 결정 | 시안 | 판정 |
|---|---|---|---|
| 비밀번호 입력란 | 어떤 형태로도 없어야 함 | 검색 결과 **0건** | ○ |
| 단체코드 입력란 | 없어야 함 (ERP 가 `Z01`~ 자동) | **0건** | ○ |
| 국가 입력란 | 없어야 함 (항상 `KR`) | **0건** | ○ |
| 대표자 칸 | **하나**여야 함 | 섹션 1 에 `data-f="ceo"` **하나**. 섹션 3 1행이 그 값을 미러링(ReadOnly) | ○ |
| 구독 설정 | 있다면 지금 고를 항목 없음 | 시안에 **없음** (계약 폼에 구독 개념 자체가 없음) | ○ |
| 상태 전이 | `create→draft→confirmed→terminated` / `draft→cancelled`, 되돌리기 없음 | 5종 전부 일치. 되돌리는 버튼 없음 | ○ |
| 녹색 | 완료·성공도 인디고 | 저희 `lint:green` 통과. `bizCheck: success` 의 색도 `var(--color-primary)` | ○ |

**녹색 0건입니다.** 검색에 걸린 `success` 는 사업자번호 확인 결과의 상태 이름이고
색은 인디고입니다. 규칙을 정확히 지켜 주셨습니다.

### 회의실·호실 — 확인 필요 1건

계약 항목의 호실 Select 가 `Room-1` · `Room-2` · `Room-15` 로 채워져 있습니다.
**호실 마스터(기준관리)는 페이즈 2 이고 아직 없습니다.** 시안 값이 예시라는 것은
알지만, 저희가 알아야 할 것은 **호실 목록을 어디서 받는 전제인지**입니다.

- 건물·층 Select 로 거른 결과인지 (섹션 헤더에 삼성센터/3층 Select 가 있습니다)
- **공실만** 내려오는지, 사용중 호실도 보이되 비활성인지
- 재계약 시 현재 쓰는 호실은 "사용중"이지만 선택돼 있어야 합니다 — 이 예외 처리

`07-data-model.md` Room 에 `status 공실/사용중/점검` 이 있는데 화면에서 그 상태가
어떻게 보이는지가 없습니다.

## 시안에 있는데 삐용에 보낼 곳이 없는 항목

전부 **ERP 가 보관**합니다. 삐용 회사 등록 규격에 자리가 없습니다.

| 항목 | 처리 |
|---|---|
| 회원구분 (프리랜서/개인사업자/법인) | ERP 보관. 첨부 서류 필수 여부를 좌우하므로 반드시 필요합니다 |
| 법인등록번호 | ERP 보관 |
| 업종 / 업태 | ERP 보관 (세금계산서) |
| 사업자등록번호 | ERP 보관. 삐용 `org010` 에 컬럼이 없습니다 |
| 특기사항 (섹션 1·2) | ERP 보관 |
| 계약 전체 (섹션 2) | ERP 보관. 삐용은 계약을 모릅니다 |

**문제 없습니다.** 알려드리는 이유는, 이 항목들이 삐용에 안 가므로 **삐용 화면에서는
안 보인다**는 점을 설계에 반영해 주십사 해서입니다.

## 삐용이 필수로 요구하는데 시안에 없는 항목

| 항목 | 처리 |
|---|---|
| `orgCode` 단체코드 (필수, 3자) | ERP 가 `Z01` 부터 자동 채번. **화면에 두지 않습니다** |
| `countryCode` 국가 (2자) | 항상 `KR` 자동. **화면에 두지 않습니다** |

둘 다 사람이 넣는 값이 아니라 **시안에 없는 것이 맞습니다.** 화면 추가 요청이 아닙니다.

## 우리 쪽 결정으로 시안이 바뀌어야 하는 부분

### 1. 대표자 칸 — 시안이 이미 맞습니다 (저희가 따라갔습니다)

저희는 두 칸을 들고 있었습니다.

```
「입주사 정보」 대표자명    사업자등록증상 법적 대표 (ERP 보관)
「대표 정보」   대표 성명    삐용 계정을 받는 사람   (삐용 전송)
```

시안은 섹션 1 에 **대표자 하나**만 두고 섹션 3 1행이 미러링하는 구조입니다.
**저희가 시안에 맞춰 하나로 합쳤습니다.** 사업자등록증상 대표가 곧 ERP 계정을 받습니다.
실무자가 대표와 다른 경우는 칸을 나누지 않고 **직원 등록으로 풉니다.**

### 2. 이메일 도메인 목록 — ★ 첫 번째 옵션을 바꿔 주십시오

```js
637행  const EMAIL_DOMAINS = ["bridgelab.co.kr", "naver.com", "gmail.com", ...];
```

**`bridgelab.co.kr` 은 시안 예시 입주사의 도메인인데 목록의 첫 번째, 즉 기본값입니다.**
`03-contract-form.md` 에도 같은 순서로 적혀 있어서 명세·시안이 함께 그렇습니다.

이대로 이관하면 운영자가 새 입주사를 등록할 때 **아무 관계 없는 회사 도메인이 기본 선택**
됩니다. 대표 이메일은 곧 로그인 아이디라 잘못 들어가면 계정이 안 열립니다.
`naver.com` 을 첫 번째로 올리거나, 기본값을 비워 두고 「선택하세요」를 넣어 주십시오.

### 3. 저희 모달은 곧 없어집니다 (시안 변경 요청 아님)

`s0300200030p2` 신규 입주사 등록 모달을 지금 저희가 들고 있습니다.
새 원본이 이 모달을 없애고 계약 폼으로 일원화한 것을 확인했고, **동의합니다.**
다만 계약 폼이 페이즈 4 라 지금 지우면 입주사를 등록할 방법이 사라집니다.
**페이즈 4 에서 걷어내는 것으로 확정**하고 로드맵에 작업으로 등록했습니다.

그동안 저희 모달의 필드 배치가 시안과 다릅니다(저희는 「대표 정보」를 별도 섹션으로 둠).
**시안을 고쳐 달라는 요청이 아닙니다** — 없어질 화면이라 그대로 둡니다.
