## 보내는 것

### ① 확정된 ERP 접속 주소 — CORS 허용 목록 등록용

| 환경 | 주소 | 용도 |
|---|---|---|
| 운영 (제안) | `https://erp.swonbiz.com` | 브라우저 오리진. **CORS 허용 목록에 이 오리진을 등록**해 주십시오 |
| 개발 | `http://localhost:3000` | 개발 PC 브라우저 오리진 |

보충 설명 두 가지입니다.

- **브라우저가 삐용 API를 직접 부르지 않습니다.** ERP 서버(Fastify)가 서버끼리 삐용 API를 호출하고, 브라우저에는 ERP가 만든 불투명한 세션 쿠키(`erp_sid`) 하나만 내려갑니다. 삐용 access·refresh 토큰은 ERP 서버에만 암호화 보관됩니다(지시서 1-4). 그래서 실제로는 **ERP 서버의 송신 IP**를 허용해 주시는 것이 더 중요할 수 있습니다 — 서버 IP는 배포 시점에 별도로 드리겠습니다.
- 그럼에도 오리진 등록을 요청드리는 것은, 삐용 비밀번호 재설정 화면으로 나가는 외부 링크(로그인 화면의 "비밀번호 찾기")처럼 **브라우저가 삐용 화면으로 직접 이동하는 경로**가 있기 때문입니다.

### ② 화면 목록 — 페이즈 1분 (팝업·모달 포함)

지시서 2-6 ③의 형식에 맞춰 **화면코드 · 화면명 · 대상 · 동작**을 드립니다. 마스터 등록 시 코드는 **대문자**로 올려 주십시오(체계는 ③ 참조).

| 화면코드 (마스터 등록용) | ERP 내부 코드 | 화면명 | 모듈 | 대상 | 동작 | 비고 |
|---|---|---|---|---|---|---|
| `S0300000010` | `s030000010` | 로그인 | 공통 | 전체 | VIEW | 인증 전 화면. 권한 판정 대상 아님 — 목록 완결성을 위해 기재 |
| `S0300000050` | `s030000050` | ERP 셸 (사이드바·헤더) | 공통 | 운영사 · 입주사 | VIEW | 라우트 없는 레이아웃. **접근 가능 화면 목록에 이 코드가 포함돼야 셸이 뜹니다** |
| `S0300000080` | `s030000080` | 접근 권한 없음 | 공통 | 전체 | VIEW | 로그인은 됐으나 접근 가능 화면이 0건일 때. 권한 판정 대상 아님 |

이번 페이즈에는 **팝업·모달이 없습니다** (`s030000010p1` 조직 선택은 회신 ⑩ 전까지 보류).

자리만 있고 내용이 없는 화면 2개는 **다음 페이즈에서 제출**합니다: `s030000060` 대시보드(운영사) · `s030600010` 회의실 예약 현황. 다만 ERP는 홈 분기를 이 두 코드의 **권한 유무**로 정하므로(대시보드 권한 있음 → `/dashboard`, 예약 권한 있음 → `/booking`, 둘 다 없음 → 안내 화면), 마스터에 미리 등록해 두시면 홈 분기를 실 권한으로 시험할 수 있습니다.

### ③ 화면코드 체계 — ERP 현행 유지로 회신

지시서 2-7의 제안(`S03` + 업무그룹 3 + 순번 4 = 10자)에 대한 회신입니다. **ERP 현행 체계(`s030` + 업무구분 3 + 순번 4 = 11자, 팝업은 접미사 `p{n}`)를 유지**하겠습니다.

| | 삐용 제안 | ERP 현행 (채택) |
|---|---|---|
| 형식 | `S031000010` (10자) | `s030200040` (11자) |
| 팝업 | 순번 뒤 2자리 | 접미사 `p1` → `s030200040p1` (13자) |
| 대소문자 | 대문자 | 소문자 사용, **마스터 제출 시 대문자로 변환** (`toUpperCase()` 뿐이라 매핑표 불필요) |

이유는 하나입니다. 삐용 제안의 업무그룹은 **기능 단위**(100 입주계약·200 예약…)이고 ERP 업무구분은 **화면 조직 단위**(010 기준설정·020 입주사관리…)라, 변환하면 기준설정과 입주사관리가 둘 다 OFFICE(100)에 떨어져 **`S031000010`이 두 화면에 동시에 배정되는 충돌**이 납니다. 결정론적 변환이 불가능해 현행을 유지합니다. 지시서 2-7 자신이 "코드는 판단 근거가 아니다"라고 못박았으므로, 판정에는 영향이 없습니다.

**확인 요청:** 화면코드 컬럼이 **11자(팝업 13자)**를 받는지 확인 부탁드립니다(③에 딸린 항목).

## ④⑤⑥⑦ — **2026-09-08 회신 도착. 반영 완료.**

네 항목이 예상대로 로그인 성공 처리 코드 한 곳에서 한 번에 나왔습니다. `HttpBbiyongAuth` 를 구현해 Mock 과 교체했고, **다른 코드는 손대지 않았습니다** — 어댑터 경계가 의도대로 동작했습니다.

| # | 회신 내용 | ERP 반영 |
|---|---|---|
| ④ | 토큰은 클라이언트 보관 전제 | ERP는 그대로 서버 보관(AES-256-GCM). 브라우저에는 `erp_sid` 하나뿐 — **변경 없음** |
| ⑤ | access 폴백 30분 · refresh 폴백 7일. **개발계·가동계가 각 DB `code010` 으로 분리돼 값이 다를 수 있음** | 만료 시각을 코드에 박지 않았습니다. 30분은 ERP 어디에도 없고, 401 을 받으면 `re-issue` 로 갱신합니다 |
| ⑥ | JWT 는 `sub`·`auth`·`exp` 셋뿐 — **`orgId` 없음** | 가정이 맞았습니다. `orgId` 는 로그인 **응답 본문**에서만 받아 세션에 보관 — **변경 없음** |
| ⑦ | `POST /rest/v1/s021200010/sign-in`, `{email, pwd}`. 실패도 HTTP 200, 판정은 `result==='success' && status===200`. 사유 필드명은 **`massage`** | `HttpBbiyongAuth` 1개 신규. 이 두 함정은 각각 시험으로 고정했습니다(테스트 42건) |

**회신에서 새로 알게 된 것 3가지**와 처리:

- **`needOrgSelect`** — 겸직 계정이면 토큰 대신 단체 선택 목록이 옵니다. 2단계 로그인 팝업(`s030000010p1`)은 아직 만들지 않되(겸직 계정이 실제로 없음), **조용히 실패시키지 않습니다** — 로그인 화면에 "여러 단체에 소속되어 있습니다. 삐용에서 로그인한 뒤 다시 시도해 주세요"를 띄우고 서버 로그에 남깁니다. 그 로그가 찍히면 팝업을 만듭니다. `selectToken` 은 3분 유효라 보관하지 않습니다.
- **실패 사유를 구분할 수 없음** — 이메일 없음과 비밀번호 틀림이 둘 다 `A005`. 계정 존재를 노출하지 않으려는 의도로 이해했고, ERP도 구분하지 않습니다("이메일 또는 비밀번호가 올바르지 않습니다" 한 문구).
- **비밀번호 재설정 딥링크 없음** — `/SignIn` 하단 링크의 모달이라 직접 열 수 없습니다. ERP의 "비밀번호 찾기"는 `/SignIn` 까지만 데려다주고 사용자가 거기서 한 번 더 눌러야 합니다.

### 아직 필요한 것 (⑦에 딸린 것들)

| 항목 | 지금 어떻게 하고 있나 | 오면 무엇이 좋아지나 |
|---|---|---|
| **삐용 REST API 의 실제 베이스 URL** | `https://bbiyong.s-wontech.co.kr` 로 시험 호출 → **HTTP 405**. 이 주소는 화면 서버이고 API 호스트가 아닌 것으로 보입니다 | 이 값 하나가 있어야 실계정 로그인 시험이 됩니다. `packages/api/.env` 의 `BBIYONG_BASE_URL` 한 줄 |
| **회원 표시정보 조회 엔드포인트** (memberId → 이름·단체명) | 로그인 응답의 이름을 **프로세스 메모리에만** 들고 있습니다. ERP DB에 복사하지 않습니다(삐용에서 이름이 바뀌면 ERP만 옛 이름을 들고 있게 되므로) | 지금은 ERP API를 재기동하면 이미 로그인해 있던 사용자의 헤더 이름이 다시 로그인할 때까지 빈칸입니다. 표시 전용이라 권한·스코프에는 영향이 없습니다 |
| **2단계 로그인(`/sign-in-org`) 요청·응답 규격** | 겸직 계정을 안내 문구로 돌려보냅니다 | 겸직 계정이 생기면 `s030000010p1` 을 만들어야 하고, 그때 필요합니다 |

### 별건 — 보안 1건 (ERP 작업이 아니라 삐용 쪽 과제입니다)

`POST /rest/v1/s021200010/init-pwd` 가 **인증도 본인확인도 없이** 단체명·대표자명·이메일 세 값만 맞으면 비밀번호를 즉시 바꿉니다. 세 값 모두 사업자등록증이나 홈페이지에서 확인되는 공개 정보라, **비밀번호를 모르는 외부인이 계정을 가져갈 수 있는 경로**입니다. ERP는 계정을 발급하지도 비밀번호를 저장하지도 않아 코드로 막을 수단이 없고, 삐용 계정이 넘어가면 ERP도 같이 넘어갑니다.

상세와 조치 제안(이메일 확인 링크 방식, 시도 횟수 제한)은 `doc/BBIYONG_SECURITY_REPORT.md` **§7** 에 적었습니다 — 9/1 에 드린 보안 점검 문서의 추가분입니다.

### 함께 받고 싶은 것 (우선순위 순)

- **⑫ 권한 조회 API 규격** — 접근 가능 화면 **목록** 엔드포인트가 있는지가 핵심입니다(단건 check 만 있으면 사이드바를 그릴 수 없습니다). 응답에 화면코드·동작·범위(본인/회사) 3종이 들어가는지.
- **⑮ 공통 화면의 모듈 소속** — `tb_s020_module010`의 S03 모듈이 OFFICE·BOOKING·LEGAL·TAX·BILLING 5종뿐이라 셸·대시보드·설정을 붙일 자리가 없습니다. 없으면 홈 분기가 동작하지 않습니다.
- ⑩ 겸직 지원 여부 — **회신 ⑦로 사실상 확인됨**(`needOrgSelect` 분기가 존재 = 같은 이메일이 여러 단체에 있을 수 있음). 남은 것은 2단계 로그인(`/sign-in-org`) 규격이며, 겸직 계정이 실제로 생기기 전까지 `s030000010p1` 은 만들지 않습니다.
- ⑬ 삐용 조직 목록 API — 입주사 ↔ 삐용 조직 연결 UI 드롭다운용(없으면 수기 입력으로 진행).
- ⑧ BILLING `provider_only_yn` / ⑨ 050 공개 화면 마스터 등록 여부 / ⑪ 삐용 미사용 입주사 계정 경로 / ⑯ 마스터 시드 리드타임.

## 참고 — 페이즈 1에서 ERP가 확정한 것 (삐용 쪽 변경 요청 아님)

- 세션: 불투명 `erp_sid` 쿠키(HttpOnly · Secure · SameSite=Lax), DB에는 SHA-256 해시만. 삐용 토큰은 서버 AES-256-GCM.
- 권한: 1단계 shadow — ERP는 화면 접근을 **막지 않고 기록만** 합니다(`tb_s080_acl_shadow_log`). 마스터 등록·⑫ 회신 후 실제 차단으로 올립니다.
- 데이터 스코프(`company_id`)는 shadow 대상이 아니며 1단계부터 강제됩니다 — 삐용 조직 ↔ ERP 입주사 연결(`link_s020_org_id`)이 없는 세션은 **0건**을 봅니다.
