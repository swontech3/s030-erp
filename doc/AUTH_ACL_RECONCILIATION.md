## 0. 지시서가 바꾼 것 한 줄

이전 설계는 **ERP가 자기 세션을 발급하고 자기가 판정**하는 구조였다. 지시서는 **ERP가 삐용 토큰을 그대로 쓰고 판정은 매번 삐용에 묻는** 구조를 확정했다. 인증·권한에서 ERP가 소유하는 것은 **화면뿐**이다.

## 1. 정면 충돌 — 지시서를 따른다

### 1.1 AUTH-03 / AUTH-04 / AUTH-05 — 자체 세션 발급 폐기

| | 기존 | 지시서 |
|---|---|---|
| AUTH-03 | 브라우저는 삐용 토큰을 절대 보유하지 않는다. 삐용 호출은 Route Handler에서 서버-서버로만 | 1-2 ④⑥⑦ — **ERP 프론트가 삐용 로그인 API를 직접 호출하고 토큰을 자기 쪽에 저장**한다 |
| AUTH-04 | 로그인 성공 시 ERP가 자체 세션 JWT를 발급해 httpOnly 쿠키로 내린다 | 3장 — **✗ 자체 토큰 발급** |
| AUTH-05 | Fastify는 ERP 세션 JWT를 독립 검증한다 | 검증 대상이 **삐용 JWT**로 바뀐다 |

**판정: 지시서.** 근거가 대칭이 아니다 — 기존 설계의 이유는 XSS 표면 축소라는 일반론이고, 지시서의 이유는 *"진실원이 둘이 되면 한쪽만 고치는 사고가 난다"* 는 이 시스템의 구체적 사고 이력(1-6, 8월 명부 유출)이다. 또한 자체 세션을 발급하면 삐용 토큰 만료와 ERP 세션 만료가 어긋나 1-5가 경고한 "작업 중 튕김"이 생긴다.

**개정:**
- ~~AUTH-03~~ → **AUTH-03′**: ERP는 삐용 로그인 API를 호출하고 받은 토큰을 저장한다. 저장 위치는 삐용 구현을 따른다(회신 ④).
- ~~AUTH-04~~ → **폐기.** ERP는 토큰을 발급하지 않는다.
- **AUTH-05′**: 모든 보호된 요청에서 **삐용 JWT**를 검증한다.

**대가로 감수하는 것:** 토큰이 브라우저 저장소에 놓이므로 XSS 노출 면적이 커진다. 저장 위치가 로컬 저장소로 확인되면(회신 ④) CSP와 의존성 감사를 별도 항목으로 세운다. → 신규 **SEC-01**.

### 1.2 AUTH-06 — 유지하되 용도를 좁힌다

토큰 검증 단일 진입점(`lib/auth/verifyToken.ts`), 알고리즘 허용목록·`iss`·`aud`·`exp` 명시 검사, 클레임 Zod 검증은 **그대로 유효하다.** 다만 1-6이 못을 박는다:

```
○  화면 상단에 "홍길동 (에스원테크)" 표시
✗  토큰의 회원유형을 보고 메뉴를 열고 닫기
✗  토큰의 회사번호를 API 요청에 실어 보내기
```

**AUTH-06′**: 검증된 클레임은 **표시 용도로만** 쓴다. 권한·범위 판정에 쓰지 않는다.

### 1.3 AUTH-09 / AUTH-10 / ACL-07 — 판정 주체가 바뀐다

기존은 ERP가 `role`을 보고 홈을 분기하고(운영사 `/dashboard`, 입주사 `/booking`), 운영사 전용 URL 직접 접근을 리다이렉트했다. 2-1은 **ERP가 판정하는 것 자체를 금지**한다.

**개정:** 분기와 숨김이라는 **결과는 유지**하되, 판단 근거를 삐용 API 응답으로 바꾼다.

- **AUTH-09′**: 로그인 직후 삐용에 접근 가능 화면 목록을 물어, 그 목록의 첫 화면을 홈으로 삼는다.
- **AUTH-10′**: 목록에 없는 화면 URL로 직접 들어오면 접근 가능한 화면으로 보낸다.
- **ACL-07′**: 사이드바는 삐용이 준 목록만 그린다. ERP가 역할을 보고 거르지 않는다.

2-9가 남는다 — **화면 숨김은 편의이고 실제 통제는 서버**다. ACL-04(존재 여부 은닉 404)·ACL-05(서버에서 필드 제거)는 그대로 유효하며 오히려 지시서가 요구하는 바다.

### 1.4 ACL-01 — `s030_org_member` 매핑 테이블 재검토

기존: 삐용 `member_id` + 선택한 `org_id`를 ERP의 `tenant_id` + `role`로 매핑하는 `s030_org_member` 테이블을 둔다.

2-1(자체 권한 모델 금지)과 3장(✗ 삐용 DB 직접 조회·스키마 넘어 조인·외래키)에 걸린다. 다만 **매핑 테이블 전부가 금지되는 것은 아니다** — 금지된 것은 *역할·권한의 판정 근거*를 ERP가 갖는 것이다.

**개정 — ACL-01′**: ERP는 역할을 저장하지 않는다. 저장하는 것은 **삐용 조직 ↔ ERP 입주사(`tb_s030_companies`)의 대응 하나**뿐이며, 이는 권한이 아니라 **데이터 소유자 식별**이다. 컬럼 하나로 족하다:

```
tb_s030_companies.link_s020_org_id   -- 삐용 org_id, FK 없음(스키마 경계)
```

`tb_s090_member010.link_s020_member_id` / `tb_s090_org010.link_s020_org_id`가 이 DB 안에 이미 있는 선례다(`SCHEMA_ANALYSIS.md` §2.2). **FK를 걸지 않는 것까지 같다.**

### 1.5 화면 3개 폐기 — 계정 관리는 삐용이다

1-3이 명시적으로 금지한다.

| 화면 | 처리 |
|---|---|
| `s0300000020` 비밀번호 재설정 요청 | **폐기** → 로그인 화면에서 삐용 해당 화면으로 링크 |
| `s0300000030` 발송 완료 | **폐기** |
| `s0300000040` 초대 수락·비밀번호 설정 | **폐기** — 초대·계정 생성은 삐용 |

디자인은 이미 완료돼 있으나 **쓰지 않는다.** 남기면 "ERP에도 계정이 있다"는 오해를 만든다.

`s0300000070` 설정 화면의 "권한 관리 준비 중" 자리도 없앤다 — ERP에 권한 관리 화면은 생기지 않는다.

### 1.6 AUTH-02 — 조직 선택 단계는 확인 필요

기존 AUTH-02는 2단계 로그인(계정 확인 → 소속 조직 선택)이고 `s0300000010p1` 조직 선택 팝업이 디자인돼 있다. 지시서 1-2 흐름에는 이 단계가 없고, 2-5는 **역할은 한 사람에 하나**라고 한다.

`tb_s020_member010`은 `org_id`를 **단일 컬럼**으로 갖는다 — 한 회원은 한 조직에 속한다. 그렇다면 선택할 것이 없다.

**판정 보류 → 회신 ⑩에서 확정.** 삐용 로그인 응답이 조직을 하나만 준다면 AUTH-02와 `s0300000010p1`은 **폐기**한다. 겸직을 지원한다면 유지한다.

## 2. 지시서가 해소한 것

### 2.1 회의실 예약 진입 경로 — 결정됨

로드맵을 막고 있던 미결이 2-11로 확정됐다.

| 질문 | 답 |
|---|---|
| 외부인 예약을 삐용 가입으로 받는가, 인증 없는 폼으로 받는가 | **인증 없는 폼.** 비회원에게 계정을 주지 않는다 |
| 신청자를 무엇으로 보는가 | **데이터**(이름·연락처). 회원이 아니다 |
| 대상 회의실 | **에스원테크 회의실만.** 입주사가 자기 회의실을 외부에 여는 것은 범위 밖 |
| 요청에서 회사 정보를 받는가 | **아니다. 서버에 고정한다** |
| 인증 없이 열리는 것 | **빈 시간 조회 + 신청 등록 둘뿐** |

**보류 해제:** `s0300500040` 외부 회의실 예약, `s0300500050` 접수 완료. 2차 유지, 승인 큐는 `s0300600020`.

**신규 BOOK-EXT-01**: 외부 예약 API는 요청 본문의 회사·건물 식별자를 무시하고 서버 상수를 쓴다. → `lib/constants.ts`(PLAT-06)에 둔다.

### 2.2 운영사 전용 구분 — 확정

2-10이 정한다. DB의 `tb_s020_module010.provider_only_yn`과 거의 일치한다(OFFICE만 `'Y'`).

| 구분 | 기능 | 화면 그룹 |
|---|---|---|
| **운영사 전용** | OFFICE 입주계약관리, BILLING 청구·수납 | `020`(계약 부분), `s0300200070` |
| 고객사용 | BOOKING 예약, TAX 세무, LEGAL 법무 | `060`, `030`, `040` |

> 2-10은 청구·수납도 운영사 전용으로 못박는다. `module010`에서 BILLING은 `provider_only_yn='N'`이라 **DB와 지시서가 어긋난다.** 청구 화면(`s0300200070`)이 고객사에게 "내 청구서"를 보여주는 화면이라면 'N'이 맞고, 운영사의 청구 관리 화면이라면 'Y'로 고쳐야 한다. → **회신 ⑧.**

### 2.3 범위(scope)는 2종뿐

`본인 것만` / `회사 전체`. **부서 범위 없음**(스키마에 값이 없다), **타사 범위 없음**. ACL-02의 스코프 헬퍼는 이 2종만 구현한다 — 3종 이상을 예상한 추상화를 만들지 않는다.

### 2.4 동작 어휘 확정

DB 저장값 `VIEW · CREATE · UPDATE · DELETE`. **`APPROVE`·`EXPORT` 금지.**

- 결재는 결재선이 정한다. 권한관리는 결재 화면을 여는 데까지만.
- 엑셀 내보내기는 브라우저가 파일을 만들어 서버 요청이 없으므로 **서버가 막을 수 없다.**

여기서 딸려 나오는 것: 기존 ACL-02가 *"목록·상세·검색·자동완성·**내보내기** 모두 예외 없이"* 스코프 헬퍼를 거치라고 했다. 이건 유효하다 — **막을 수 없는 건 권한 어휘이고, 내보낼 데이터를 서버가 스코프로 거르는 것은 그대로 해야 한다.** 둘은 다른 얘기다.

### 2.5 구독 없는 계정 — 신규 요구사항

1-7: 삐용 계정이면 누구나 ERP 로그인에 성공한다. ERP 기능을 하나도 구독하지 않은 회사 직원도 통과해 **빈 화면만 본다.**

**신규 AUTH-13**: 로그인 직후 접근 가능 화면이 0건이면 안내 문구를 띄운다 — *"이 계정은 ERP 이용 권한이 없습니다. 담당자에게 문의하세요."*

현재 `tb_s020_org_module010`은 **0행**이다. 구독이 하나도 없으므로 **지금 상태로는 모든 계정이 이 화면을 본다.**

### 2.6 단계적 시행 — 신규 요구사항

2-12: 처음부터 막지 않는다.

**신규 ACL-08**: 권한 판정에 shadow 모드를 둔다. 1단계는 막지 않고 "막았을 것"만 기록하고, 기록이 0건이 되면 2단계로 실제 차단한다. 모바일 추가 시 전환 전 전 화면 회귀 확인.

## 4. 화면코드 체계 — 회신 ③에 대한 답

지시서 2-7이 제안한 것과 ERP가 이미 쓰는 것이 다르다.

| | 삐용 제안 | ERP 현행 |
|---|---|---|
| 형식 | `S03` + 업무그룹 3 + 순번 4 = **10자** | `s030` + 업무구분 3 + 순번 4 (+ 팝업 `p{n}`) = **11자** |
| 예 | `S031000010` | `s0300200040`, `s0300200040p1` |
| 팝업 | 순번 뒤 2자리 (`S031000011`) | 접미사 `p1` |

**제안: ERP 현행을 유지한다.** 근거는 지시서 자신에 있다 — 2-7이 *"코드 문자열에서 시스템을 파싱하지 않는다. 코드는 사람이 읽는 용도지 판단 근거가 아니다"* 라고 했고, 화면 마스터가 시스템을 별도 컬럼으로 갖는다. 소속 기능도 2-6에서 **독립 항목**으로 제출한다. 그러면 코드 자릿수는 판정에 관여하지 않는다.

바꾸는 비용은 실재한다 — 27개 화면 코드가 `SWONBIZ_SCREEN_LIST.md`·`SWONBIZ_MODAL_COMPOSITION_P1.md`·`design/*.dc.html`·파일명 규칙에 이미 박혀 있다.

**다만 업무구분은 지시서의 기능 구분과 1:1이 아니다.** 이건 코드가 아니라 **매핑 표로 해결한다**:

| ERP 업무구분 | 이름 | 소속 기능(제출 항목) |
|---|---|---|
| `000` | 공통 | — (셸·로그인·대시보드·설정) |
| `010` | 기준설정 | OFFICE |
| `020` | 입주사관리 | OFFICE (계약·입주사) / BILLING (`s0300200070`) |
| `030` | 세무 | TAX |
| `040` | 법무 | LEGAL |
| `050` | 공개 화면 | 인증 없음 — 권한 대상 아님 (회신 ⑨) |
| `060` | 공간운영 | BOOKING |

`020`이 두 기능에 걸치는 것이 유일한 예외이고, 화면 단위로는 갈린다.

**`050`은 별도 처리가 필요하다.** ERP의 `050`은 업무가 아니라 **인증 여부**로 묶은 그룹이다(라우팅 미들웨어에서 인증 제외로 걸기 위함). 권한 마스터에는 등록 대상이 아니지만, 2-6은 *"마스터에 없으면 권한 체크 대상이 없어져 그냥 뚫린다"* 고 경고한다. `050`은 **의도된 공개**이므로 뚫린 것이 아니지만, 등록 제외를 명시 합의하지 않으면 나중에 누락으로 오인된다. → **회신 ⑨.**

## 5. 회신 초안

### ERP → 삐용

**① 확정된 ERP 접속 주소** — 미확정. `PROJECT.md`는 `swonbiz.com`을 적었고, `tb_s020_system010`은 `S03 / base_path=/erp`로 **경로 분기**를 등록해 뒀다. 둘은 다른 배치다. 1-8이 *"같은 상위 도메인 아래가 좋다"* 고 하므로 **`erp.swonbiz.com` 형태를 제안**하되 확정 후 회신한다.

**② 화면 목록** — 2-6 제출 항목 형식으로 작성 예정. **경로와 동작은 비워 둔다** — 2-6이 *"진실원은 코드다. 실제 라우트·엔드포인트에서 뽑아서 제출한다"* 고 했고 아직 코드가 없다. 화면 개발 후 채워서 최종 제출한다. 팝업·모달은 `SWONBIZ_MODAL_COMPOSITION_P1.md`에 이미 정리돼 있어 누락 위험은 낮다.

**③ 화면코드 체계** — 다른 체계를 쓰고 있다(4절). 현행 유지를 제안한다.
