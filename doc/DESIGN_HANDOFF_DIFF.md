### ★ 인벤토리에서 나온 사실 하나 — 시안(`.dc.html`)은 오지 않았다

핸드오프는 **마크다운 명세 + 토큰 + 로고**뿐이다. `.dc.html` 템플릿은 들어 있지 않다.
`README.md` 는 *"디자인 원본은 SwonBiz Design System 프로젝트의 `templates/` 아래에 있습니다.
문서와 원본이 어긋나면 **원본이 기준**입니다"* 라고 적고 있다.

즉 **이번 대조의 기준은 명세 문서이고, 그 명세보다 위에 있는 시안 파일은 우리에게 없다.**
저장소의 `design/erp-master-detail/*.dc.html` 은 9월 6일자 **옛** 시안이다.
문서와 시안이 어긋나는 경우를 우리 쪽에서 확인할 방법이 지금은 없다 — 보고 대상.

### 컴포넌트 원본

`README.md` 는 컴포넌트 15종을 "별도 전달"이라 적고, 개발 저장소에서는
`design/_ds/swonbiz/components/` 에 두라고 안내한다. **그 경로에 이미 있다**(15종 확인).
핸드오프 안에 중복으로 넣지 않은 것은 디자인 시스템 컴파일러의 이름 충돌 때문이라고 명시돼 있다.

### A-3-2. `s0300200030p2` 신규 입주사 등록 모달

> # ★ 이 화면은 새 원본에 없다.
>
> `02-master-detail.md` 최종 문단:
> *"계약 등록 모달(new-tenant / new-contract / renew)은 **제거되었습니다.**
> 같은 기능을 모달과 페이지 두 곳에서 관리하면 계속 어긋나므로 계약 폼 페이지로 일원화했습니다."*
>
> `01-flow.md` 흐름도에도 모달 진입 경로가 없다 — `[신규 입주사 등록]` 은 곧바로
> 계약 폼(`mode: create`)으로 간다.
>
> 보강 근거: `03-components.md` Dialog 폭 표에 **480(확인) / 720(상세) / 1000(문서)** 세 가지만 있다.
> 입력 폼 모달의 폭이 없다. 현재 코드의 모달은 720px 로, 새 원본에서 720px 은 "상세 보기" 폭이다.

#### 그래서 항목 단위 대조가 성립하지 않는다

3-1 의 실패는 "원본 7칸인데 지시문 보고 14칸을 그린 것"이었다. 이번에는 **원본이 0칸**이다.
회사·대표 입력 항목은 계약 폼 섹션 1(회사 기본정보)로 이사했고 그 화면은 페이즈 4다.

지시문 §2 — *"원본에 있는 요소를 만들어내지 않고, 원본에 있는 요소를 임의로 빼지 않는다.
판단이 필요하면 손대지 말고 보고한다"* — 에 따라 **모달의 섹션·항목 구성은 손대지 않았다.**
지우는 것도 계약 폼 섹션 1 모양으로 다시 그리는 것도 이 작업의 권한 밖이다.

우측 패널 콘텐츠 박스 686px(1440 − 사이드바 248 − 레이아웃 패딩 64 − 좌측 420 − gap 20)」.
명세의 숫자는 합이 **672px 을 넘어 마지막 열이 잘린다.** 2차 인계분의 CSS 가 나중 값이다.

### H-2. 상태 뱃지 — 시안에 없는 상태 둘을 더했다

시안 데이터에는 확정된 계약만 있어 뱃지가 「진행중 / 만료」 둘뿐이다. 저장 가능한 상태는
넷(`draft`·`confirmed`·`terminated`·`cancelled`)이고 **화면에 전부 뜬다.** 없는 둘은
계약 폼의 상태 어휘(`04-status.md`)를 그대로 썼다 — `draft`=「대기」, `cancelled`=「취소」.

★ **「만료」는 상태값이 아니라 날짜다.** `confirmed` 인데 종료일이 지나면 만료로 그린다.
상태 컬럼에 「만료」를 저장하는 자리는 없다(008 의 어휘 넷에 없다).

### H-3. 입주사 상태 판정 — 규칙을 우리가 정했다

시안은 `filters: ["active","soon"]` 을 데이터에 박아 두고 판정 규칙을 보여주지 않는다.
실제로는 **계약에서 유도**해야 한다(`deriveTenantStatus`, shared).

```
유효 계약(confirmed · 종료일 ≥ 오늘) 있음   → 계약중 (30일 이내면 + 만기 임박, 뱃지는 D-n)
성립한 적 있으나 전부 끝남                  → 종료
그 외 (계약 0건 · 임시저장/취소뿐)          → 검토중
```

★ **「검토중」을 «계약 전»으로 읽었다.** 시안에서 계약 0건인 곳(세움컴퍼니)이 검토중으로
그려져 있어 그 해석을 택했다. 임시저장만 있는 입주사를 「종료」로 넣으면 계약서를 아직
쓰는 중인 회사가 끝난 회사로 보인다. **판단이 필요했던 자리다.**

★ 「종료일 당일은 아직 계약 중」으로 뒀다(잔여 0일). 하루 일찍 끊지 않는다.

### H-4. 시안에 있는데 그대로 못 만든 것

| 항목 | 시안 | 구현 | 왜 |
|---|---|---|---|
| **[재계약]** (행 액션 · 상세 모달) | 이전 계약 값을 복사해 계약 폼을 연다 | 버튼은 있고 **안내만** | 복사 규칙이 CONT-02(항목·조건·사용자 복사, 첨부 제외, 시작일은 이전 종료일 다음 날)인데 아직 없다. 빈 폼으로 보내면 「재계약」 버튼이 신규 계약을 여는 셈이다 |

### H-5. ★ 시안이 정하지 않은 상태 하나 — **칩 결과 0건**

시안 `renderTenantList()` 는 검색 0건과 목록 0건만 다루고, **칩으로 걸러 0건인 경우는
빈 영역을 그대로 둔다.** 기본 칩이 「계약중」이라 계약중인 입주사가 하나도 없으면
목록이 통째로 비어 보인다 — 지금 개발 DB 가 정확히 그 상태다.

**시안대로 두었다**(빈 영역). 안내 문구를 지어내지 않았다. 디자인 확인이 필요한 자리다.

### H-6. 데이터 쪽에서 갈린 것 — 화면과 무관하지만 기록해 둔다

- **`is_representative` 는 「여부」가 아니라 코드다** — `'C'` 대표 / `'M'` 직원(`RES_TP` 어휘).
  컬럼 이름과 주석이 boolean 처럼 읽힌다. 레거시 앱이 `=== "C"` 로 비교한다
- **화면 「업태」 → `business_type`, 화면 「업종」 → `business_item`(종목)** 으로 맞췄다.
  DB 주석과 사업자등록증 용어 기준이다. **판단이 필요했던 자리다**
- **대표자 자택 주소는 새 컬럼 3개**(`011`)에 넣었다. `address` 는 사업장 주소 자리이고
  거기 넣으면 세금계산서·삐용에 대표자 집 주소가 나간다(§F-6 ① 참조)
- **명부에서 뺀 사람을 지우지 않는다.** `tb_s080_reservations` 가 `ON DELETE SET NULL` 로
  참조해서, 지우면 그 사람이 잡은 예약의 예약자가 조용히 비워진다. `status='inactive'` 로 둔다
