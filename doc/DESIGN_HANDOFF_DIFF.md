### ★ 인벤토리에서 나온 사실 하나 — 시안(`.dc.html`)은 오지 않았다

핸드오프는 **마크다운 명세 + 토큰 + 로고**뿐이다. `.dc.html` 템플릿은 들어 있지 않다.
`README.md` 는 *"디자인 원본은 SwonBiz Design System 프로젝트의 `templates/` 아래에 있습니다.
문서와 원본이 어긋나면 **원본이 기준**입니다"* 라고 적고 있다.

즉 **이번 대조의 기준은 명세 문서이고, 그 명세보다 위에 있는 시안 파일은 우리에게 없다.**
저장소의 `design/erp-master-detail/*.dc.html` 은 9월 6일자 **옛** 시안이다.
문서와 시안이 어긋나는 경우를 우리 쪽에서 확인할 방법이 지금은 없다 — 보고 대상.

### 컴포넌트 원본

`README.md` 는 컴포넌트 15종을 "별도 전달"이라 적고, 개발 저장소에서는
`design/_ds/swonbiz/components/` 에 두라고 안내한다. **그 경로에 이미 있다**(15종 확인).
핸드오프 안에 중복으로 넣지 않은 것은 디자인 시스템 컴파일러의 이름 충돌 때문이라고 명시돼 있다.

### A-3-2. `s0300200030p2` 신규 입주사 등록 모달

> # ★ 이 화면은 새 원본에 없다.
>
> `02-master-detail.md` 최종 문단:
> *"계약 등록 모달(new-tenant / new-contract / renew)은 **제거되었습니다.**
> 같은 기능을 모달과 페이지 두 곳에서 관리하면 계속 어긋나므로 계약 폼 페이지로 일원화했습니다."*
>
> `01-flow.md` 흐름도에도 모달 진입 경로가 없다 — `[신규 입주사 등록]` 은 곧바로
> 계약 폼(`mode: create`)으로 간다.
>
> 보강 근거: `03-components.md` Dialog 폭 표에 **480(확인) / 720(상세) / 1000(문서)** 세 가지만 있다.
> 입력 폼 모달의 폭이 없다. 현재 코드의 모달은 720px 로, 새 원본에서 720px 은 "상세 보기" 폭이다.

#### 그래서 항목 단위 대조가 성립하지 않는다

3-1 의 실패는 "원본 7칸인데 지시문 보고 14칸을 그린 것"이었다. 이번에는 **원본이 0칸**이다.
회사·대표 입력 항목은 계약 폼 섹션 1(회사 기본정보)로 이사했고 그 화면은 페이즈 4다.

지시문 §2 — *"원본에 있는 요소를 만들어내지 않고, 원본에 있는 요소를 임의로 빼지 않는다.
판단이 필요하면 손대지 말고 보고한다"* — 에 따라 **모달의 섹션·항목 구성은 손대지 않았다.**
지우는 것도 계약 폼 섹션 1 모양으로 다시 그리는 것도 이 작업의 권한 밖이다.

### G-9. 섹션 3 열 폭 — **시안보다 좁혔다.** 이메일에 「직접입력」이 들어갔기 때문이다 (2026-09-19)

시안 `s0300200040.html` 의 섹션 3 은 이메일 칸에 **id + @ + 도메인 Select** 셋만 넣는다.
2026-09-19 에 **「직접입력」**을 더하면서(섹션 1 에는 원래 있었다) 네 번째 칸이 생겼고,
기존 폭에서는 id 칸이 눌려 입력을 읽을 수 없었다.

| 열 | 시안 | 구현 | 비율 |
|---|---|---|---|
| 성명 | `minmax(150px, 0.9fr)` | **100px** | 67% |
| 연락처 | `minmax(180px, 1fr)` | **152px** | 84% |
| 이메일 | `minmax(300px, 1.7fr)` | **`minmax(400px, 1fr)`** | 남는 폭 전부 |
| 대표자 | `80px` | **56px** | 70% |
| 비고 | `minmax(160px, 1fr)` | **160px** (고정) | fr 제거 |

**`fr` 을 이메일만 갖는다.** 다른 열이 같이 늘면 남는 폭이 나뉘어 「직접입력」일 때
id 칸이 다시 눌린다. 비고에서 `fr` 을 뺀 것도 같은 이유다 — 지시에 없었지만
「남는 폭을 전부 이메일에」를 지키려면 필요했다.

**지시와 다르게 한 곳 하나** — 성명은 「현재의 50%」(75px) 요청이었는데 **100px(67%)**
로 멈췄다. 75px 이면 글자 영역이 31px 이라 4글자(56px)가 잘린다. 같은 지시의
「성명 4글자가 다 보여야 한다」와 충돌해 그쪽을 택했다. 대신 이 표의 입력 좌우 여백을
12px → **8px** 로 줄여 100px 안에서 62px 을 확보했다(섹션 1·2 의 입력은 12px 그대로다).

계산 확인(그리드 1062px = formWrap 1120 − 섹션 패딩 56 − 테두리 2):

| 확인 | 결과 |
|---|---|
| 성명 글자 영역 | 62px ≥ 4글자 56px |
| 연락처 글자 영역 | 114px ≥ `010-0000-0000` 109px |
| 이메일 열 | 442px |
| id 칸 (목록 선택) | 280px |
| id 칸 (**직접입력**) | 154px ≥ 바닥 110px |
| 행 최소 폭 | **1020px** (이전 1022px) ≤ 그리드 1062px → 가로 스크롤 없음 |

★ 헤더(`.userHead`)와 행(`.userRow`)은 **한 선택자**에서 열을 정의한다. 한쪽만 고치면
조용히 어긋난다. 1행(대표자 미러링)의 읽기 전용 도메인 표시와 2행 이후의 Select,
「직접입력」 칸이 전부 `.mailFixed`·`.mailDomain` 한 값(120px)을 쓴다 — 인라인
`width: 140` 두 곳을 CSS 로 걷어냈다.

### G-10. 섹션 3 대표자 체크박스 — **전부 비활성.** 명세 두 줄이 충돌해 한쪽을 택했다 (2026-09-19)

`03-contract-form.md` 섹션 3 이 서로 맞지 않는 말을 한다:

| 위치 | 문장 |
|---|---|
| 「1행 — 자동 채움 + ReadOnly」 | 선택 체크박스 체크 고정(해제 불가), **대표자 체크 고정**, 삭제 비활성 |
| 「대표자 체크박스」 | 1명만 선택 — **라디오처럼 동작**합니다(체크 시 나머지 해제) |

둘 다 지킬 수 없다. 1행이 고정인데 2행을 체크하면 라디오 규칙상 1행이 풀린다.

**「1행 고정」을 택했다.** 근거는 데이터 쪽이다 — 1행은 섹션 1 「대표자」를 실시간
미러링하는 자리이고(같은 명세), 회사의 대표자가 곧 그 사람이다. 대표자를 바꾸는 방법은
섹션 3 에서 고르는 것이 아니라 **섹션 1 의 대표자를 바꾸는 것**이다.

그래서 **모든 행의 대표자 체크박스가 비활성**이다. 1행만 잠그고 2행 이후를 열어 두면
2행을 체크하는 순간 1행이 풀려 「고정」이 깨진다.

**함께 고친 것 — 화면과 저장이 갈리던 자리.** 예전에는 저장된 `is_representative` 로
`repIndex` 를 잡아 화면에서 고를 수 있었다. 그래서 **1행에 대표자 이름이 보이는데 체크는
3행에 있는** 상태가 만들어졌다(1행 값은 섹션 1 에서 덮어쓰므로). 이제 저장도
`isRepresentative: index === 0` 이다. `repIndex` 상태와 `onRep` 콜백은 걷어냈다.

> ⚠️ **기존 데이터에 영향이 있다.** 저장된 대표자가 1행이 아닌 입주사를 계약 폼에서
> 저장하면 **대표자가 1행으로 옮겨진다.** 지금 데이터에서는 해당 사례가 없다.

★ **「만료」는 상태값이 아니라 날짜다.** `confirmed` 인데 종료일이 지나면 만료로 그린다.

### H-3. 입주사 상태 판정 — 규칙을 우리가 정했다

시안은 `filters: ["active","soon"]` 을 데이터에 박아 두고 판정 규칙을 보여주지 않는다.
실제로는 **계약에서 유도**해야 한다(`deriveTenantStatus`, shared).

```
유효 계약(confirmed · 종료일 ≥ 오늘) 있음   → 계약중 (30일 이내면 + 만기 임박, 뱃지는 D-n)
성립한 적 있으나 전부 끝남                  → 종료
그 외 (계약 0건 · 임시저장/취소뿐)          → 검토중
```

★ **「검토중」을 «계약 전»으로 읽었다.** 시안에서 계약 0건인 곳(세움컴퍼니)이 검토중으로
그려져 있어 그 해석을 택했다. 임시저장만 있는 입주사를 「종료」로 넣으면 계약서를 아직
쓰는 중인 회사가 끝난 회사로 보인다. **판단이 필요했던 자리다.**

★ 「종료일 당일은 아직 계약 중」으로 뒀다(잔여 0일). 하루 일찍 끊지 않는다.

★ **정확히 하자면** — 「확정된 계약은 폼도 읽기 전용」은 절반만 맞다. `confirmed` 는

- 행이 `<button>` → **`<a>`(`next/link`)** 가 됐다. 버튼 안에 링크를 넣을 수 없고,

- `.row` CSS 에 `color: inherit; text-decoration: none` 을 더했다. 버튼 리셋에 기대고

- `[재계약]` 은 `stopPropagation` 에 더해 **`preventDefault`** 가 필요해졌다. 행이
  링크가 된 뒤로는 전파를 막아도 링크 기본 이동이 남는다

**`ContractDetailModal.tsx` 는 지우지 않았다.** 지금은 아무 데서도 열지 않는 죽은
코드이고, 파일 머리말에 그렇게 적어 두었다. 첨부 · 상태 이력 · 청구가 붙으면 목록에서

### H-9. 계약 상태 표시명을 **코드 테이블에서 가져온다** (2026-09-20)

**무엇이 시안과 다른가**

| 자리 | 시안 · 종전 구현 | 지금 |
|---|---|---|
| 계약 목록 뱃지 | 대기 / 진행중 / 종료 / 취소 | **계약대기 / 계약중 / 계약종료 / 계약취소** |
| 계약 폼 헤더 보조 안내 | 계약 확정 / 취소 / `(일자) 종료` | **계약중 / 계약취소 / `(일자) 계약종료`** |
| 헤더 버튼 `[종료]` | 종료 | **계약종료** |
| 종료 확인 모달 확정 버튼 | 종료 처리 | **계약종료** |
| 종료·취소 뒤 토스트 | 「종료 처리했습니다」 | **「계약종료 처리했습니다」** |

출처는 코드 `CONTRACT_ST` / `use_tp='000'` 4행이다. 화면이 이름을 들고 있지 않는다.

**왜**

같은 상태를 화면마다 다른 이름으로 부르고 있었다 — 목록은 `confirmed` 를 「진행중」,
폼 헤더는 「계약 확정」이라고 했다. 운영자가 목록에서 「진행중」을 보고 폼을 열면
「계약 확정」이 뜬다. 이름을 코드 테이블 한 곳으로 모으면 기준관리 화면이 생겼을 때
**DB 에서 한 번 고치면 네 자리가 같이 따라간다.**

**일부러 남긴 것 — 넷**

1. **「만료」는 코드에 없다.** `confirmed` 인데 종료일이 지난 계약을 화면이 부르는
   이름이고, 저장된 상태값은 그대로 `confirmed` 다. 코드에 넣으면 저장되지 않는
   상태가 코드 목록에 끼어 **상태가 다섯 개인 것처럼** 보인다. 판정은 종전대로
   `contractStatusLabel()` 이 날짜로 한다.
2. **`[계약확정]` · 확인 모달의 `[확정]` 은 그대로 뒀다.** `confirmed` 의 코드명은
   「계약중」인데 그것은 **상태를 가리키는 이름이지 동작이 아니다.** 버튼에
   「계약중」이라고 적으면 무엇을 하는 버튼인지 읽히지 않는다. 넷 중 이 하나만
   이름과 동작이 어긋난다 — `cancelled`=계약취소, `terminated`=계약종료 는 둘 다 된다.
3. **확인 모달의 제목·설명은 그대로 뒀다.** 「계약을 종료하시겠습니까?」의 *종료*는
   문장 안의 **동사**다. 상태 이름으로 바꾸면 「계약을 계약종료하시겠습니까?」가 된다.
4. **입주사 카드 뱃지는 연결하지 않았다.** → 아래.

> ⚠️ **입주사 카드 뱃지는 계약 상태가 아니다.** 그 뱃지의 어휘는
> 「계약중 · D-9 · 검토중 · 종료」이고 `deriveTenantStatus()`(shared)가 **계약들로부터
> 유도**한다. `CONTRACT_ST` 4행 중 대응하는 것이 하나도 없다 —
> 「계약중」은 글자만 같고, 「검토중」·「D-9」은 저장되는 상태가 아니며,
> 입주사의 「종료」를 `terminated` 의 코드명 「계약종료」로 바꾸면 **같은 화면의 필터 칩
> `[종료]` 와 뱃지가 어긋난다.** 계약 어휘와 입주사 어휘는 별개로 둔다.
> 묶어야 한다면 그것은 표시명 교체가 아니라 **입주사 상태 어휘를 새로 정하는 일**이고,
> 디자인팀 판단이 필요하다. §H-10 에 올렸다.

**코드를 못 받았을 때** — `/codes` 는 실패해도 화면을 여는 구조다(`codesRes.ok ? … : []`).
그때 뱃지가 빈 칸이 되면 상태를 읽을 수 없는 목록이 되므로,
`features/contracts/contract-status-name.ts` 가 DB 와 같은 값의 기본값을 깔고 코드가
오면 덮는다. 기본값에도 없는 값이면 **코드값 자체**(`draft` 등)를 보여준다 — 틀린
이름보다 낫다. 정본은 어디까지나 코드 테이블이다.

### I-1. 인쇄 CSS — 숨기는 방식을 바꿨다 (★ 바꾸지 않았으면 뒷장이 잘린다)

**명세**는 숨길 것을 태그·속성으로 열거한다:

```css
header, section, [data-sidebar], [data-print-hide] { display: none !important; }
[data-overlay]    { position: static !important; }
[data-print-root] { height: auto !important; }
```

**구현**은 모달을 `document.body` 로 **포털**하고, 인쇄할 때 **body 의 다른 자식만** 지운다:

```css
body[data-printing='contract-doc'] > *:not([data-print-portal]) { display: none !important; }
```

**왜 — 두 가지**

1. **열거는 빠뜨린다.** 화면이 하나 늘 때마다 이 목록을 고쳐야 하고, 빠뜨리면 계약서 뒤에
   사이드바가 한 장 더 인쇄된다. 인쇄해 보기 전에는 모른다.
2. **★ 절대위치는 페이지 나눔을 죽인다.** 중간에 «전부 감추고 문서만 절대위치로 끌어내는»
   방식을 썼다가 **전대차계약서가 3장 분량인데 2장만 인쇄돼 뒷부분이 통째로 사라졌다.**
   절대위치 요소는 흐름에서 빠지고, 흐름에서 빠지면 브라우저가 나눌 높이를 잃는다.
   포털은 문서를 **정상 흐름**에 두므로 이 문제가 생기지 않는다.

명세의 의도(모달 껍데기를 걷어내고 문서만 남긴다)는 그대로다. `data-scroll` ·
`data-seal` · `page-break-inside: avoid` 도 명세 그대로 쓴다.

### I-2. 비활성 탭을 `display:none` 하지 않고 **아예 렌더하지 않는다**

구현은 선택한 문서만 마운트한다. 결과는 같지만, 숨긴 문서가 인쇄에 섞일 **여지 자체**가
없어진다 — 인쇄 규칙이 `visibility` 나 `display` 를 잘못 되살리는 사고를 막는다.
검증에서 «비선택 문서가 DOM 에 0개»로 확인한다.

### I-7. 용지 여백을 **0 으로** 두고 여백을 문서 안쪽으로 옮겼다

**왜** — 크롬은 용지 여백 안에 「날짜 · 제목 · about:blank · 1/2」를 자기 마음대로 그린다.
계약서에 그게 찍히면 그 종이는 못 쓴다. **여백이 0 이면 그릴 자리가 없어 사라진다** —
CSS 로 되는 유일한 방법이다.

명세의 `@page { margin: 15mm }` 대신:

```css
@page          { size: A4 portrait; margin: 0; }       /* 이용계약서 */
@page sublease { size: A4 portrait; margin: 14mm 13mm; } /* 전대차 */
[data-doc-page='usage']    { padding: 12mm 13mm; }
[data-doc-page='sublease'] { padding: 0; page: sublease; }
```

**전대차만 `@page` 여백을 쓰는 이유** — 3장짜리라 **2·3장에는 padding 이 오지 않는다**
(padding 은 흐름의 시작과 끝에만 붙는다). 매 장에 여백을 주려면 `@page` 여백이어야 한다.
이름 붙인 페이지가 실제로 적용되는지 확인했다(여백을 60mm 로 키우니 3장 → 6장).

> ⚠️ **그래서 전대차에는 머리글·바닥글이 뜰 수 있다.** 여백이 있으면 크롬이 그릴 자리가
> 생긴다. 이용계약서도 브라우저 설정이 CSS 를 이기는 경우가 있다.
> 그래서 **모달 상단에 「인쇄 대화상자에서 머리글·바닥글을 꺼 주세요」 안내를 한 줄 두었다**

이메일 아이디 칸은 **영문·숫자와 `.` `_` `-` 만** 남기고 나머지는 입력되는 즉시 떨어진다.

- 막는 것: **한글 · 공백 · `@`** 와 그 밖의 기호
- 허용한 것: **`.` `_` `-`** — 「영문·숫자만」을 글자 그대로 적용하면
  `hong.gil-dong@…` 같은 **실재하는 주소를 입력할 수 없다**
- 뺀 것: `+`(`user+tag@…`) — 개인 메일에서는 흔하지만 회사 대표 주소에서는 드물다.
  필요하면 `maskEmailId` 의 정규식 한 곳만 고치면 된다

검증이 아니라 마스크인 이유: 아이디 칸과 도메인 칸을 합쳐 저장하므로(`joinEmail`)
깨진 주소가 그대로 DB 에 남고, 그 회사에는 아무것도 보낼 수 없게 된다. 저장 직전에
막으면 이미 여러 칸을 채운 뒤라 되돌리기가 번거롭다.

★ 섹션 1 과 섹션 3(사용자 행)에 **같은 마스크**를 걸었다. 같은 종류의 칸이 서로 다르게
굴면 안 된다.

### J-3. 이용계약서 제목에 「(비 제출용)」을 붙였다 — 전대차에는 붙이지 않는다

시안 `06-contracts.md` 의 제목은 「이 용 계 약 서」다. 여기에 꼬리표를 더했다:

```
이 용 계 약 서 (비 제출용)      ← 우리와 입주사 사이의 문서
전 대 차 계 약 서                ← 세무서 제출용. 그대로 둔다
```

두 문서가 비슷하게 생겨서 **창구에 잘못 내는 일**을 제목에서 막는다. 제출용이 어느
쪽인지는 종이 한 장을 보는 사람이 알 수 있어야 한다.

**★ 제목 본문과 같은 크기로 잇지 않았다 — 그러면 한 줄을 넘는다**

「이 용 계 약 서 (비 제출용)」을 40px · 자간 0.15em 으로 한 줄에 쓰면 문서 폭 714px 를
넘겨 **두 줄이 된다.** 두 줄이 되면 제목 높이가 그만큼 늘고, 이용계약서는 이미 한 장을
거의 채운 상태(§I-8)라 **두 장이 될 수 있다.**

그래서 꼬리표를 `<span data-doc-title-note>` 으로 떼어 **0.5em** 으로 이어 붙였다.
작은 글자는 줄 상자 높이를 바꾸지 않으므로 **문서 길이가 1px 도 늘지 않는다.**

| | 제목 높이 | 줄 수 | 넘침 | 장수 |
|---|---|---|---|---|
| 이용계약서 (붙이기 전) | 56px | 1 | 없음 | **1장** |
| 이용계약서 (붙인 뒤) | 56px | 1 | 없음 | **1장** |
| 전대차 (변화 없음) | 56px | 1 | 없음 | **3장** |

크롬 헤드리스로 실제 인쇄(`Page.printToPDF`)해 센 값이다. 인쇄 화면에서는 제목이
28px 로 줄고 꼬리표도 `em` 이라 14px 로 함께 줄어든다 — 문서 채움 **0.91장**.

★ 자간은 꼬리표에서 0.02em 으로 되돌렸다. 제목의 0.15em 을 물려받으면 괄호가 글자에서
떨어져 「( 비 제출용 )」처럼 읽힌다.

### J-4. 호실 셀렉트가 **입주 현황**으로 한 번 더 걸러진다 (2026-09-20)

§G-2 는 「계약구분으로 거른다」까지였다. 시안(`03-contract-form.md` 섹션 2)도 거기까지다.
여기에 입주 현황을 더했다:

| 계약구분 | 0곳 | 1곳 | 2곳 이상 |
|---|---|---|---|
| 비상주(VR) | 보인다 | **안 보인다** | 안 보인다 |
| 그 외 | 보인다 | 보인다 — **「Room 1 (에스원3DP)」** | 안 보인다 |

비상주는 **주소만 쓰는 계약**이라 한 호실에 두 회사가 들어가면 같은 주소로 두 사업자가
등록된다. 그 외 구분은 자리를 나눠 쓸 수 있어 1곳까지 남기되, **누가 쓰고 있는지 이름을
함께 보여준다** — 모르고 겹치는 것과 알고 겹치는 것은 다르다.

**입주로 세는 것**: 계약중(`confirmed`) + 계약대기(`draft`). 종료·취소는 세지 않는다 —
그 호실은 놓아 준다. 「살아 있는 계약」의 정의는 계약호실(§p3)과 **같은 목록 하나**다
(`OCCUPANCY_LIVE_STATUSES === ROOM_LIVE_STATUSES`).

**★ 자기 계약은 세지 않는다.** 세면 자기 계약을 열어 그대로 저장할 때 자기 호실이
목록에서 사라지고, 빈 줄로 조용히 저장된다.

★ 같은 계약 안에서 **같은 호실을 두 줄에** 넣는 것도 막았다(시안에 규칙 없음). 두 줄이면
금액이 두 번 잡히고 어느 줄이 진짜인지 알 수 없다.

★ 판정은 `@swonbiz/shared/domain/space-occupancy` 한 곳이고 **서버가 같은 함수로 다시
본다**(`POST`·`PATCH /contracts` → 409). 셀렉트에서 사라진 호실이 API 로는 들어가면
막은 의미가 없다.

## K. 재계약 · 계약 등록 3모드 (CONT-01 · CONT-02) — 2026-09-21

정본 규칙은 `packages/shared/src/domain/contract-renewal.ts` 이고, 시험은
`contract-renewal.test.ts`(19건) · `scripts/verify-4-6.js`(왕복 15항목)다.

### K-1. 세 모드는 **질의 하나로** 갈린다

라우트는 계속 `/contracts/[id]` 하나다. 신규 작성(`/contracts/new`)에서 질의만 다르다.

| 모드 | 주소 | 채워지는 것 |
|---|---|---|
| 신규 입주사 | `/contracts/new` | 빈 폼. **첫 저장이 입주사를 만든다** |
| 신규 계약 | `/contracts/new?companyId=` | 회사만 |
| **재계약** | `/contracts/new?renewFrom=` | 이전 계약의 조건·금액 |

★ `renewFrom` 은 `companyId` 를 **스스로 정한다.** 재계약은 같은 회사의 다음 계약이라
따로 받을 이유가 없고, 둘이 어긋나면 어느 쪽이 맞는지 알 수 없다. 서버도 이어받을 계약이
정말 그 회사 것인지 다시 본다(`rejectRenewal` → 400).

### K-2. 무엇을 이어받고 무엇을 새로 받는가

**이어받는다** — 호실 줄(금액째) · 납부방법 · 접근경로 · 계약호실 · 건물.

**새로 받는다** — 계약일자는 **오늘**, 시작일은 **이전 계약 종료일의 다음 날**,
기간은 이전과 같게, 종료일은 **다시 계산**.

★ **시작일은 시안 주석(「이전 종료일 다음 날」)과 같다.** 2026-09-21 처음 붙일 때는
오늘로 뒀다가 같은 날 되돌렸다 — 이어지는 계약이라 하루도 비지 않고 겹치지도 않아야 하고,
오늘로 두면 **만기 전에 미리 재계약할 때 아직 살아 있는 계약의 기간 위에 새 계약이 겹쳐
시작한다.** 두 계약이 같은 호실을 겹쳐 드는 것은 §K-3 이 허용하는 상태라 저장은 되고,
그래서 **아무도 눈치채지 못한 채 기간이 겹친 계약이 남는다.**

★ **기본값일 뿐이다 — 운영자가 화면에서 바꾼다.** 시작일 칸은 잠기지 않는다.

★ 이전 종료일을 읽을 수 없으면 **오늘로 떨어진다.** 시작일은 필수값이라 빈 칸으로 두면
운영자가 왜 비었는지 모른 채 저장이 막힌다.

★★ 종료일을 넘길 때 **`YYYY-MM-DD` 로 정규화한다**(`renewalSourceOf` → `toDateInput`).
응답의 날짜는 `2026-12-31T15:00:00.000Z` 로 오고, 앞 10자를 자르면 KST 기준 **하루 앞선
날짜**가 된다. `buildRenewalSeed` 는 그런 값을 받아 주지 않고 오늘로 떨어뜨린다 —
조용히 하루 밀린 시작일을 만드는 것보다 낫다.

★ **종료일을 이어받지 않는다.** 새 시작일과 기간에서 다시 계산되는 값이라, 이어받으면
그 순간 이전 계약의 종료일이 새 계약에 박힌다.

★ **특기사항은 이어받지 않는다.** 그 계약 당시의 사정을 적은 자리다. 첫 줄의 할인 문구는
어차피 금액에서 다시 만들어진다.

★ **회사 정보·구성원·첨부는 「복사」가 아니다.** 계약이 아니라 **회사에 붙어 있어서**
같은 회사를 열면 그대로 따라온다(3-4). CONT-02 의 「사용자 목록 복사」는 그 구조에서
저절로 성립한다 — 복사 코드가 없는 것이 정상이다.

### K-3. ★★★ 이전 계약을 «자기»로 본다 — 이 기능의 본체

> **★ 2026-09-21 개정 — 이제 확정하는 순간 이전 계약이 닫힌다(§L-1).** 아래 문단은
> 「닫히기 전까지」의 사정을 적은 것이고, 그 구간은 여전히 존재한다 — 재계약 폼을
> 열어 두고 **아직 확정하지 않은 동안**이다. `selfContractIds` 는 그대로 필요하다.

**이전 계약은 재계약을 확정하기 전까지 살아 있다.** 폼을 열어 값을 채우는 내내 이전
계약은 계약중이고, 호실도 계약호실도 계속 잡고 있다.

그 결과 **저장 검증이 도는 시점에 두 계약이 같은 계약호실과 같은 호실을 동시에 들고
있는 것이 정상**이다.
이전 계약을 자기로 보지 않으면 재계약이 **자기 이전 계약과 부딪혀 저장이 막힌다** —
계약호실 중복(§p3)에서 한 번, 호실 입주 계산(§J-8)에서 또 한 번. 비상주는 한 호실에
한 회사라 특히 그렇다.

그래서 「자기」가 하나가 아니게 됐다. 목록을 만드는 자리는 `selfContractIds` 하나이고
**화면과 서버가 같이 부른다.**

| 상황 | 자기로 보는 계약 |
|---|---|
| 신규 | 없음 |
| 저장된 계약 수정 | 자기 자신 |
| **저장 전 재계약** | **이전 계약** (자기 ID 가 아직 없다) |
| **저장된 재계약 수정** | **자기 자신 + 이전 계약** |

이에 맞춰 `findRoomConflict` 와 `occupancyBySpace` 의 셋째 인자가 `string | null` 에서
`readonly string[]` 로 바뀌었다.

★ **예외가 남에게 새지 않는다.** 다른 회사가 같은 계약호실·같은 비상주 호실을 쓰려 하면
그대로 409 다(`verify-4-6.js` 5번이 그 자리다).

★ 저장된 재계약은 **본문이 보낸 값이 아니라 저장된 `renewed_from_contract_id`** 로
자기 목록을 만든다. 본문을 믿으면 아무 계약이나 자기라고 주장해 남의 계약호실 위에
덮어쓸 수 있다.

### K-4. 화면에 남긴 것

- 제목이 **「재계약」**이다. 「계약 등록」으로 보이면 값이 미리 채워진 이유가 화면 어디에도
  없고, 운영자가 남의 값이 섞였다고 의심한다
- 저장 전에는 「이전 계약의 조건을 이어받았습니다 — **시작일은 이전 종료일 다음 날**이고,
  이전 계약은 그대로 유지됩니다」. 시작일이 오늘이 아닌 이유를 말하지 않으면 운영자가
  날짜가 잘못 채워졌다고 읽는다
- 저장 뒤에는 그 계약으로 가는 링크(**「이어받은 이전 계약 보기」**). DB 에만 있으면
  운영자는 이 계약이 어디서 왔는지 알 방법이 없다
- 목록 행의 `[재계약]` 이 이 경로로 연결됐다. 행이 이미 `<Link>` 라 중첩 링크를 쓸 수 없어
  `router.push` 로 옮기고 바깥 링크의 기본 이동을 막는다(§H-4 의 「안내만」이 닫혔다)

## L. 재계약 확정으로 이전 계약 종료 · 기간 만료 확인 — 2026-09-21

정본 규칙은 `contract-renewal.ts`(재계약) · `contract-status.ts`(만료)이고, 시험은
`contract-renewal.test.ts`(34건) · `contract-status.test.ts`(44건) ·
`tenant-status.test.ts`(17건) · `scripts/verify-4-6.js`(왕복 30항목)다.

### L-1. ★★★ 확정 한 번에 **두 계약**의 상태가 바뀐다

재계약을 **확정**하면 같은 트랜잭션에서:

| | 결과 |
|---|---|
| 새 계약 | `confirmed` 로 저장 |
| 이전 계약 | `terminated` · 종료일자 = **이전 계약의 원래 종료일** · 사유 「재계약으로 계약 종료」 |

**하나만 바뀌고 멈추면** 두 계약이 동시에 계약중이거나(호실이 이중으로 잡힌다) 둘 다
끝난 상태(입주사에 유효 계약이 없다)가 된다. 그래서 순서를 규칙으로 고정했다 —
**검사가 전부 끝난 뒤에 쓰기가 시작된다.** 서류 부족처럼 막히는 경우는 쓰기 전에
돌려보내고, 쓰기 도중에 던지면 `withCompanyScope` 가 ROLLBACK 한다.

★ **종료일자가 오늘이 아니다.** 만기 전에 미리 재계약하면 오늘을 넣는 순간 이전 계약이
실제보다 짧았던 것으로 남고, 그 날짜가 정산에 쓰인다.

★ **이미 종료·취소된 계약은 건드리지 않는다**(`closesPrevious`). 다시 닫으면 종료일자와
사유가 덮여서 원래 왜 끝났는지가 사라진다. 종료된 계약을 이어받는 것은 정상 경로다.

★ **상태 이력이 두 계약 모두** 남는다 — 새 계약은 `null → confirmed`, 이전 계약은
`confirmed → terminated`.

★ 응답에 `closedPrevious` 를 싣는다. 화면이 「이전 계약이 종료됐습니다」를 말할 근거다.

### L-2. ★ 재계약 화면에는 **[임시저장] 이 없다**

재계약은 입주사가 **계약 의사를 밝힌 것**이라 작성 중 상태가 필요 없다. 임시저장을 두면
「아직 계약이 아닌 재계약」이 생기고, 그동안 이전 계약은 닫히지 않은 채 두 계약이 같은
호실을 들고 있게 된다 — 아무도 그걸 정리하지 않는다.

그래서 **이전 계약을 닫는 시점도 하나**로 정해진다: 확정하는 순간.

★ 섹션 4 의 가등록 안내 뒷문장이 재계약에서는 달라진다(`draftable`). 「그때까지는
[임시저장] 으로 둡니다」를 그대로 띄우면 **없는 버튼을 누르라고 말하는 셈**이고, 안내와
화면이 어긋나면 운영자는 안내를 아예 믿지 않게 된다. 실제로 그렇게 나올 뻔했다.

★ 재계약하기로 했다가 **안 하게 되면 [계약종료]** 로 처리한다. 확정된 계약이라 계약취소는
없다(`confirmed → cancelled` 전이가 없다 — 기존 규칙 그대로다).

### L-3. ★★ 시작일은 **이전 종료일 다음 날부터** — 종료일 당일도 막는다

씨앗이 다음 날을 기본값으로 넣지만(§K-2) 운영자가 바꿀 수 있으므로 검사가 따로 있다.
**화면과 서버가 같은 함수**(`rejectRenewalStart`)를 보고, 서버는 등록·수정 **양쪽**에서
본다 — 등록에서만 보면 저장 뒤에 시작일을 끌어올려 하루 겹침을 만들 수 있다.

★★ 겹치면 두 계약이 같은 날 같은 호실을 동시에 들고, 그 상태는 §K-3 의 재계약 예외가
**일부러 허용하는 모양**이라 중복 판정에 걸리지 않는다. 즉 **막지 않으면 아무도 못
알아챈다.** 비는 기간은 막지 않는다 — 한참 뒤부터 다시 시작하는 재계약이 있다.

### L-4. 기간 만료 — **운영자가 확인하고 닫는다. 배치는 없다**

종료일이 지나도 저장된 상태는 `confirmed` **그대로**다. 자동 종료 배치를 만들지 않았다 —
시스템이 먼저 닫아 버리면 아직 이야기 중인 계약이 끝난 것으로 보이고, 되돌리는 전이가
없어 **재계약으로만 복구할 수 있다.**

★★★ 그래서 **만료된 계약도 호실을 계속 잡는다.** 운영자가 입주사에게 재계약 의사를
확인하는 동안 호실이 다른 회사에 넘어가면 안 된다. `ROOM_LIVE_STATUSES` 가 상태만 보는
것이 그 약속이고, **자동으로 풀지 않는 것이 규칙이지 실수가 아니다.**

**칩을 나눴다** — 시안에 없던 칩을 하나 더한 자리다.

| 칩 | 뜻 |
|---|---|
| 기간 만료 | 종료일이 지났는데 **아직 계약중** — 할 일이 남았다 |
| 종료 | 종료 처리가 끝났다 — 할 일이 없다 |

예전에는 한 칩이었다. 자동 종료가 없으니 **처리한 곳과 안 한 곳이 섞여** 운영자가 어디를
봐야 하는지 알 수 없었다.

★★ **칩은 더해진다.** 만료가 붙었다고 「만기 임박」에서 빼면 임박으로 거르는 운영자가 그
회사를 못 본다 — 한 번 그렇게 만들었다가 칩 개수가 줄어드는 것으로 드러났다.
뱃지는 하나뿐이라 **할 일 쪽**(「기간 만료」)을 보여준다.

★ 만료 판정은 `isContractExpired` **한 곳**이다 — 계약 행의 「만료」 뱃지도 같은 함수를
본다. 두 벌이면 행은 만료라는데 칩에는 안 뜬다.

★ 만료는 **코드 테이블에 없다.** 저장되지 않는 이름이 `CONTRACT_ST` 에 끼면 상태가 다섯
개인 것처럼 보인다.

### L-5. [계약종료] 모달의 기본값

| | 기본값 |
|---|---|
| 종료일자 | 만료된 계약이면 **원래 종료일**, 아니면 오늘 |
| 사유 | 만료된 계약이면 「계약기간 만료로 계약 종료」, 아니면 빈 칸 |

★ 뒤늦게 닫는 것이라 오늘을 넣으면 계약이 실제보다 길었던 것으로 남는다.
**실제 퇴실일이 다르면 운영자가 바꾼다 — 기본값일 뿐이다.**

★ 아직 안 끝난 계약을 중도에 닫는 것이면 사유를 지어내지 않는다.

### L-6. ★★★ 고친 버그 — 날짜를 **UTC 로 세고 있었다**

만료 판정을 붙이다 드러났다. pg 는 `date`/`timestamp` 를 **로컬 자정의 Date** 로 주고 그
값의 UTC 날짜는 **하루 앞**인데(KST), 「오늘」(`new Date()`)은 낮에 UTC 날짜와 로컬
날짜가 **같다.** 둘의 어긋남이 서로 달라서 **한쪽만 밀린다.**

증상: **같은 계약이 아침에는 만료로, 자정 직후에는 아닌 것으로 읽힌다.**
`deriveTenantStatus` 의 「계약중·만기 임박」 판정도 같은 셈을 쓰고 있었다.

`Date` 끼리 비교하는 자리는 전부 `day.ts` 의 `daysBetweenLocal` 로 모았다.
**문자열(`YYYY-MM-DD`)을 다루는 자리는 반대로 UTC 다** — 시간대가 없으니 흔들릴 것이
없고, 거기서 로컬을 쓰면 오히려 밀린다. 그 구분을 `day.ts` 머리말에 적어 뒀다.
