# 1장. 로그인

## 1-1. ★ 확정된 방식

```
랜딩 페이지 · 로그인 화면 UI      ERP 가 만든다 (ERP 디자인)
이메일 · 비밀번호 확인            삐용 백엔드 (기존 API 그대로)
JWT 발급                        삐용 백엔드 (기존 그대로)
```

**삐용 로그인 엔드포인트를 수정하지 않는다.** 8월에 오픈한 실서비스이고, 로그인이 깨지면 아무도 못 들어온다. ERP 는 **기존 API 를 부르기만** 한다.

## 1-2. 흐름

```
① 사용자가 erp 주소 접속
② ERP 랜딩 페이지 (ERP 디자인)
③ ERP 로그인 화면에서 이메일 · 비밀번호 입력
④ ERP 프론트 → 삐용 로그인 API 호출
⑤ 삐용이 JWT 발급
⑥ ERP 가 자기 쪽에 토큰 저장
⑦ 이후 모든 요청에 그 토큰을 실어 보냄
```

**계정은 삐용 한 곳뿐이다.** 삐용에 계정이 있으면 ERP 에도 그대로 로그인된다.

## 1-3. ERP 가 만들지 않는 것

```
✗ 직원 테이블 · 비밀번호 저장
✗ 회원가입 화면
✗ 비밀번호 재설정 · 변경 화면
✗ 이메일 변경 화면
✗ 자체 토큰 발급 로직
```

**계정 관리는 전부 삐용이다.** 비밀번호를 잊은 사람은 삐용에서 재설정하고 ERP 로 돌아온다. ERP 로그인 화면에 "비밀번호 찾기" 를 둔다면 **삐용 해당 화면으로 보내는 링크**로 만든다.

## 1-4. CORS — 허용 목록에 주소만 추가한다

삐용 백엔드가 ERP 주소의 요청을 받아줘야 한다.

**★ 전체 허용으로 열지 마라.** 주소를 하나 추가하는 것으로 끝낸다. 로그인 엔드포인트는 가장 위험한 자리다.

이 작업은 **삐용 쪽에서** 한다. ERP 개발 쪽은 **확정된 접속 주소**만 알려주면 된다.

## 1-5. 토큰 갱신 — 삐용과 같은 방식을 따른다

토큰에는 만료가 있다. 삐용이 자동 갱신을 하고 있다면 **ERP 도 같은 방식을 그대로 구현한다.** 안 그러면 작업 중에 갑자기 튕긴다.

**★ 갱신 방식을 ERP 가 임의로 정하지 마라.** 삐용 쪽 구현을 확인하고 맞춘다 (4장 확인 항목).

## 1-6. ★★ 토큰 내용을 믿고 판단하지 마라

토큰 안에 직원번호·회사번호·회원유형이 들어 있어도, **그건 화면에 이름 띄우는 용도까지다.**

```
○  화면 상단에 "홍길동 (에스원테크)" 표시
✗  토큰의 회원유형을 보고 메뉴를 열고 닫기
✗  토큰의 회사번호를 API 요청에 실어 보내기
```

**"이 사람이 이 화면을 쓸 수 있는가" 는 반드시 삐용 API 에 물어본다.**

프론트에서 토큰을 풀어 판단하면 브라우저에서 고칠 수 있다. **8월에 남의 회사 명부가 열린 사고와 같은 종류다** — 회원목록 API 가 회사번호를 요청에서 그대로 받아 생긴 일이었다.

## 1-7. 로그인은 됐는데 ERP 를 못 쓰는 경우

**삐용 계정이면 누구나 ERP 로그인에 성공한다.** ERP 기능을 하나도 구독하지 않은 회사 직원도 통과한다. 그러면 판정이 전부 막아서 **빈 화면만 보게 된다.**

**→ 로그인 직후 그 회사가 ERP 기능을 하나라도 쓰는지 확인하고, 없으면 안내 문구를 보여준다.**

```
"이 계정은 ERP 이용 권한이 없습니다. 담당자에게 문의하세요."
```

## 1-8. 감수하는 것 — 두 번 로그인

주소가 다르면 브라우저 저장소가 갈린다. 삐용에 로그인해 둬도 **ERP 는 다시 물어본다.**

둘 다 매일 쓰는 사람은 에스원테크 직원 몇 명뿐이라 지금은 감수한다. 나중에 불편해지면 쿠키 방식으로 옮기는 길이 있고, 그때를 위해 **같은 상위 도메인 아래**로 두는 것이 좋다.

# 2장. 권한관리

## 2-1. ★★ ERP 는 판정하지 않는다

**ERP 는 자체 권한 모델을 만들지 않는다.** 역할 표도, 권한 표도, 화면별 접근 제어 로직도 두지 않는다.

**사유** — 두 군데서 판정하면 규칙이 두 벌이 되고, **한쪽만 고치는 사고가 난다.**

```
ERP 화면 진입 → 삐용에 "이 사람이 이 화면을 쓸 수 있는가" → 답대로 연다 / 막는다
```

## 2-2. 구조는 4계층이다

```
제품서비스   삐용 · ERP · 메일 Agent          사이드바를 묶는 단위
   └ 기능    회의실 예약 · 세무 · 법무 …       ★ 파는 단위 = 구독 단위
       └ 화면
           └ 동작   조회 · 등록 · 수정 · 삭제
```

**파는 단위는 제품서비스가 아니라 기능이다.** 회사마다 회의실만 쓰거나 회의실+세무+법무를 쓰거나 제각각이기 때문이다.

## 2-3. 화면을 열 때 확인하는 것 네 가지

```
① 그 회사가 그 기능을 쓰는가        구독 · 기간 포함
② 그 사람 역할에 그 화면이 있는가
③ 그 역할에 그 동작이 있는가
④ 볼 수 있는 범위를 만족하는가
```

**넷 다 참이어야 열린다.** 구독을 끊으면 역할을 하나도 안 건드려도 그 기능 전체가 사라지고, 다시 켜면 그대로 돌아온다.

## 2-4. 볼 수 있는 범위는 2종뿐

```
본인 것만     자기가 만든 것만 보인다
회사 전체     자기 회사 것 전부 보인다
```

**부서 범위는 없다** — 값 자체가 지금 스키마에 없다.
**다른 회사 것을 보는 범위도 없다** — 세무·법무를 「판매」로 확정했기 때문이다(2-8).

## 2-5. 역할은 한 사람에 하나

```
김대리 ─── [사원]  ┬ 경비 등록 · 내 결재함     (삐용)
                   ├ 회의실 예약 · 취소        (ERP)
                   └ 메일 계정 연결           (메일)
```

**역할 하나가 여러 제품서비스를 가로지른다.** 입주사 대부분이 4인 이하라, 시스템별로 쪼개면 4명 회사의 관리 대상이 12개가 된다.

**★ ERP 전용 역할을 따로 만들지 않는다.**

## 2-6. ★ 화면을 만들었다고 열리는 게 아니다

**삐용 화면 마스터에 등록돼야 권한을 줄 수 있다.**

```
① 삐용에서 기능을 켠다                                운영사
② ERP 화면을 개발한다                                 ERP 개발
③ ★ 화면 · 동작 목록을 삐용 쪽에 제출한다             ERP 개발  ← 핵심
④ 삐용 개발자가 SQL 로 화면 마스터에 시드한다          삐용 개발
⑤ 회사별로 권한을 부여한다                            운영사 / 회사 대표
```

**③ 을 빠뜨리면 화면은 만들어졌는데 아무도 못 쓴다.** 반대로 권한만 주고 화면이 없으면 "권한은 줬는데 아무 일도 안 일어난다" 가 된다.

### 제출할 항목

**진실원은 코드다.** 라우트에 없는 화면코드를 등록해 봐야 열리는 화면이 없고, 엔드포인트가 없는 동작을 등록해 봐야 실행되지 않는다. **실제 라우트·엔드포인트에서 뽑아서** 제출한다.

| 항목 | 값 |
|---|---|
| 화면코드 | 2-7 규칙 |
| 화면 이름 | 사이드바 · 목록에 뜨는 이름 |
| 경로 | 프론트 라우트 |
| 상위 화면 | 없으면 최상위 |
| 소속 기능 | OFFICE · BOOKING · TAX · LEGAL · BILLING |
| 화면 성격 | 사이드바에 뜨는 화면 / **팝업 · 상세 · 모달** |
| 대상 | **운영사 전용** / 고객사용 / 공통 |
| 플랫폼 | 웹 / 모바일 |
| 동작 | 그 화면의 엔드포인트에서 역산 |

**★ 팝업 · 상세 · 모달을 빠뜨리지 마라.** 마스터에 없으면 권한 체크 대상이 없어져 그냥 뚫린다.

## 2-7. 화면코드 규칙 (제안 — 다른 체계를 쓰고 있으면 회신 바람)

```
S03  ###  ####
 │    │     └─ 순번 4자리
 │    └─────── 업무그룹 3자리
 └──────────── 제품서비스
```

| 그룹 | 기능 |
|---|---|
| `100` | 입주 계약 관리 (운영사 전용) |
| `200` | 회의실 예약 |
| `300` | 세무 |
| `400` | 법무 |
| `500` | 청구 · 수납 |
| `900` | 공통 · 설정 |

**순번은 앞 2자리가 화면, 뒤 2자리가 그 화면에 딸린 것.**

```
S031000010   입주 계약 목록
S031000011   계약 상세 팝업     ← 목록에 딸린 것
S031000020   계약 등록
```

삐용이 이미 쓰고 있는 방식이다(`S022300010` / `S022300011`). 팝업 · 모달에도 코드를 줘야 권한 체크 대상이 되는데, 이 방식이면 부모가 눈에 보인다.

**★ 코드 문자열에서 시스템을 파싱하지 않는다.** 메일 Agent 가 삐용 그룹 90 을 쓰면서 시스템 코드는 S09 인 전례가 있어, 화면 마스터가 시스템을 별도 컬럼으로 갖고 있다. **코드는 사람이 읽는 용도지 판단 근거가 아니다.**

## 2-8. 동작 어휘

```
DB 에 넣는 값      VIEW · CREATE · UPDATE · DELETE
화면에 보이는 것    조회 · 전체
```

'전체' = 그 화면에 정의된 등록 · 수정 · 삭제를 **전부 가진 상태**다. 등록만 있는 화면의 '전체' 는 등록 하나이고 그게 정상이다.

**`APPROVE` · `EXPORT` 는 쓰지 않는다.**

- 결재 권한은 결재선이 정한다. 권한관리는 **결재 화면을 여는 것까지만** 담당한다. 둘 다 두면 진실원이 둘이 된다
- 엑셀 내보내기는 **서버에서 강제할 수 없다**(브라우저가 파일을 만들어 서버 요청이 없다). 막지 못하는 것을 권한 목록에 두면 통제된다는 착각만 준다

## 2-9. 저장할 때 서버가 막는다

화면에서 안 보이게 하는 것만으로는 부족하다. **반드시 서버에서 막는다.** 화면 숨김은 편의이고, 실제 통제는 서버다.

## 2-10. ★★ 운영사 전용 화면은 반드시 갈라 놓을 것

**세무 · 법무는 「판매」다.** 에스원테크는 시스템만 제공하고 고객사 업무에 관여하지 않는다 — 핀테크 사업자 권한이 없기 때문이다.

**→ 에스원테크 직원이 고객사 업무 자료를 보는 화면을 만들지 않는다.** 필요해 보이면 만들기 전에 물을 것.

★ 다만 **입주 계약과 청구 · 수납은 에스원테크 자신의 자료다**(임대인이자 청구하는 쪽). 위 원칙과 충돌하지 않는다. 대신 **고객사에게 보이면 안 된다.**

```
운영사 전용   입주 계약 관리   호실 · 계약 기간 · 보증금 · 임대료
             청구 · 수납      누구에게 얼마를 청구했는가
```

**입주사끼리는 이웃이자 경쟁사다.** 옆 호실이 얼마에 들어왔는지가 보이는 순간 그게 사고이고, **정보가 새는 건 부여를 되돌려도 복구되지 않는다.**

화면 마스터에 등록할 때 대상 구분을 정확히 붙일 것. **하나만 잘못 분류돼도 샌다.**

## 2-11. 회의실 예약 — 로그인 없는 화면

**에스원테크 회의실만 대상이다.** 입주사가 자기 회의실을 외부에 여는 것은 지금 범위가 아니다.

대상이 하나로 고정이므로 **요청에서 받을 회사 정보가 없다.** 서버에 고정한다.

신청자는 회원이 아니라 **데이터**(이름 · 연락처)다. **비회원에게 계정을 주지 않는다** — 주는 순간 그 사람은 회원이고 어느 회사 소속인지를 정해야 한다.

로그인 없는 화면에서 열리는 것은 **빈 시간 조회와 신청 등록 둘뿐**이다. 명부 · 계약 · 다른 신청자 정보는 열지 않는다.

## 2-12. 처음부터 막지 않는다

```
1단계   막지 않고 "막았을 것" 만 기록한다     며칠
2단계   기록이 0건이 되면 실제로 막는다
```

**처음부터 막으면 등록 안 된 화면이 있는 순간 실사용자가 막힌다.** 모바일이 생기면 **전환 전에 전 화면 회귀 확인**을 반드시 한다.

# 3장. 하지 말 것 (요약)

```
로그인
✗ ERP 에 직원 테이블 · 비밀번호 저장
✗ 회원가입 · 비밀번호 재설정 · 이메일 변경 화면 (삐용으로 보낸다)
✗ 자체 토큰 발급
✗ 삐용 로그인 엔드포인트 수정 (허용 목록 추가만)
✗ 토큰을 풀어 메뉴를 열고 닫기
✗ 토큰 갱신 방식을 임의로 정하기

권한
✗ ERP 자체 권한 모델 (역할 표 · 권한 표 · 접근 제어 로직)
✗ ERP 에서 권한 판정 (삐용 API 에 물어본다)
✗ ERP 전용 역할
✗ 화면 등록 없이 화면 개발 끝내기 (2-6 ③)
✗ 팝업 · 상세 · 모달을 화면 목록에서 빼기
✗ 운영사 전용 화면을 고객사 화면과 섞기
✗ 부서 범위 · 다른 회사 범위 (2종뿐이다)
✗ APPROVE · EXPORT 동작
```

# 4장. 회신 · 확인 바람

## ERP 개발 쪽 → 삐용

```
① 확정된 ERP 접속 주소               → CORS 허용 목록에 추가해야 함
② 화면 목록 (2-6 제출 항목 형식)      → 시드 명세 작성
③ 다른 화면코드 체계를 쓰고 있는가    → 2-7 확정
```

## 삐용 쪽 → ERP 개발

```
④ 토큰을 어디에 저장하는가           로컬 저장소 · 세션 · 쿠키
⑤ 토큰 만료 시간과 자동 갱신 방식
⑥ 토큰에 무엇이 들어 있는가           표시용으로만 쓸 것
⑦ 로그인 API 규격
```

**④⑤⑥⑦ 은 삐용 로그인 성공 처리 코드 한 곳에서 다 나온다.**

**막히지 않는 순서** — ①②③ 을 회신하고 ④~⑦ 을 받기 전까지, **랜딩 페이지와 로그인 화면 UI**, **입주 계약 테이블 설계**, **화면 개발 자체**는 먼저 진행할 수 있다.
