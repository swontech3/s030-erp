## B. 레거시 결함 5건 — 각각 어떻게 했는가

### ① 버킷 이름이 코드마다 달랐다 → **상수 하나**

레거시는 업로드·조회·삭제가 각자 버킷 이름을 들고 있었고 값이 서로 달랐다. 그래서
**삭제해도 파일이 남았다** — 지우려는 버킷에 그 파일이 없었기 때문이다.

`lib/storage.ts` 의 `FILE_BUCKET = 'erp-files'` 하나뿐이고, **이 파일 밖에서는 버킷 이름을
쓰지 않는다.** 업로드·서명·삭제가 전부 같은 상수를 통과한다.
검증: 재업로드 후 옛 경로가 **실제로 사라지는지**를 스토리지에 직접 물어본다.

### ② 비공개 버킷에 공개 URL 을 저장했다 → **서명 URL · DB 에 주소를 두지 않는다**

레거시는 `/object/public/...` 주소를 `storage_url` 컬럼에 저장했다. 둘 중 하나다 —
링크가 열리면 인증 없이 신분증이 열리는 것이고, 안 열리면 죽은 값이 쌓이는 것이다.
실제로는 후자였다(48행 전부 열리지 않는다).

**`storage_url` 컬럼을 지웠다**(020). NULL 허용으로 남겨 두면 언젠가 누가 채운다.
경로(`storage_path`)만 있으면 서명 URL 은 언제든 다시 만들 수 있다(유효 5분).
화면도 주소를 담아 두지 않는다 — **[보기]를 누르면 그 순간 목록을 다시 받아** 새 주소로 연다.
화면을 열어 둔 채 5분이 지나면 손에 든 주소는 이미 죽어 있기 때문이다.

### ③ 업로드마다 버킷 생성을 시도했다 → **생성 코드를 넣지 않았다**

매 요청마다 쓸데없는 왕복이고, 더 나쁘게는 **버킷 설정을 코드가 덮을 수 있다.**
`erp-files` 는 이미 `public=false` · 10MB · JPG/PNG/PDF 로 만들어져 있고 그것이 마지막
방어선이다. 버킷이 없으면 업로드가 **실패해야 한다** — 조용히 만들고 넘어가면
**공개 버킷이 생길 수도 있다.**

### ④ 스토리지 삭제 실패를 무시했다 → **어느 쪽이 남는지 정했다**

> **정한 것 — 고아 파일이 남는다. 기록 없는 파일은 남기지 않는다.**

고아 파일은 **아무도 볼 수 없다** — 화면은 `tb_cm_file` 을 읽어 목록을 만들고, 버킷은
비공개이며 경로에는 UUID 가 들어간다. 스토리지 용량이 조금 새는 것이 전부다.
반대쪽(기록은 있는데 실물이 없는 상태)은 화면에 「등록됨」으로 보이고 눌러야 깨진다 —
**레거시 48행이 정확히 그 상태였다.**

| 흐름 | 순서 | 실패하면 |
|---|---|---|
| 올릴 때 | ① 스토리지 → ② DB | ②가 실패하면 ①을 되돌린다. 되돌리기도 실패하면 고아 |
| 지울 때 | ① DB → ② 스토리지 | ②가 실패하면 고아 |
| 바꿀 때 | ① 새 파일 → ② DB → ③ 옛 실물 | ③이 실패하면 옛 파일이 고아 |

**어느 경우에도 «DB 에 있는데 스토리지에 없는» 상태는 만들지 않는다.**
모든 실패는 `req.log.error` 로 남긴다 — 무시하지 않는다. 이 규칙은
`routes/files.ts` 머리말에 그대로 적혀 있다.

### ⑤ 권한 판정이 흐름마다 달랐다 → **한 줄을 셋이 공유 + DB 2차 방어선**

업로드·조회·삭제가 **같은 `assertOperator()`** 를 제일 먼저 부른다. 운영사 전용이다.

그리고 020 이 `tb_cm_file` 에 **RLS 를 켰다**(그전에는 꺼져 있었고 정책도 없었다).
정책은 `erp_is_operator()` 하나이고 `FOR ALL` 이다. 라우트에서 역할 검사를 한 줄
빠뜨려도 DB 가 막는다.

| 역할 | `rolbypassrls` | 결과 |
|---|---|---|
| `erp_app` (API 가 쓰는 역할) | **false** | 정책이 적용된다 |
| `postgres` · `service_role` | true | 정책이 **적용되지 않는다** |

> **★ 검증 스크립트를 쓸 때 주의** — `postgres` 로 붙어서 「입주사 스코프로 0건이 보인다」를
> 확인하면 **가짜 통과**다. 그 역할은 RLS 를 통째로 우회하므로, 빈 테이블에서만 참인 결과를
> 정책 덕이라고 읽게 된다. 처음에 실제로 그렇게 적었다가 `verify-cont17.js` 에서 잡혔다.
> 정책 시험은 **`erp_app` 으로, 행이 있는 상태에서** 해야 한다.

## C. 설계에서 정한 것

### C-1. 첨부는 **회사(COMPANY)** 에 붙는다 — 계약이 아니다

신분증·사업자등록증은 회사의 속성이지 계약의 속성이 아니다. 계약에 붙이면
**재계약할 때마다 같은 신분증을 다시 올려야 한다.** `tb_cm_file.target_type` 이 이미
polymorphic 이라 `'COMPANY'` 하나만 쓴다.

따라오는 결과 둘:
- 아직 저장되지 않은 신규 계약(`companyId === null`)에서는 **올릴 수 없다.** 화면이
  「먼저 [임시저장] 으로 입주사를 등록해 주세요」라고 말한다 — 버튼만 죽이면 이유를 알 수 없다.
- **API 는 계약 상태를 보지 않는다.** → C-4

### C-2. 서류 4종과 규칙은 **shared 한 곳**에 있다

`@swonbiz/shared/domain/contract-files` 를 화면과 서버가 **같이** 부른다. 화면에만 두면
화면을 우회한 요청이 통과한다.

| 종류 | 개인 `Z` | 개인사업자 `P` | 법인 `R·A·C·S` |
|---|---|---|---|
| `CEO_ID` 신분증 | 필수 | 필수 | 필수 |
| `BIZ_REG` 사업자등록증 | **선택** | 필수 | 필수 |
| `CORP_REG` 법인등기부등본 | **숨김** | **숨김** | 표시(선택) |
| `EXISTING_CONTRACT` 기존 이용계약서 | 선택 | 선택 | 선택 |

- **숨긴 카드로는 올릴 수 없다.** 화면에 없는 칸을 API 로 찔러 넣는 것을 서버가 막는다
  (개인사업자 회사에 `CORP_REG` → 400 「이 회원구분에서는 등록할 수 없는 서류입니다」).
- 사업자등록증 판정에 `isCorpMemberType` 을 쓰지 않는다. 그러면 **개인사업자가
  사업자등록증 없이 통과한다** — 가르는 선이 다르다(개인 `Z` 만 예외).
- `file_purpose` 문자열은 **레거시 48행이 쓰던 값 그대로**다. 바꾸면 옛 기록과 끊긴다.

### C-3. 검사는 **세 겹**이다

| 겹 | 어디 | 무엇을 막나 |
|---|---|---|
| 1 | 화면 `SectionDocs` | 고른 순간 · 사용자에게 이유를 말한다 |
| 2 | Fastify `routes/files.ts` | 같은 함수로 다시 · `bodyLimit` 이 10MB 초과를 **본문을 다 받기 전에** 끊는다 |
| 3 | 버킷 `erp-files` | `allowed_mime_types` · `file_size_limit` |

10MB 를 넘으면 Fastify 가 연결을 끊으므로 클라이언트에는 HTTP 코드가 아니라
**소켓 오류**로 온다. 그것이 정상이다 — 서버가 임의 크기를 메모리에 올리지 않는다.

### C-4. 「종료된 계약은 읽기 전용」의 범위 — **화면까지다**

계약 폼이 `terminated`·`cancelled` 이면 섹션 4의 [파일 선택]·[교체]·[삭제] 가 사라진다
([보기]는 남는다 — 못 보게 할 이유가 없다).

**API 는 계약 상태를 보지 않는다.** 첨부가 회사에 붙기 때문이다(C-1) — 한 회사가 종료된
계약과 살아 있는 계약을 동시에 가질 수 있고, 그때 「종료된 계약 화면에서 왔다」는 이유로
회사의 서류를 잠그면 **멀쩡한 계약의 서류도 같이 잠긴다.**

> 계약 상태로 첨부를 잠가야 한다면 그것은 「계약 화면에서 온 요청인가」를 API 가 알아야
> 한다는 뜻이고, 지금 구조로는 표현할 수 없다. **판단이 필요한 자리라 남겨 둔다.**

### C-5. 저장 경로 · 원본 이름

```
{operatorId}/companies/{companyId}/{PURPOSE}/{uuid}.{ext}
```

- **운영사 번호로 시작한다.** 나중에 스토리지 정책을 걸 때 경로 접두사로 운영사를 가를 수 있다.
- `operator_id` 는 **회사 → 건물 → 운영사**로 타고 간다. 상수 `1` 을 박지 않는다 — 박으면
  둘째 운영사가 생기는 날 모든 첨부가 1번 것으로 들어간다. 건물이 없으면 400 이다.
- **파일 이름에 원본 이름을 쓰지 않는다.** 「최현수_신분증.jpg」가 경로에 들어가면 URL 에
  사람 이름이 실린다. 원본 이름은 `original_name` 컬럼에만 둔다.
- 020 의 유일 인덱스 `(target_type, target_id, file_purpose)` 가 **한 회사 · 한 종류 · 한 장**을
  DB 에서 보장한다. 애플리케이션만 알고 있으면 동시 업로드에서 두 행이 남고, 그중 한 장은
  **아무도 지울 수 없는 파일**이 된다.

### 남은 것

- **화면 조작 확인은 사람이 해야 한다.** 위 42건은 API·스토리지·DB 를 직접 두드린 것이고,
  「파일 선택 → 미리보기 → 교체 → 삭제」를 브라우저에서 눌러 본 것은 아니다.
- `npm run verify:db` 의 **V2 가 실패한다 — 이 작업과 무관하다.** 그 시험은
  `tb_s080_companies` 가 2행 이상일 때 UNIQUE 위반을 확인하는데 지금 DB 에 회사가 **1곳**뿐이라
  `two[1]` 이 `undefined` 다. 019 게이트 때와 같은 상태다.
- 고아 파일을 **주기적으로 청소하는 장치는 없다.** ④의 규칙상 고아는 생길 수 있고 무해하지만,
  쌓이면 용량이 샌다. `storage.objects` 와 `tb_cm_file` 을 대조하는 정리 작업이 언젠가 필요하다.
