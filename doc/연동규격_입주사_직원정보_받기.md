# 연동 규격 — 삐용 → ERP : 입주사 직원 정보 받기

**작성:** 2026-10-23 · **대상:** 삐용 팀 · **근거:** 결정 2026-10-23 · 삐용 회신 2026-10-23(직원 수정은 `U` 만 동기화)
**짝:** ERP → 삐용 「보내기」는 기존 `erp-member` 의 `U` 를 그대로 쓴다(바뀐 칸만, 빈 칸은 보내지 않음).

삐용에서 ERP 입주사 직원의 정보를 고치면 이 주소를 불러 주세요. ERP 구성원 정보에 반영합니다.

## 1. 주소

```
POST <ERP API 주소>/companies/bbiyong/member-changed
Authorization: Bearer <운영사 회원의 삐용 accessToken>
Content-Type: application/json
```
- ERP API 주소(개발계 · 가동계)는 따로 알려 드립니다.
- 서버끼리 쓰는 키는 만들지 않습니다(연동규격 Q1). 토큰은 **삐용이 발급한 운영사 또는 그 회사 회원의 accessToken** 입니다.

## 2. 부르는 쪽 확인

ERP 는 실어 온 토큰 그대로 삐용 `GET /rest/v1/s021000000/my-menus` 를 부릅니다(2026-10-25 넓힘).
목록에 **단체관리 `S021100010`** 이 있으면 운영사로 받습니다. 없으면 `GET /rest/v1/s021200010/my-orgs` 의
지금 계정(`current: true`) 줄의 `orgId` 가 **`memberId` 의 직원이 속한 ERP 입주사의 단체 ID** 와 같을 때만 받습니다
(그 직원이 ERP 에 있으면 본문 `orgId` 는 이 판단에 쓰지 않습니다). 운영사가 아니면 그 직원이 ERP 에 있든 없든
my-menus 에 **직원 수정 키**(ERP 공통 코드 `BBIYONG_EDIT_GRANT` 의 `MEMBER_SELF` — `화면코드:키`)가 있어야 받습니다
(삐용 통합 시험 C3, 2026-10-25).

**그 직원이 ERP 에 없으면**(삐용 통합 시험 C1, 2026-10-25) 대상 회사는 **본문 `orgId`** 입니다. 본문 `orgId` 가
지금 계정의 `orgId` 와 같고, my-menus 에 **직원 수정 키**(ERP 공통 코드 `BBIYONG_EDIT_GRANT` 의 `MEMBER_SELF` —
`화면코드:키`)가 있을 때만 받습니다. 받으면 아무것도 쓰지 않고 `not_found` 로 답합니다.
my-menus 의 `data` 는 객체 목록 `{ menuCode, keys }` 와 옛 화면코드 문자열 목록을 둘 다 읽습니다.

| 경우 | ERP 응답 |
|---|---|
| 목록에 `S021100010` 있음(운영사) | 받음 |
| `S021100010` 없음 · my-orgs 지금 계정의 `orgId` = 그 직원 회사의 단체 ID(자기 회사) · 직원 수정 키 있음 | 받음 |
| `S021100010` 없음 · 그 직원이 ERP 에 없음 · 본문 `orgId` = 지금 계정의 `orgId` · 직원 수정 키 있음 | 받음(`not_found`) |
| `S021100010` 없음 · 지금 계정의 `orgId` ≠ 그 직원 회사의 단체 ID(남의 회사) · `memberId` 를 읽을 수 없음 · 직원 수정 키 없음 | **HTTP 403** |
| `S021100010` 없음 · 그 직원이 ERP 에 없음 · 본문 `orgId` 가 없음 · 본문 `orgId` ≠ 지금 계정의 `orgId`(남의 회사) · 직원 수정 키 없음 | **HTTP 403** |
| 토큰이 없음 · my-menus 또는 my-orgs 가 거절(401 · 403 · 본문 실패 · 지금 계정 줄 없음) | **HTTP 403** |
| ERP 가 삐용 my-menus · my-orgs 에 붙지 못함 | **HTTP 503** — 잠시 뒤 다시 보내 주세요 |

## 3. 본문

```json
{ "memberId": 851, "orgId": 324, "orgCode": "Z04",
  "memberName": "최현수", "email": "ceo@hanseong.co.kr", "hpNo": "01012345678" }
```

| 칸 | 필수 | 규칙 |
|---|---|---|
| `memberId` | ✅ | 삐용 회원번호(양의 정수). **이 값으로 직원을 찾습니다** |
| `orgId` | | 그 직원이 ERP 에 **없을 때만** 대상 회사로 봅니다(§2). 양의 정수가 아니면 없는 것으로 봅니다 |
| `orgCode` | | 받기는 하지만 보지 않습니다 |
| `memberName` | | 이름 |
| `email` | | 이메일 |
| `hpNo` | | 연락처 · **숫자만**(하이픈 없이 · 02 는 9~10자리, 010 은 11자리, 그 밖의 0XX 는 10~11자리) |

- **받은 칸만 바꿉니다.** 칸이 없거나 `null` · 빈 문자열(`""`)이면 **안 바꿉니다**. 빈 값으로 지우는 일은 없습니다.
- 연락처는 ERP 가 하이픈 넣은 모양(`010-1234-5678`)으로 바꿔 저장합니다.
- 그 직원이 회사의 **대표**이고 이름이 오면, ERP 회사 정보의 대표자명도 같이 바꿉니다.
- 받은 이메일을 **같은 회사의 다른 직원**이 이미 쓰고 있으면 400 이고, 아무 칸도 쓰지 않습니다.
- 받은 값을 삐용에 다시 보내지 않습니다. 같은 수정이 되돌아가지 않습니다.

## 4. 응답

성공은 모두 **HTTP 200** 입니다. 실제로 썼는지는 `applied` · `skipped` 로 알 수 있습니다.

```json
{ "ok": true, "applied": true,  "skipped": null }
{ "ok": true, "applied": false, "skipped": "not_found" }
```

| `skipped` | 뜻 |
|---|---|
| `null` | 반영했습니다 |
| `not_found` | 그 회원번호에 연결된 ERP 직원이 없습니다. 아무것도 하지 않았습니다(장애가 아닙니다) |
| `no_fields` | 바꿀 칸이 없었습니다(전부 빈 값) |

실패 응답:

| HTTP | 본문 | 다시 보내면 |
|---|---|---|
| 400 | `{ "error": "invalid_request", "message": "...", "errors": [{ "field": "hpNo", "message": "..." }] }` — 칸 하나라도 틀리면 **아무 칸도 쓰지 않습니다** | 값을 고쳐야 합니다 |
| 400 | `{ "error": "invalid_request", "message": "같은 회사의 다른 직원이 쓰는 이메일입니다", "errors": [{ "field": "email", ... }] }` | 값을 고쳐야 합니다 |
| 403 | `{ "error": "forbidden", "message": "운영사이거나 그 회사의 토큰이 아닙니다" }` | 토큰 · 역할을 바꿔야 합니다 |
| 503 | `{ "error": "bbiyong_unavailable", "message": "..." }` | 잠시 뒤 다시 보내면 됩니다 |
