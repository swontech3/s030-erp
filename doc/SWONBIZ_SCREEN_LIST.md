## 1. 화면 ID 규칙

```
s030   010   0010   p1
 │      │     │      └─ 팝업 순번 (선택) — 모달·드로어·바텀시트 공통
 │      │     └─────── 화면 순번 4자리, 10단위
 │      └───────────── 업무 구분 3자리
 └──────────────────── 시스템 코드 (SwonBiz ERP)
```

- 파일명 예: `s0300200040.js` / `s0300200040p1.js`
- 팝업은 모달·드로어·바텀시트를 구분하지 않고 모두 `p{n}`
- 순번은 10단위 — 사이 삽입 시 `s0300200015` 형태로 여유 확보

### 업무 구분

| 코드 | 구분 | 비고 |
|---|---|---|
| 000 | 공통 | 인증, 셸, 대시보드, 설정 |
| 010 | 기준설정 | 건물·층·호실·회의실, 표양식 |
| 020 | 입주사관리 | 입주사, 계약, 청구, 멤버 |
| 030 | 세무 | 5차 |
| 040 | 법무 | 4차 |
| 050 | 공개 화면 | **인증 없이 접근** — 랜딩, 신청, 외부 예약, 현황판 |
| 060 | 공간운영 | 회의실 예약, 승인 큐 |

> **050의 기준은 업무가 아니라 인증 여부다.** 라우팅 미들웨어에서 050만 인증
> 제외로 처리할 수 있게 하기 위함. 회의실 예약이 050과 060으로 나뉘는 이유도
> 이것 — 외부 예약은 050, 로그인 예약은 060.

### 대상 구분 (`audience_tp`)

삐용에 화면을 등록할 때 화면마다 **누구에게 내려보내는 목록인가**를 함께 준다.
회신(2026-09-12)에 따라 이 구분은 삐용이 갖고, ERP는 받은 목록만 그린다.
아래 ★ 세 규칙은 같은 회신 §6 으로 **확정**됐다.

| 표기 | `audience_tp` | 뜻 |
|---|---|---|
| **P 운영사** | `P` | 운영사(`org_tp='S'`, 에스원테크) 조직에만 내려보낸다 |
| **공통** | (운영사 전용 아님) | 운영사·입주사 모두에게 내려보낼 수 있다 |
| **무인증** | — | 로그인 전 화면. 목록 판정 대상이 아니다 (050 공개 화면, 로그인) |

> **★ 입주 계약 · 청구 · 보증금은 예외 없이 `P` 다.** 옆 호실의 임대 조건이
> 경쟁사에 한 번 새면 되돌릴 방법이 없다.

> **★ 팝업(`p{n}`)은 부모 화면의 구분을 그대로 따른다.** 부모가 `P` 인데 팝업만
> 공통이면 그 틈으로 같은 데이터가 나간다. 팝업에 독자적인 구분을 주지 않는다.

> **★ "공통"은 같은 데이터를 보여준다는 뜻이 아니다.** 화면이 열리는 것과 그 화면이
> 보여주는 행 범위는 다른 축이다 — 후자는 `company_id` 데이터 스코프가 정한다
> (`doc/ORG_ARCHITECTURE.md` §2-4).

### 관련 스키마

- 테이블 접두어 `tb_s080_*` (SwonBiz ERP · 기존 앱과 공유, 제자리 확장)
- 참고: `s020_*` 삐용 / `s040_*` 법무·세무(계획)

## 4. 미해결 사항

**T7 온라인 신청 폼 (보류)** — 사업자 유무 분기가 계약 폼 필드 의미까지 바꿈.
아래 3건 결정 후 재개 (상세: `HANDOVER_T7_ErpApplyForm.md`)

1. 예비창업자를 계약 주체로 받는지
2. 법인 / 개인사업자를 나누는지
3. 개인(비사업자) 회원의 계약서 종류

**외부 회의실 예약 (보류)** — 추후 검토. 결제는 3차이므로 2차에서는
요청 → 승인 → 확정 흐름만

**기타**

- `BOOKING_QR_URL` 확정 및 인증 화면 `redirect` 파라미터 처리 확인
- ~~권한 관리 화면~~ — **해소.** ERP에 권한 관리 화면을 만들지 않는다. 권한 판정은
  삐용이 하고 ERP는 접근 가능 화면 목록을 받기만 한다 (`지시_ERP_로그인_권한관리.md` 2-1)
- 세션 만료 기본값이 삐용 JWT TTL과 일치하는지 확인

## 5. 대상 구분 — 판단 애매 (삐용 결정 요청)

1차 13화면 중 아래 2건은 **같은 화면 ID를 운영사와 입주사가 나눠 쓸 수 있는가**가
갈리는 자리다. 지금은 둘 다 `P`(운영사 전용)로 잠가 두었다.

| ID | 화면 | 애매한 이유 | 잠정 |
|---|---|---|---|
| s0300200020 | 입주사 상세 | 운영사가 **임의 입주사**를 보는 화면이다. 입주사가 "우리 회사 정보"를 보는 요구가 생기면 ① 이 화면을 공통으로 열고 데이터 스코프로 자사만 남기거나 ② 별도 화면 ID를 신설해야 한다. ①은 화면 하나에 두 대상이 섞여 스코프 실수 한 번이 그대로 명부 유출이 된다 | `P` |
| s0300200040p1 | 계약서 미리보기 | 자기 계약서를 입주사가 내려받는 요구는 실제로 나올 만하다. 다만 이 팝업의 부모(s0300200040 계약 폼)가 `P` 라, 팝업만 공통으로 열면 §1 "팝업은 부모를 따른다"를 깬다 | `P` |

### ★ 결정 (2026-09-12 회신 §6) — 둘 다 ②(별도 화면 ID 신설)

**기존 화면을 공통으로 열지 않는다.** 지금 `P` 로 잠근 상태를 그대로 두고, 입주사용이
필요해지면 그때 **새 화면 ID 를 판다.** 화면 하나를 두 대상이 나눠 쓰면 "이 화면은 누구
것인가"에 답이 둘이 되고, 그 애매함은 코드 리뷰가 아니라 사고로 드러난다.

이 결정은 위 2건에만 걸리는 예외가 아니라 **일반 규칙**이다 — 앞으로 어떤 화면이든
"입주사도 보게 해 달라"는 요구가 오면 그 화면을 공통으로 바꾸는 것이 아니라 새 ID 를 판다.

2차 이후 중 미리 짚어둘 1건:
